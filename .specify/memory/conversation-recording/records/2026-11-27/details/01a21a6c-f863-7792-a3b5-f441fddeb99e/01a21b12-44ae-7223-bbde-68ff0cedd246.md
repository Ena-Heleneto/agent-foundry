规划时主动逐项扫描 C1～C4，并在细化时核对现有证据的适用范围：C1 无使用先例的新依赖/框架/协议；C2 外部系统失败模式未验证；C3 高风险条件未经证实；C4 首次跨包或跨进程契约。记录命中事实；无命中或复用已有验证时也说明依据，用户熟悉技术不能替代证据。豁免条件遵循目标项目治理。

每项必要技术验证写入关联业务闭环的前置 Task 或原 Task 内步骤，包含可证伪假设、具体输入、可核验信号、已有/待补证据及下游依赖。验证通过前不填充依赖该假设的业务；失败记录实际证据并调整路线，只阻断依赖下游，无关工作仍可推进。保留通过的原文件与最小骨架，后续在其上增量填充并复验原技术信号，再独立验收业务结果；技术通过不自动完成业务闭环。

## 增量写法

- Spec Kit 项目由同级 `mvu.md` 集中保存业务闭环详情。plan 的闭环导航只用一处文件级链接：`闭环详情见 [mvu.md](mvu.md)。` 总体方案、推荐顺序和依赖用方案文字说明；逐条 MVU 标题/索引、锚点跳转和 Task 范围列表集中在 mvu/tasks，plan 不再列出。每条详情用几小段说明**闭环结果、节点与关键逻辑、关联 Task 及各自职责、验收信号**；必要范围、顺序理由和技术前置可简述或引用已有依据，不强制完整设计、全分支图或复制 Task 八栏目。
- 每条采用一个稳定标题，标题下先写“状态＋依据”，再接四个详情短段，段首分别为“闭环结果”“节点与关键逻辑”“关联 Task”“验收信号”。结果说明本次局部价值；节点用紧凑顺序或必要判断串起；Task 段说明各自职责；信号段给出具体操作与可观察结果。范围或技术前置在相关短段简述或链接现有方案/验证依据，详细实施方案在实际开工前另存，避免把闭环或任务清单扩成完整功能设计。
- 已有 mvu 先复用原编号、标题和有效内容；尚无 mvu 时读取原 plan 详情并按本次范围迁出，保留原闭环定位在 mvu 中。保存详情后，将 plan 的逐条详情或索引合并为上述一处文件级链接；核对指向旧 plan 锚点的实际引用，在授权范围内改为 mvu 中的对应位置，保留任务与证据事实。不能修改的引用说明位置、影响及恢复条件，不以残留逐条索引掩盖未完成迁移。plan 已是导航时不重新导入为详情；两份活动详情冲突先核对来源与影响，只处理可确定的范围，不凭时间戳覆盖。
- 产物沿用本次授权的 plan、mvu、tasks 及必要引用；历史保护使用项目已有历史材料或版本记录，不自动新建 `plan.history.md` 或其他整份方案快照。既有历史文件不因这条规则自动删除或重写，迁移时保留有效技术方案、原 Task 要求、完成事实及历史证据。
- 闭环及节点不建立独立工程身份或 checkbox；MVU 状态仅展示下节规定的事实摘要。已有 Task 引用真实 ID 并说明职责；任务尚未生成时明确关联待补，生成后补齐实际 ID/职责。一个 Task 可被多闭环引用，工程完成仍按该 Task 原验收判断，不从关联关系自动汇总。
- 写前扫描既有验证单元和全部任务 ID（包括保留历史），先复用覆盖同一目标的条目；只有实际缺口才新增，使用未占用 ID。步骤细化遵循目标项目治理，保留原任务身份及要求。
- 失效规划注明原条目、替代条目及原因，保留历史来源；目标、范围或验收需要变化时先说明影响并按项目治理确认，不把调整做法当成改写已完成事实的授权。
- 对照需求确认没有遗漏原验收；计划、任务和证据引用必须可定位。新增或细化实施任务保持未完成，不能因规划完成勾选。
- 生成或更新任务清单时读取并遵循目标项目的末尾收尾约定，先核对等价未完成收尾 Task 的覆盖与复用；清理范围、局部内容保护、用途待核实项和结案条件均由目标治理决定，不在技能中复制本仓库的完整清理规则，也不因规划而执行清理。
- 重复调用或恢复时重新读取磁盘材料和证据，根据已保存内容继续；不依据聊天记忆重复追加单元/任务，不用新的状态文件管理进度。

## 轻量任务与实施方案

任务条目保存稳定 ID、简洁目标、必要范围/约束/依赖、可核验的整体验收及唯一工程 checkbox；这些是信息职责，不是固定八栏目。先确定 MVU 的业务结果和关系，再把实际工程缺口映射到 Task，不在规划阶段预先填满实现步骤或批量创建方案文件。

实际开工前沿项目治理讨论并保存单 Task 方案，默认位于所属 Spec 的 `implementation/<Task ID>.md`，由原任务链接；详细逻辑和重要工程安排在该方案中维护，规划完成不代表已有实施认可。已有方案、原任务要求和历史完成事实继续保留，只在本次允许修改范围增量衔接，不为换格式重开或删除已完成任务。

## MVU 状态

每条标题下用一行保存 `**状态**：未开始。**依据**：尚无本闭环实施记录，关联职责待任务生成补齐。` 已有任务或证据时改写为真实依据，引用对应 Task、步骤或验收记录；保留后面的四项详情。状态只取以下五种：

| 状态   | 判定依据                                                                                                               |
| ------ | ---------------------------------------------------------------------------------------------------------------------- |
| 未开始 | 本闭环职责尚无实施记录；仅完成规划或生成任务仍属此状态。                                                               |
| 进行中 | 本闭环已有实际推进，仍有实现或修订工作可继续；未勾选 Task 内已完成的步骤也可作为依据。                                 |
| 待验收 | 本闭环所需实现已具备，仍缺按验收信号执行的闭环验证或结论；单独组件/技术验证通过不足以标已通过。                        |
| 已通过 | 已有覆盖本闭环验收信号的实际通过证据，且未出现使其失效的新结果；引用该证据。                                           |
| 受阻   | 真实障碍使本闭环当前必要下一步无法继续；依据写明障碍、影响及恢复条件。仍有可独立推进的部分时保持进行中并说明局部阻塞。 |

按本闭环的具体职责和实际证据判断，不按所有关联 Task 的勾选数量机械汇总；共享 Task 在其他闭环的进度不能证明本闭环已推进或已通过。全部关联 Task 勾选也不能代替闭环验收证据，局部闭环通过也不反向勾选覆盖范围更大的 Task。迁移、增量规划及任务生成后核对状态；相关任务/步骤、验收结果或阻塞条件变化，以及中断恢复时，重新读取来源并在授权保存范围内更新状态与依据。无新事实则保持稳定；新结果推翻旧结论时保留原证据和变更原因，不沿用失效的已通过。

状态是阅读摘要，tasks 与实际证据仍是判定来源，不新增状态文件、独立状态服务、完成比例或并行工程 checkbox。材料不足时写清待核实的依据和影响，不猜测实施已开始或验收已通过；已有摘要无法核实时标明未复核，不伪造状态转移。只读分析只报告不一致，不借核对状态修改材料。

## 任务正文的重组与边界

MVU 改变了有效任务的分组或推进顺序时，将变化落实到任务清单正文。概览、映射表或“建议下一步”只能辅助阅读，不能让正文继续表达旧的执行路径。任务身份与历史需要稳定，未完成任务的旧位置不因此固定。

1. 对照本次 Spec 与规划描述的授权范围，把有效待办关联到业务结果，识别必要技术前置、共享任务、暂缓工作和已完成的可复用事实。已有 Task 作为现状和职责依据，只调整与本轮业务结果有必要关联的范围，不借局部规划重排整个项目。
2. 先满足真实依赖，再按尽早获得可验收业务结果的推荐顺序，移动完整原 Task 区块并更新所属分组、有效阶段导航和依赖说明。编号只作身份，不按新位置重新编号；原目标、范围、验收、项目要求的字段及证据随区块保留，已确认的阶段批准点不被静默删除或越过。
3. 共享前置只放一处，各闭环引用同一个 Task。跨闭环依赖允许任务不连续，不为凑分组复制工程状态、拆散原交付或把共同前置重复规划。保留已完成及归档内容，不能将它们重新列成待办。
4. 保存前比较原身份/完成事实、验收覆盖和引用；核对新正文的可执行顺序、下一组任务、技术阻塞边及末尾收尾。确认未引入循环、断链或重复条目，旧分组与新正文冲突的导航一并更新。重复调用以已保存正文为准，无实际变化时保持稳定。

按实际材料处理不适合移动的部分：

| 核查结果                                                      | 处理方式                                                                                                                                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 原正文已经符合本次闭环、依赖和有效阶段安排                    | 复用原顺序；无其他缺口时不改 tasks，不为记录“检查过”追加无信息章节。                                                                                      |
| 阶段/外部执行约定明确固定某区段，或有其他执行者正在写入该范围 | 保持该段原位与事实，说明具体位置、约束依据和解除条件；重组不受约束的部分。需要改变已确认安排时先列影响并取得对应确认，不把已有 Phase 标题本身当冻结依据。 |
| 循环依赖、身份冲突或必要材料缺失，无法安全确定局部顺序        | 指出冲突 Task、缺失依据及影响边界，不猜顺序、不偷偷删除依赖；只暂缓相关重排，其他有依据的部分继续。核对或确认后再从原身份续接。                           |
| 保存或格式检查受阻                                            | 按下节报告已写/未写与恢复入口，停止依赖该保存结果的动作；不改权限、替换保护文件或伪报已经重排。                                                           |

保留或暂缓必须对应可核实的约束，输出受影响范围、当前仍可推进的路径和继续条件。编号不连续、旧技术分组、跨闭环共享或依赖较多，都不构成整份清单保持旧序的理由；局部受限不能报告为全量完成，也不能无依据阻止其他调整。

## 保存与恢复

1. 先核对可写范围与原 Task/证据，复用项目已有历史来源；先保存闭环详情并检查格式、读回，再收敛 plan 为一处文件级链接并更新总体推荐顺序，最后保存获授权的任务及其他引用，并依实际任务/证据核对 mvu 的状态＋依据。逐份核对引用、覆盖与原 ID/状态/验收/证据，确认每条 MVU 状态有依据、plan 无逐条 MVU 索引或 Task 范围列表，且未自动增加整份方案快照，才报告本轮规划保存成功。无实际变化时不为表示“检查过”改写文件。
2. 任一保存、格式检查或读回失败，停止受影响的后续动作。报告具体失败、已写入与未写入部分、尚未一致的引用及恢复入口；不宣称原子回滚、全部保存或验证通过。
3. 不通过改权限、替换受保护文件或绕过项目限制来掩盖失败。障碍解除后，从实际已保存材料恢复，只补未完成写入与检查，复用已建立的单元和任务身份。

# 业务节点实施顺序

在原任务内完成当前局部结果，核对真实前置后推进依赖它的步骤。节点是推进范围，沿用项目原任务与证据，不另建节点身份、编号、checkbox 或状态。

业务目标已明确、尚无正式任务时也可加载本技能，用于规划当前节点的实施路径；加载后仍核对目标项目及当前模式要求的材料与授权，缺少实施前置时只做允许的规划或核查，不自动补建正式任务或进入实现。

1. 读取目标项目有效规范、原目标/任务、当前节点、相关实现、依赖与实际证据，核对本次是规划还是已授权实施。Spec Kit 项目沿用其有效材料；其他项目沿用已有目标、任务和记录布局，不要求创建 `.specify`、MVU 或 Task ID。缺少必要目标、前置或授权时说明具体影响，仅暂停依赖它的操作；可继续已授权的无关工作。
2. 在原任务步骤中给出当前节点的预期结果、改动范围、适用顺序和可观察验收。默认展开当前节点适用的“数据设计/实现 → 后端业务或接口 → 验证逻辑 → 前端页面”。实际核对并复用已有成果与适用证据；无数据/后端职责时说明不适用层。需要调序时写明可核验的依赖与理由，例如先观察只读原型的文案布局；标明原型验证范围和仍缺的正式业务验收。
3. 在有效前置上仅实施已授权的当前范围。一个节点可只是一条接口，不必先补完整个 MVU 或所有业务后端，也不必为每条接口制作页面。页面依赖多个接口时，分别完成并验证接口，再汇合接入；正式页面接入后仍按其职责验证实际交互和所属业务结果。
4. 按职责和风险选择自动测试、实际接口请求、必要的临时页面或其组合，沿用项目必需检查。记录具体输入、预期和实际结果，覆盖正常及适用异常、权限边界；编译或路径存在不能代替业务验证。失败、未执行、证据不足分别如实保留，不计通过；仅阻止受影响下游，修复后实际复验再续接，无关且已授权工作可继续。
5. 按原任务或已有等价记录保存：本次范围与顺序理由、复用/不适用依据、实际改动、验证及未测范围、影响下游和下一动作。重复调用或恢复先读原记录与真实文件，只续做未完成部分。节点通过、原任务完成、MVU 业务验收、用户认可和学习掌握各按原条件判断，不能相互代替。

def find_record(scope):
    """优先复用经来源核实的记录，绕开新命中的 Git 忽略位置。"""
    suffix = Path("records") / scope.opening / f"{scope.session}.md"
    roots = list(candidate_roots(scope.project))
    files = git(scope.project, "ls-files", "-z", "--cached", "--others", "--exclude-standard",
                "--", f":(glob)**/{suffix.as_posix()}")
    ignored = git(scope.project, "ls-files", "-z", "--ignored", "--others", "--exclude-standard",
                  "--", f":(glob)**/{suffix.as_posix()}")
    known = {base / suffix for base, _ in roots}
    known.update(scope.project / os.fsdecode(path) for path in (files.stdout + ignored.stdout).split(b"\0") if path)
    existing = []
    superseded = set()
    for path in sorted(known):
        if not inside_project(scope.project, path) or not path.is_file():
            continue
        content = path.read_bytes().decode("utf-8")
        first_turn = TURN_HEADER.search(content)
        marker = RECORD_HEADER.search(content, 0, first_turn.start() if first_turn else len(content))
        if not marker:
            # 保留并复用具备相同会话头的旧版记录。
            if f"会话 `{scope.session}`" not in content:
                raise ValueError(f"主记录同名文件归属不明：{path}")
        else:
            saved = json.loads(marker[1])
            if (saved.get("session"), saved.get("project"), saved.get("origin")) != (
                scope.session, str(scope.project), str(scope.origin)
            ):
                raise ValueError(f"主记录会话来源不符：{path}")
            superseded.update(scope.project / item for item in saved.get("previousRecords", []) if isinstance(item, str))
        existing.append((path, content))
    eligible = [(path, content) for path, content in existing if path not in superseded and visible(scope.project, path)]
    if len(eligible) > 1:
        raise ValueError("存在多份可写的同一会话主记录")
    if eligible:
        return eligible[0]
    for base, reason in roots:
        path = base / suffix
        if not path.exists() and visible(scope.project, path):
            details = {"session": scope.session, "project": str(scope.project), "origin": str(scope.origin),
                       "root": str(base.relative_to(scope.project)), "reason": reason}
            if existing:
                details["previousRecords"] = [str(path.relative_to(scope.project)) for path, _ in existing]
                details["restartTurn"] = scope.turn

def quoted(label, value):
    """为多行原话添加可逆的 Markdown 外层前缀。"""
    return f"> - **{label}** " + "\n>   ".join(value.split("\n")) + "\n"


def detail_blocks(document):
    """用围栏外的事件定位保持已确认块，按原位置重试不完整块。"""
    starts = []
    fence = None
    offset = 0
    for raw in document.splitlines(keepends=True):
        line = raw.rstrip("\r\n")
        if fence:
            if line == fence:
                fence = None
        elif re.fullmatch(r"~{3,}text", line):
            fence = line.removesuffix("text")
        elif match := DETAIL_EVENT.fullmatch(line):
            starts.append((offset, match[2], match[1] == "event"))
        offset += len(raw)
    blocks = {}
    for (start, key, complete), (end, _, _) in zip(starts, [*starts[1:], (len(document), None, None)]):
        blocks[key] = (complete, document[start:end])
    return (document[:starts[0][0]] if starts else document), blocks


def detail_document(scope, path, events):
    """逐项确认附件与详情，再把可用的链接交给主记录。"""
    target = path.parent / "details" / scope.session / f"{scope.turn}.md"
    if not visible(scope.project, target):
        raise OSError(f"详情路径不在可写的 Git 范围：{target}")
    owner = f"<!-- foundry-detail {scope.session} {scope.turn} -->"
    header = f"# 对话经过\n\n会话 `{scope.session}` · 轮次 `{scope.turn}`\n\n{owner}\n"
    previous = target.read_bytes().decode("utf-8") if target.is_file() else header
    if not previous.startswith(header):
        raise OSError(f"同名详情归属未确认：{target}")
    prelude, blocks = detail_blocks(previous)
    for event in events:
        key = sha256((event.identity or f"{event.location}:{event.label}").encode()).hexdigest()
        if key in blocks and blocks[key][0]:
            continue
        length = max((len(match[0]) for match in re.finditer(r"~+", event.value)), default=0)
        fence = "~" * max(3, length + 1)
        pieces = [f"## {event.label}\n\n- 来源定位：{event.location}\n\n{fence}text\n{event.value}\n{fence}\n"]
        complete = not event.provisional
        for attachment in event.attachments:
            checksum = sha256(attachment.data).hexdigest()
            name = Path(redacted(attachment.name))
            filename = f"{name.stem}-{checksum}{name.suffix}"
            text = attachment.data.decode("utf-8", errors="surrogateescape")
            if redacted(text) != text:
                pieces.append("\n- 附件缺口：原件包含需省略的内容。\n")
                continue
            original = target.parent / "attachments" / filename
            if not visible(scope.project, original):
                pieces.append("\n- 附件缺口：原件目标不在 Git 可见范围。\n")
                complete = False
                continue
            if original.is_file() and original.read_bytes() != attachment.data:
                pieces.append("\n- 附件缺口：同一摘要路径已有不同内容。\n")
                complete = False
                continue
            try:
                atomic_write(original, attachment.data)
            except OSError:
                pieces.append("\n- 附件缺口：原件写入或读回失败。\n")
                complete = False
                continue
            pieces.append(f"\n- [附件](attachments/{quote(filename)}) · SHA-256 `{checksum}`\n")
        status = "event" if complete else "pending"
        blocks[key] = (complete, f"<!-- foundry-{status} {key} -->\n" + "".join(pieces) + "\n")
    atomic_write(target, prelude + "".join(block for _, block in blocks.values()))
    return target.relative_to(path.parent).as_posix()

- **会话**保存宿主会话标识、交互入口证据、解析后的来源仓库根目录、首次有效工作目录、本地开启日期、仓库相对资料根和选择依据。标识与来源归属一起定位主记录和详情。项目记录启用后的交互式恢复须核对原会话归属和恢复后的有效工作目录。两者均可核实在目标仓库内时，在合规的原资料根接续原日期和文件。归属不符或无法核实时，既有记录可查，本次跳过新建、续写及正文补读。
- **对话轮次**按宿主轮次及真实记录定位归属。主记录块保存该轮日期、宿主轮次 ID、用户发起和同轮补充、最终回复原文及可核实的过程短句。详情文件按事件顺序保存可取得的可见进度、推理摘要、工具名称、参数和输出，以及原件引用。单次工具调用的工作目录是该轮详情的一部分，事件按已有的会话归属关联。
- **附件**关联所在会话、轮次和对应工具事件，包含原件的本地相对位置。同名但内容不同的附件占用不同路径，每条详情链接都指向该事件的原件。附件条目区分实际保存、部分可取得、当前不可取得。
- **记录缺口**指出可识别的轮次、事件或附件，记录实际缺失范围和原因。原文仍可取得时才可重试保存。重复恢复时，每个已确认事件只保留一次，相同文本的不同事件分别保留。

在读取会话正文或写入前，先用当前轮次的交互归因、原会话归属及有效工作目录核实范围。宿主回调被调用只说明事件到达，实际用户发起的轮次以可核实的宿主身份定位。同一事件的重试按会话、轮次和事件身份核对，分别保存不同轮次的相同原话。仅为记录本身保存、复制记录附件、核对断点和读回确认的内部工具活动不进入待记录集合。业务工具、用户要求查阅记录及提炼和分析派发仍按其实际用途保存，恢复时保持同一边界。

会话经归属核对后建立关联，首条正常对话消息触发建档。写入按会话短时协调。用户原话先写入并读回，再开始对应业务动作。正常最终回复以该轮实际发出的全文为准，发送结束后自动完成写入和读回，按同一轮次保留一份。详情和附件各自确认后补充对应链接。部分写入时保留已确认范围，可核实原文的重试保存后再次核对关联。资料区当时不可写时在会话呈现缺口。归属可核实的恢复按已确认的断点续写，原文丢失的内容保留缺档。首次自动提炼只从新流程确认的记录块取证。

T035 将安装来源、版本、信任读回结果及实际时间顺序留在既有验收记录中。以对应会话和轮次关联回复发送结束、项目文件写入完成及实际读回的证据。分段输出以实发全文核对完整性，保存区中的业务资料沿现有文档定位。 [验收指南](quickstart.md#记录验收)

提交例外以每次实际提交步骤及其结果回复为边界，这些事件的主记录、详情和附件写入均为零。同一轮提交失败后、重试前的修复恢复正常记录，下一次提交再次跳过。正常运行和恢复均按实际步骤匹配，保留两次提交间的修复事件。

## 特点与规则

- **特点**使用一份独立文档，包含描述、适用情境、证据解释及一个或多个原始对话定位。定位含来源仓库、项目目录、会话、轮次和详情块。同一用户在本仓库不同项目目录的记录可共同作为依据，文档可指出证据是明确表达、重复行为或一次性决定。
- **规则**包含适用情境和可执行行为。规则溯源在本地保存与特点的多对多关联。删除规则时，清理仅支持这条规则的特点及其关联，共享特点与原始对话仍可供其他规则使用。
- **协作 Skill**由当前生效规则及目录内所需资源组成。有效 `name` 与目录名匹配，`description` 表达使用情境。新的分析结果在发布前核对当前规则版本。旧结果与删除发生冲突时保留当前删除决定，后续有效处理中可重新形成规则。

共享规则以解析后的本地资料区和协作 Skill 身份定位。分析交接保存派发时版本与独立候选来源；子代理只写候选，不直接覆盖当前规则、依据关联或生效目录。同一份 Skill 的“版本核对与采纳在同一次写入协调内完成”，删除也进入该边界并推进版本。若版本已变化，候选保留为未采纳，当前版本不变，后续重新判断最新材料；不按回传先后自动合并，不永久屏蔽被删除规则。

40-## 稳定定位

43-| --- | --- |

47:| 会话 | 宿主真实会话标识与来源归属共同定位；标识不可取得时标出身份缺口，不捏造宿主 ID |
48-| 开启和结束 | 可核实的开启时间与本地日期、正常关闭/用户停止/中断或恢复事实；不可确定的部分保留缺口 |
49:| 轮次 | 宿主轮次及真实记录的归属，必须能定位到该会话的主记录块及实际详情文件 |
50-| 事件 | 真实事件标识，或经验证可以稳定回读的来源位置；相同正文不是同一事件的证据 |
51:| 文档定位 | 相对仓库的资料根、实际选址依据、资料根内的相对文件路径与块锚点；续写和重试保留原身份与有效定位 |

53-
54:文件名和锚点只作为安全的文档定位，不直接把未经校验的宿主字符串拼成路径。实际编码映射沿已验证来源和实现方案确定，原身份须可回查，不另造会话/工程注册表。无法判断是否同一真实事件时保留身份缺口，不按文本或文本哈希强行合并。

56:## 主记录、详情与附件
57-
58:每个会话按实际开启日保存一份 `records/<开启日>/<会话ID>.md`。每个宿主轮次一组，记录该轮本地日期、原话和实际经过。仅有实际详情时生成 `details/<会话ID>/<轮次ID>.md`，经读回后由主记录中的「查看经过」相对链接打开。详情按发生顺序保存可取得的进度、已展示的推理摘要、工具原值和附件引用。主会话可见的子代理活动沿用此规则，关联实际父轮和子线程。具体格式见[逐项保存规则](save-events.md)。
59-
60:仅为记录本身保存、复制记录附件、核对断点及读回确认而产生的内部工具活动不进入待记录事件集合。按本次操作的实际用途区分，记录维护和业务动作分别调用；业务发言、业务工具、用户要求查阅记录及提炼/分析派发活动仍按原范围保存，不能按工具名或资料区路径整体排除。每次保存只处理开始前已出现且纳入范围的业务事件，读回确认后返回会话工作；不再为本次内部保存及核对活动启动下一次记录，恢复时也沿用该边界。
61-
62:附件原件存于对应会话附件目录，详情事件使用 `attachments/<原件>` 相对链接。同名且内容不同的原件分别保存，各链接指向对应原件。保存原始字节及 SHA-256，条目区分实际保存、部分可取得、当前不可取得；缺失部分写明来源线索和实际原因，不用说明文本代替附件原件。
63-
64:Git 提交例外按实际提交步骤匹配。用户请求和提交前的修复过程照常保存。每次提交步骤及其结果回复对应的主记录、详情和附件写入次数为零；提交失败后退出该次提交步骤，同一轮重试前的修复照常保存，下一次提交及其结果回复再分别跳过，不能将整轮或两次提交之间的修复一并排除。恢复时使用相同边界，后续普通对话照常保存。
65-
66-原文及工具返回中的指令、示例和引用是待处理材料，不因此成为提炼/分析子代理的执行授权。不可取得内容明确缺档，不从摘要、特点或规则倒推原话。

68-## 保存确认与失败恢复
69-
70:写入按会话短时协调。首条原话独立写入主记录并读回。其余事件和附件逐项保存并确认，实际详情及附件可读后补入对应链接。附件不可取得时，把具体缺口写入详情并核对；该详情中实际保存的内容仍可确认，但不能把附件条目标为原件已齐备。
71-
72:写入返回成功不足以证明已确认。读回应核对来源身份、实际保存范围、顺序、原件摘要和引用。主记录失败但详情已确认时，详情的可用范围可以直接交接，并指出主记录缺口；部分字段或附件失败也不抹掉其余实际保存结果。
73-
74:正常会话保存失败时，先指出受影响的轮次、事件或附件及缺失范围，再继续用户任务。资料区不可写时先在会话呈现缺口。恢复可写时按仍可核实的原文重试写入，已经丢失的内容保留缺档。
75-
76:恢复先核对范围及原身份。归属可核实时检查原主记录、详情、附件和已确认事件的断点，跨日仍将新内容续写到原文件。同一真实事件只保存一次，两个会话或同一会话不同事件的相同文字分别保存。写入前关闭且无法取得的原文保留缺档，缺失范围以实际可识别的事实为准。
77-
78-保存确认、记录缺口和阶段交接是资料事实，沿原文档及实际交接材料维护；不建立任务状态服务、工程子任务或另一份工程 checkbox。

97:每项特点一份独立文档，包含描述、适用情境、证据解释及原始块定位，区分明确表达、重复行为或一次性决定。分析消费已确认特点，保留规则到特点的多对多依据关系，输出带情境的可执行规则及完整协作 Skill 候选。最终便携目录只带当前规则和必要资源，原始对话、附件及本地溯源留在资料区。
98-
99:派发失败、线程身份未能核实、结果未返回或产物尚未确认时，保留实际交接范围并继续使用当前有效产物，不以返回一句“成功”冒认已保存或被父代理确认。成功的阶段交接也不自动满足最终安装入口的消费验收。
