# 改动符号 JSDoc 注释

## 核心规则

每次编辑 TypeScript、JavaScript、Vue 或相关前端代码时，凡是本次新增的声明，或本次修改了行为、签名、类型、初始值、业务含义的声明，都必须在声明正上方添加或保留准确的多行 JSDoc 注释。

需要覆盖的改动符号包括：

- 函数、方法、构造函数、赋值给标识符的回调函数、组合式函数、hook、事件处理函数和计算辅助函数。
- 变量、常量、ref、reactive 状态、类字段，以及新增或语义变化的解构别名。对象字面量属性、interface/type 属性、枚举成员等内部成员不单独挂注释，按下方执行流程第 5 条收拢到外层声明。
- 类型、接口、枚举、类型别名、类、模块、导出对象和 schema 定义。

不要为了满足规则去给无关的旧代码批量补注释，除非它们属于同一个被修改声明块且不补会造成风格或含义不一致。

## 执行流程

1. 编辑前，先识别这次可能会新增或修改的声明。
2. 编辑时，在每个改动声明的正上方放置多行 JSDoc 块，格式必须是：`/**` 开始，中间每行以 `*` 开头，` */` 结束。
3. JSDoc 块至少包含一句职责说明；函数、方法、回调、复杂类型或有约束的声明，应按需添加 `@param`、`@returns`、`@template`、`@property`、`@throws` 等标签。
4. 不要使用单行 `/** ... */`、普通 `//`、普通 `/* ... */`、Python docstring、Go 导出注释等格式替代 JSDoc。
5. **不在声明内部写注释**：对象字面量、interface/type 的属性、枚举成员、泛型参数等声明内部（如属性上方）不放 JSDoc；属性语义收拢到外层声明（接口、类型别名、常量、函数）的 JSDoc 块里统一描述。JSDoc 只挂在外层声明正上方。
6. 注释要简短、事实准确，说明符号的职责、含义或约束，不要写“这是新增/修改的函数”。
7. 完成编辑后检查 diff，确认每个改动声明上方都有准确的多行 JSDoc 注释。
8. 使用中文写注释

## 注释质量

优先描述意图、约束或业务含义。

推荐：

```ts
/**
 * 将承运商对账原始行转换为表格可渲染的数据。
 *
 * @returns 标准化后的对账行集合。
 */
const reconciliationRows = computed(() => normalizeRows(rawRows.value))

/**
 * 提交选中的订单发起仓库取消流程。
 *
 * @param orderIds 需要取消的订单 ID 列表。
 * @returns 取消流程提交完成后的 Promise。
 */
function submitWarehouseCancel(orderIds: string[]) {
  // ...
  return Promise.resolve()
}
```

避免：

```ts
/** submitWarehouseCancel 函数。 */
function submitWarehouseCancel() {}

// 提交选中的订单发起仓库取消流程。
function submitWarehouseCancel() {}

/** 新变量。 */
const value = 1
```

## 边界情况

- 如果匿名内联回调无法自然放置直接注释，且该回调有独立业务含义，优先提取为带多行 JSDoc 注释的命名常量。
- 如果声明已经有准确的多行 JSDoc 注释，只在本次改动导致注释过期时更新它。
- 即使项目平时不给简单局部变量写 JSDoc 注释，只要用户明确要求本次改动的变量要有注释，就按本技能执行。
- 不要用单行 JSDoc 或普通行注释凑数；格式不符合多行 JSDoc 时视为未完成。
- 对生成文件、压缩文件、lockfile、snapshot 或机器维护的产物，不主动添加手写 JSDoc 注释，除非用户明确要求修改这些文件并补注释。

## 验证清单

结束前检查最终 diff，并确认：

- 每个新增声明的正上方都有多行 JSDoc 注释。
- 每个修改了行为、签名、类型、初始值或业务含义的声明，都有或保留了准确的多行 JSDoc 注释。
- 注释简洁、有用，并符合附近代码的语言和风格。
- 改动声明的内部（对象字面量、interface/type 属性、枚举成员、泛型参数上方）没有新增 JSDoc 或行注释，属性语义已收拢到外层声明的 JSDoc 块。
- 没有对无关旧代码做大范围注释补充或格式扰动。

# Agent Foundry Spec Kit 工作流宪章

## Core Principles

### I. 工作流职责与边界

本宪章 MUST 只规范 Spec Kit 的需求澄清、方案规划、任务生成、实施协作、验证门禁及流程验收。
条款 MUST 围绕工作流输入、产物、推进条件和记录职责制定，不定义项目技术栈、源码分层、编码样式、
工程检查命令、安全操作或日常仓库协作规则，不为其他规范设置读取入口或优先级关系。

### II. 产物契约与一致性

spec MUST 保存需求、范围和验收；plan 保存总体方案、顺序、依赖及一处 mvu.md 文件级链接；
与 plan 同级的 mvu.md 集中保存小闭环详情；tasks 保留简洁任务和唯一工程 checkbox。详细实施
方案由原 Task 链接，清单不预先展开全部做法。
分析与证据引用有效来源，不重复维护活动闭环详情或工程状态。生成或更新下游产物前
MUST 读取有效上游输入；缺少必要材料时报告缺项，不靠猜测补造已确认需求或已通过结果。

需求、范围或验收变化时 MUST 在受影响产物间核对覆盖、引用和依赖，记录变更依据及未同步部分。
不以更新某一文档自动完成工程任务，也不以历史材料覆盖后续已确认的要求。

需求实质变化时 MUST 在所属 Spec 保留原始输入、可知来源和实际日期，整理稿和后续确认不能
覆盖原文。相关工作流操作须提供简洁分段摘要，讲清问题、解决方向、本次变化、确认或待定与
日期，并关联原文及必要讨论；普通进度和 AI 建议不能被记录成用户原始要求。

### III. 业务闭环（MVU）与技术前置验证

MVU MUST 以可观察、可验收的业务结果为目标，按“有业务意义、能够验收、范围适合推进、顺序有
依据”说明划分、依赖、暂缓内容和调整条件，并结合真实反馈修订。业务结果可以属于当前 Task 的

 * @throws 遇到软链接时携带其路径终止扫描，不跟随链接。
 */
function assertSkillFiles(path: string): void {
  /**
   * lstat 保留链接本身的身份，包括目标已不存在的链接。
   */
  const stats = lstatSync(path)
  if (stats.isSymbolicLink())
    throw new Error(`技能源不能包含软链接：${path}`)
  if (stats.isDirectory()) {
    /**
     * 按名称检查目录内容，稳定定位首个不允许交付的路径。
     */
    const names = readdirSync(path).sort()
    for (const name of names)
      assertSkillFiles(join(path, name))
  }
}

/**
 * 集合扫描使用的发布范围、配置类型及缺配置回调。
 */
interface CollectionScanOptions {
  skipNonRegularConfig?: boolean
  publishOnly?: boolean
  onMissingConfig?: (configurationPath: string) => void
}

/**
 * 按目录读取集合配置，并根据各集合的发布开关过滤。
 *
 * @param sourceDir 集合来源目录。
 * @param options 集合配置读取选项。
 * @param options.skipNonRegularConfig 是否跳过路径存在但类型为目录或软链接等的配置。
 * @param options.publishOnly 是否仅扫描选择参加发布构建的集合。
 * @param options.onMissingConfig 发现缺失配置时收到对应的文件路径。
 * @returns 各集合的源目录和配置。
 */
export async function scanCollections(
  sourceDir: string,
  { skipNonRegularConfig = true, publishOnly = false, onMissingConfig }: CollectionScanOptions = {},
) {
  /**
   * 仅枚举普通集合目录，并按名称排序。
   */
  const names = readdirSync(sourceDir, { withFileTypes: true })
    .filter(entry => entry.isDirectory())
    .map(entry => entry.name)
    .sort()

  /**
   * 并行读取集合配置，保持目录的扫描顺序。
   */
  const collections = await Promise.all(names.map(async (name) => {
    /**
     * 集合的实际源目录，可与配置声明的包名不同。
     */
    const directory = join(sourceDir, name)
    /**
     * 集合顶层的 TypeScript 配置文件。
     */
    const configurationPath = join(directory, 'collection.config.ts')
    /**
     * 检查配置路径是否存在，保留已有配置的文件类型。
     */
    const configuration = lstatSync(configurationPath, { throwIfNoEntry: false })
    if (!configuration) {
      onMissingConfig?.(configurationPath)
      return
    }
    if (skipNonRegularConfig && !configuration.isFile())
      return

    /**
     * 集合模块默认导出的配置。
     */
    const { default: config }: { default: CollectionOption } = await import(pathToFileURL(configurationPath).href)
    if (publishOnly && config.publish !== true)
      return
    return { directory, config }
  }))

  return collections.filter(collection => collection !== undefined)
}

/**
 * 扫描启用技能并拒绝异常目录名及软链接，返回可交付清单。
 *
 * @param sourceDir 集合来源目录，默认使用当前包的 src。
 * @param options 扫描的发布范围及缺配置回调。
 * @returns 包含集合、名称、源目录、目标目录及原技能配置的清单。
 * @throws 配置导入失败、启用项名称非法或实际交付内容含软链接时报错。
 */
export async function scanSkills(
  sourceDir = join(process.cwd(), 'src'),
  options: Omit<CollectionScanOptions, 'skipNonRegularConfig'> = {},
) {
  /**
   * 仅将包含 SKILL.md 的二级目录视为可交付技能。
   */
  const availableSkills = new Set(globSync('*/*/SKILL.md', { cwd: sourceDir })
    .map(file => dirname(join(sourceDir, file))),
  )
  /**
   * 根据当前构建范围读取集合配置，再扫描其中启用的技能。
   */
  const collections = await scanCollections(sourceDir, { ...options, skipNonRegularConfig: false })
  return collections.flatMap(({ directory, config: { packageName, skill } }) =>
    Object.entries(skill)
      .filter(([, { enabled }]) => enabled)
      .flatMap(([name, config]) => {
        assertDirectoryName(name, `${directory}/collection.config.ts 的技能名`)
        /**
         * 名称通过校验后才拼接源目录，不接受跨集合路径别名。
         */
        const source = join(directory, name)
        if (lstatSync(source, { throwIfNoEntry: false })?.isSymbolicLink())
          throw new Error(`技能源不能包含软链接：${source}`)
        if (!availableSkills.has(source))
          return []

        assertDirectoryName(packageName, `${directory}/collection.config.ts 的 packageName`)
        assertSkillFiles(source)
        return [{
          collection: packageName,
          name,
          source,
          target: join('dist', 'skill', packageName, name),
          config,
        }]
      }))
}

## 目标与范围

让集合作者能按 Vite `mode` 声明集合启用条件；共享扫描器先判集合，再扫描集合内已启用技能。既有 `build` 沿用 Vite 默认 `production`；增加 `build:development`、`build:release`、`build:prod`，其中 `build:prod` 显式指定 `production`，与默认 `build` 选择一致。本任务只接包内脚本、配置、扫描及其回归，不执行部署。

本任务不改 `.github/workflows`、`scripts/dev/mount-speckit.sh` 或其他直接调用 Vite 的脚本。工作流和脚本后续按职责明确 mode；在此之前，未显式指定 mode 的直接调用自然采用 Vite 默认 `production`。

## 建议的数据与选择逻辑

1. 集合环境类型限制为 `development | release | production`。`CollectionOption.enabled` 保持可选，支持布尔值或接收当前 mode 并返回布尔值的函数。
2. 扫描函数接收当前 Vite mode；包内构建调用均显式转交 Vite 提供的值，默认 `build` 不加 `--mode`。直接调用扫描或引擎工厂时显式声明 mode，避免函数默认值掩盖遗漏接线。不读进程环境变量，不直接在 Node 扫描模块中用 `import.meta.env.MODE`。
3. 对本功能支持范围外的 mode 明确报错，避免集合误按默认 production 或 development 纳入。
4. 集合选择优先级：
   - 配置有 `enabled`：用布尔值或当前 mode 的求值结果决定是否纳入，显式结果优先于旧 `publish`。
   - 配置没有 `enabled`：`development` 沿用原本地纳入行为；`release` 与 `production` 仅纳入 `publish: true` 的旧配置。
   - 集合通过后再读取技能项并按技能级 `enabled` 过滤；集合插件开关仍按原有逻辑处理。
5. 移除扫描选项及调用点各自按 Vite mode 传入的 `publishOnly` 布尔值，统一传递实际 mode，避免重复环境判定。发布材料仍由 Vite `release` 构建逻辑产生，不在本任务扩展生产材料。

1. 在 `utils/define-collection-handle.ts` 定义带中文多行 JSDoc 的环境类型与集合 `enabled` 类型；保留配置工厂已有默认值。
