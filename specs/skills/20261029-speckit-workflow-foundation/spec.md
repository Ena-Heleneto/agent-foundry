**验收场景**：

1. **给定** 一轮实际对话与工具操作，**当** 回复前留档，**则** conversations 摘要只记录已发生表达、目的、关键结果、影响和必要日志依据；不提前编造回复、工具结果、原话或精确时间。
2. **给定** 新结论、普通进度或纠正，**当** 维护，**则** 新结论关联来源及情境，区分明确表达和暂定观察；影响整体理解才更新 profile，保留被推翻方案与更正关系，重复进度不强造画像结论。
3. **给定** 新会话、中断恢复或画像变化，**当** 协作开始，**则** 读取当前描述并按需查依据；持续协作复用已加载描述，不每轮重读全部历史。不完整历史说明覆盖范围，资料只服务当前仓库。
4. **给定** 仓库画像及对话留档需要维护，**当** 确认规则落点，**则** 由项目协作规范独立维护，工作流宪章不再复制该规则；原路径、真实内容和引用链保持，不能因职责迁移重写历史。

5. **给定** 实施讨论形成关于用户习惯/思路/判断方式的有效认识，**当** 维护画像，**则** 按既有约定核对来源和适用范围，复用或修订结论并更新有影响的当前理解；单Task建模或阶段选择不直接泛化。
6. **给定** 后续出现可应用的真实机会或重复纠正，**当** 回顾画像效果，**则** 核对相关行为及实际断点，按轻量试用方式调整；没有机会、未验证或机制未实现时不报告通过。

### 用户故事 10 - 阅读一致的综合 Spec 分析（优先级：P1）

**优先级原因**：规划变化后需要一致导航来识别缺项、依赖和假设。

用户在 tasks 生成或 Increment 更新后，获得覆盖业务、技术、闭环和任务的统一分析，能看清目标、假设、缺项及证据。

**独立测试**：依据实际Spec创建并刷新核心功能与逻辑概览及原六类分析，核对主要能力、关键规则、来源和缺项提示，不执行暂停模式行为验收。

**验收场景**：

1. **给定** tasks 刚生成，**当** after_tasks 触发 artifact-spec-analysis，**则** 根据最新原始输入和确认、spec、plan、mvu.md 中的闭环及 tasks 新增核心功能与逻辑概览，并输出原业务分析/流程图、技术分析/流程图、MVU里程碑/流转图的适用内容，缺项或冲突明确指出，不冒认为验收通过。
2. **给定** Increment 调整规划，**当** 保存，**则** 显式复用同一能力刷新 analysis/spec-analysis/README.md 及必要分文档，索引和最新闭环、任务一致，不新增 after_increment 事件或第二套生成规则。
3. **给定** 图示与既有辅助产物并存，**当** 组织导航，**则** Mermaid 一图一事、术语有通俗解释且关联实际代码或待建位置；diagrams.md 保留技术图导航职责，历史产物不批量迁移，不生成冲突副本。

4. **给定** 用户希望快速理解当前Spec或检查变更涉及的功能，**当** 阅读分析中的核心功能点，**则** 每项独立成块、用简洁完整文字讲清功能，必要逻辑融入说明；不强制字段模板，需要时可定位有效依据。

### 用户故事 11 - 自然语言与显式调用使用同一准备流程（优先级：P1）

**优先级原因**：自然语言是常用实施入口，只有实际消费同一准备流程，讨论条件才不会随调用方式失效。

用户在 Spec Kit 项目自然表达实施已有任务或规划小闭环时，分别使用共用实施准备 skill 和保留的 Increment 入口，无须先选择 Pair、Tutor 或 Direct。

**独立测试**：实际宿主分别执行自然语言与显式 Implement 的准备流程、自然语言与显式 Increment 的规划流程。三种暂停模式的发现、切换、分工和行为测试全部移出本期。

**验收场景**：

1. **给定** 同一 Spec、原 Task 与授权，**当** 用户自然表达实施意图或显式调用 Implement，**则** 完整加载同一个准备 skill，核对已有方案与真实确认；没有方案时先讨论，不写业务代码。
2. **给定** 用户只是询问或讨论方案，**当** 宿主理解请求，**则** 不把讨论当作已经确认开工，不虚构批准或自动切换协作模式。
3. **给定** 用户明确定位或已有唯一上下文，**当** 准备实施，**则** 核对 Spec/Task 归属；多候选只澄清必要定位，不串用同号任务、不静默改指针。
4. **给定** 项目未初始化、材料或 skill 缺失，**当** 准备实施，**则** 报告实际缺项与继续条件，不自动初始化、不绕过准备或用来源文件冒充正式加载。
5. **给定** 自然语言请求规划 MVU，**当** 进入 Increment，**则** 以 Spec 与可选描述规划，无 Task 参数，保留 plan 前置与已有成果，不因规划自动实施。
6. **给定** hook 已登记但普通自然语言未进入共同准备流程，**当** 验收，**则** 记录真实漏触发与限制，不凭 hook 存在宣称全覆盖，也不向项目级规范追加路由。

### 用户故事 12 - Implement 开工前讨论并消费确认方案（优先级：P1）

**优先级原因**：没有认可方案就实施会偏离用户思路，增加返工和审计成本，是本次修订首先要解决的问题。

用户发起实施后，AI 先核对项目现状并共同讨论实现思路；方案获得认可并成功保存后，原生 Implement 在该范围内推进，恢复时复用仍有效的方案。

**独立测试**：隔离项目和真实宿主分别覆盖缺方案、真实讨论确认、已有方案、逐 Task 边界、普通工程调整、实质偏差、保存失败与恢复；不要求暂停模式参与。

**验收场景**：

1. **给定** 没有有效方案，**当** Implement 准备开工，**则** before_implement 实际加载准备 skill，停止业务实施并进入讨论，不能仅展示 hook 名称后继续写代码。
2. **给定** 用户没有初始思路，**当** AI 实际读取现有材料并提议，**则** 可经讨论认可形成方案；不强制用户独立设计，不用 AI 自评冒充认可。
3. **给定** 已有适用的确认方案，**当** 用户要求续做，**则** 核对代码、记录与有效授权后复用，不重复讨论或重做已完成事项。
4. **给定** 一次实施可能推进多个 Task，**当** 下一个 Task 没有适用的确认方案，**则** 停止其实施并讨论，不能把一次 hook 成功当所有任务已确认。
5. **给定** 方案需要普通工程调整或实质偏离，**当** 实施核对，**则** 前者说明依据并同步记录，后者先讨论受影响范围；不僵硬锁死路径，不擅自改变业务逻辑。
6. **给定** 方案文件、确认来源或记录无法保存/核实，**当** 准备继续，**则** 报告影响并修复，不以文件存在替代有效确认，不推进依赖该记录的实施。
7. **给定** Task 实施结束，**当** 验收和续接，**则** 工程进度回到原 Task 唯一 checkbox，详细方案和实际证据可定位，用户讨论认可不代替工程或业务验收。
8. **给定** 开发与分发新能力，**当** 核对范围，**则** 不改项目级规范、不恢复三模式挂载，保留必要技术验证、已完成事实及外部操作授权边界。
9. **给定** 准备配置无法解析、准备执行失败或条件使准备步骤被跳过，**当** 当前 Task 尚无有效认可方案，**则** 受影响的业务实施仍不能开始；记录实际停止结果、原因和恢复条件。接入不能满足时报告限制并回到方案调整，不把错误提示、注册成功或说明输出当作拦截证据。

### 用户故事 13 - 简洁记录需求变化并找到来源（优先级：P1）

**优先级原因**：简洁摘要和真实原文共同帮助用户判断改变了什么，减少重复阅读长规格的成本。

用户每次改变需求后，都能保留原始输入和讨论依据，并通过简短说明理解问题、解决方向与当前变化，继续定位有效材料。

**独立测试**：使用实际需求变更，核对原文、摘要、讨论及现行要求的关联；允许未知新材料按职责归类，不以目录存在代替内容有效。

**验收场景**：

1. **给定** 用户改变需求，**当** 保存，**则** 所属Spec保留原始输入和实际可知来源/日期，整理内容不覆盖原文，纠正与后续决定可定位。
2. **给定** 需要快速理解本次变化，**当** 阅读简洁摘要，**则** 能读懂问题、解决方向、本次范围及确认/待定，并找到原文/讨论；不需要先阅读全部长Spec。
3. **给定** 产生预设表未列出的必要材料，**当** 落盘，**则** 结合已有约定按职责灵活安排并更新必要导航，保留有效定义/状态的唯一来源，不为未知文件机械新增批准点。

### 边界情况

- 已有 plan 但尚无 mvu.md 时，从原方案读取并在后续规划中增量整理，不把缺少该附属文件误判为缺 plan，也不重建已完成任务；只有 mvu.md 而缺 plan 时仍遵守原方案前置。详情迁出后保留可用定位和历史来源，重复调用不把旧 plan 当另一份活动详情重新导入。
- MVU 状态是任务职责与验收事实的摘要，材料不足须注明待核实或未复核，不虚构实施开始、验收通过或状态转移。旧定位保护通过 mvu 稳定标题及有效入站引用处理，不要求在 plan 残留逐条跳转；保护历史不授权自动生成整份方案快照。
- 工程规范与工作流规范的职责边界必须明确；不得通过互相引用、优先级声明或“同步正文”重新绑定。纯工作流规则可被其模式和 hooks 使用，不等于日常项目规范依赖宪章。
- 提示词独立性不删除其原则中必要的产物角色和定位约定；不得要求读取现有规范或历史材料才获得完整原则输入。
- Spec/Task 不能唯一定位时，先读取现有上下文再报告缺项，不向猜测目录写入。当前工作流暂限 Spec Kit，非 Spec Kit 项目报告不支持，不自动新建 .specify 或回退到其他任务工具；独立 coding 规则沿自身条件使用，不受该工具范围收敛影响。
- 自然语言实施与显式 Implement 共用实施准备，规划与显式 Increment 共用保留的规划入口；三种暂停模式不参与当前发现和切换验收。普通讨论或入口说明问答不自动触发实施，定位不明确时只澄清必要信息，已有明确上下文不要求重复输入正式指令。
- 准备配置解析失败、执行失败或条件跳过均可能导致准备未实际运行；无有效认可方案时，受影响业务实施仍须停止。必须核对真实宿主结果并保留限制及恢复条件，不能假设 mandatory 标记或一次 hook 调用自动保证逐 Task 停止。
- 原始来源与正式入口同时存在不代表应同时公开匹配；迁移须保护未知或用户维护内容，发现控制及附件定位方法在方案阶段验证。缺失或已知过期入口不能通过旁路来源冒充修复，未测宿主及只读识别不能当作真实自然加载通过。
- 用户技术熟悉不代表项目验证已通过，画像也不替代工程证据；业务结果可以是 Task 的局部职责，不强求贯穿所有页面、接口与存储层。
- 通用顺序规则的一次推进可以小到单个接口，不把全部 MVU 作为每次最小实施范围，也不为每个节点补齐数据库与页面。多个接口可按同一页面的真实依赖汇合，不能以此取消各节点验证、跨业务批量推进或提前判定整个 MVU 通过。
- 依赖失败只限制相应下游；未知后续步骤写明补全时机，不把未验的当前步骤推入下游。
- 历史子任务确实存在才迁移，已完成事实保留；覆盖、链接或保存失败时保留原依据并先恢复，不宣称事务性回滚。
- 用户缺席、环境或公开源不可用时分别标记未执行；不模拟反馈、学习掌握、阶段批准或行为验收。
- 工程完成、学习掌握、草稿完成、真实行为、阶段批准与总体结案分开；新入口安装成功不替代旧入口退役及真实行为验证。
- 当前注册的 after_specify 旧 hook 在工程退役前仍按实际配置执行；一次性原意快照存在则跳过，不因本轮修订覆盖。
- 清理粒度可到文件内的代码段、文档段落或注释；不能因局部失效删除整个文件。用途待核实的内容保留并列明位置、原因与后续处理条件，不单独阻止清理任务完成；已确认应清理的内容未处理、必要验证失败或引用受损时，不得标记清理完成。

## Requirements _(mandatory)_

### Functional Requirements

#### 调查、治理与共享基座

- **FR-001**: 必须先调查仓库、现行章程、已安装 Spec Kit 版本及实际指令、模板、扩展、Skill 挂载机制，记录事实与待验证假设；接入方式经 Clarify / Plan 确定，不预设扩展接口。调查产生的 JSON 基线快照必须通过仓库 ESLint 检查；修复快照格式时必须保持解析后的完整数据不变，包括原始提示词、注册行和 hash。允许使用等价 JSON Unicode 转义，不得为通过检查而改写原始记录或放宽检查规则。
- **FR-002**: 保留按复杂度选择验收里程碑的原则，小型验证规则或功能，中型验证完整流程，大型验证持久化恢复或端到端集成；不强制每项包含全部层级。本期不包含三种暂停模式的兼容/切换验收，具体技术条件在plan明确，并沿既有宪章修订治理。
- **FR-003**: 实施前 tasks.md 保留稳定 ID、简洁目标、必要范围/约束/依赖、验收和唯一工程 checkbox；取消强制八栏目及预先内联拓展全部做法。详细方案保存于所属 Spec 的专门目录，一 Task 一文件，由原任务引用，不新增子任务身份或状态。
- **FR-004**: 普通实施请求和显式 Implement 使用同一个准备 skill；没有有效实现方案时先讨论，方案经真实认可并成功保存后开工。已有适用方案复用，普通工程调整与实质偏差按 FR-104 区分。
- **FR-005**: 细化不改变原 Task 的目标、范围、约束、验收或已完成事实；实际业务变更须按治理确认。历史未完成子任务先核对，把有效未完成做法衔接回原 Task 并保留来源；完成结果不追溯改写，不因新规则批量重做已完成工作。
- **FR-006**: tasks 独占工程完成状态并链接详细实施方案；mvu.md 保存业务闭环与职责，plan 保留总体方案及一处文件级 mvu 链接。方案、分析和证据不维护另一份 checkbox、state.json 或子任务身份。
- **FR-007**: 原生spec/plan/tasks/research/data-model/quickstart/contracts/checklists职责保留；后续工作流宪章补齐Spec内产物职责、基础布局和灵活扩展原则，由相应skill执行读写。新增材料先核对已有约定，再按用途和阅读需要安排位置/名称/粒度，必要时扩充分类并更新导航；不要求预列全部文件，不新增文件注册或状态系统，不写项目级路由或批量迁移其他Spec，实质范围/验收变化再讨论。
- **FR-008**: 优先保留原生 Implement，经 before_implement 复用共同准备 skill，不另造实施引擎。中断恢复核对原 Task、方案认可、实际文件和证据，只续未完成部分；三种协作模式研发与验收按 FR-100 暂停。

#### Tutor

**研发与测试安排：暂停；本节仅保留原定义和历史，不参与本期研发、验收或结案。**

- **FR-009**: Tutor 读取指定 Spec/plan/mvu.md/Task；已有 MVU 直接沿用并在原 Task 拓展工程与学习步骤，尚未迁移的原 plan 详情按 FR-080 核对，不因缺 mvu.md 重新生成已有闭环。缺 MVU 时复用 Increment 的规则，但严格限指定 Task 的既有目标、范围与验收；其他 Task 只作依赖引用。范围不足以形成业务结果须说明限制，不扩围或以技术通过冒充业务闭环；缺 plan 提示先规划。
- **FR-010**: Tutor 围绕当前步骤了解必要基础，解释概念、理由、适用条件及限制，提供提示和必要示例，允许回退补基础，不一次性代写后续全部主要实现。
- **FR-011**: Tutor 默认用户亲自编写主要代码，AI 依据实际实现提供检查、反馈和纠错；代写限当次请求且随后恢复原分工。学习依据用户实际解释或实践验证，AI 示例、自动测试、模拟发言或讲解完成不充当掌握证据。
- **FR-012**: 同一 Task 持续维护必要学习续接说明，可暂停、恢复、结束或重新开启并保留历史；学习结果和工程完成分开，不因会话结束、代码通过或报告完成自动认定掌握。

- **FR-081**: 每条 MVU 面向当前 Spec 的局部可验收结果，稳定标题下先写“状态＋依据”，再用几小段说明闭环结果、节点与关键逻辑、关联 Task 及职责、可观察验收信号四项；不强制完整设计、全分支图或八栏目副本，必要范围、顺序理由和技术前置沿用 FR-057～060。任务未生成时明确关联待补，生成后补齐真实职责。状态使用未开始、进行中、待验收、已通过、受阻：仅规划或无本闭环实施记录时未开始；已有实际推进且仍有实现/修订可继续时进行中；实现具备而缺闭环验证时待验收；有覆盖验收信号的实际通过证据且未被新结果推翻时已通过；当前必要下一步无法继续且无独立可推进部分时受阻，并注明障碍、影响和恢复条件。按本闭环职责核对，不按关联 Task 勾选数量汇总，不反向更改工程状态；任务/步骤、验收或阻塞条件变化及恢复时重读并在授权范围内刷新，保留旧证据及更正原因，无新事实则稳定，只读分析只报告不一致。来源见状态确认（原仓库私有记录，未迁移）。

### 关键实体

- **当前入口与准备能力**：Increment 是保留的规划入口，Implement 保持原生入口；自然语言实施及显式 Implement 复用同一个实施准备 skill。来源、附件、官方 hook 与实际加载分别核对，三模式仅保留暂停与历史资料。
- **业务闭环（MVU）**：当前 Spec 内的局部可验收结果；mvu.md 以闭环结果、节点与关键逻辑、Task 职责、验收信号四项保存详情，必要范围、顺序和技术前置可引用已有依据；plan 提供一处文件级链接和整体推荐，tasks 保存工程步骤与状态。每条 MVU 的状态＋依据是 FR-081 定义的事实摘要，不新增工程身份、checkbox 或第二套工程状态；节点仍是说明闭环的阅读定位。
- **Task**：正式工程身份，实施前清单保留简洁目标、必要边界/依赖、验收和唯一工程完成状态，链接详细方案与证据。
- **实施方案**：所属 Spec 专门目录中的单 Task 文件，保存必要逻辑、职责、推进/验收、工程依据、真实讨论认可与调整来源；不是另一份工程状态，字段与写法按需要展开。
- **业务节点或接口**：当前实施推进的局部范围，可以小于一个 MVU；关联所属业务结果、原任务步骤、实际依赖与验证信号，不新增工程身份或状态。节点验证通过与 MVU 业务验收分别判断。
- **知识片段与学习报告（研发暂停）**：保留原 Task 的真实学习记录及稿件来源，当前不新增学习/共同报告验收或作为结案条件，不复制工程状态。
- **影子摘要、结论与描述**：仓库内三层资料，摘要提供依据，结论表达有效理解与情境，当前描述综合协作建议。
- **综合分析**：新增核心功能与逻辑概览，并保留最新需求、闭环和任务的原六类分析及图示；以当前主要能力和关键规则为入口，需要处关联有效原文、现行规则、方案和证据，不承担验收或工程进度。
- **移交与验收记录**：区分主线工程、分发消费、Implement/Increment 实际行为、阶段批准与总体结案；三模式不作为本期移交或结案前置，通过证据链接跨 Spec 回填。
