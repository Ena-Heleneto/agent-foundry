### 一、目标与已选方案

围绕真实业务目标组织最小闭环，让 AI 在用户缺少实现思路时规划路径，在用户有思路时按其思路协作，在用户需要学习时提供导师支持。技术风险验证纳入业务闭环的实现过程。

已讨论并选择：

- 规划与教学合并会减少入口，但二者使用时机不同，用户选择保留 Increment 和 Tutor 两个指令。
- 细步骤独立建子任务会增加身份、目录与进度维护，用户选择直接展开在原 Task 内，删除独立子任务体系。
- 对话逐字留档内容过多，用户选择摘要留档；摘要、有效结论和当前影子描述分开维护。
- 原 Explore 偏向探索未定效果，无法准确表达当前协作方式，改为用户主导式协作 Direct；Guide 与 Review 删除。

### 三、统一 MVU：业务闭环与技术风险

MVU 的目标与完成标准基于业务结果，不以建表、链路联通等技术完成度直接代替业务验收。业务结果可以属于当前 Task 的局部职责，不强制每个闭环贯穿全部页面、接口和存储层。

划分以合理性为重点，不追求唯一正确答案。用户认可四条原则：有业务意义、能够验收、范围适合推进、顺序有依据。AI 必须解释推荐划分、必要依赖、暂缓内容及调整条件，结合实际反馈与仓库内画像修订路径。

AI 主动检查实现业务结果所依赖的技术假设。沿用现行章程 III 的风险识别依据：新依赖/框架/协议无验证先例、外部交互失败模式未验证、方案依赖未经证实的高风险条件、首次建立跨包或跨进程契约。规划时识别，细化闭环时核对证据，实施中新发现不确定性时补充检查。技术熟悉程度影响教学，不能代替项目验证证据；已有适用证据可复用并注明依据。

将必要技术验证编入对应业务闭环的前置步骤；验证失败时阻止依赖该假设的后续步骤，记录证据并调整路线，不自动阻塞无关工作。通过的验证实现作为后续增量骨架保留。业务闭环仍须达到自己的业务验收条件。

plan 保存闭环目标、业务验收、顺序与依赖、技术假设和关联 Task；tasks 保存工程步骤与工程完成状态，证据通过链接引用。不得另造 state.json、子任务管理工具或并行的工程状态系统。具体锚点与显示格式交由实施者确定，保持引用稳定、避免重复维护状态。

### 四、Increment 行为

入口接收可选 Task，优先使用明确 Spec，否则按项目既有上下文唯一定位，沿用实际文件和证据。

| 当前材料                        | 行为                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------- |
| 缺少 plan，不论是否有孤立 tasks | 提示先完成 plan，说明缺项                                                                         |
| 有 plan、无 tasks               | 规划业务闭环，写入 plan，并生成符合项目现有格式的 tasks，承接本次 tasks 生成职责                  |
| 有 plan 和 tasks                | 核对已有实现与证据，补充或调整闭环、任务顺序和依赖，保留已完成事实                                |
| 指定 Task                       | 以该 Task 为切入点，规划所属业务结果；独立调用时可关联同一业务目标下必要的既有 Task，说明影响范围 |

独立 Increment 的跨任务关联与 Tutor 的单 Task 补齐必须区分。关联不等于授权扩大业务范围、改变已完成事实或任意重写其他任务的目标与验收。

检查任务顺序是否只按技术层分组或批量实现，是否忽略用户获得反馈的顺序；根据真实依赖、风险、业务反馈及画像解释和调整，不假设某种固定顺序永远适用。缺少了解用户思路的证据时，先提出可解释的推荐，不虚构画像。

保留 Task ID、已验证结果及证据；新增工作使用未占用 ID，失效规划明确说明替代关系，不把重排变成重新完成历史任务。同步完成后调用同一套 Spec 分析生成能力刷新分析文档，重复调用先核对已有结果，避免重复任务与重复闭环。

### 五、Direct 行为

使用方式：`$speckit-modes-direct [Task] [想法、逻辑或思路]`。上下文已唯一定位时直接续接。

用户决定当前实现思路与下一步方向，AI 参与讨论、独立质疑、按实际分工实施和验证。例子包括先讨论数据库、调整、写 CRUD、接入前端接口，再实现某个组件；不限于视觉效果探索。

允许不按 tasks 排列顺序推进，但核对实际前置依赖、范围与验收。将每次实际改动映射回原 Task 的细步骤、证据及进度，记录当前思路、调整理由、已确认与待定事项和下一步。用户的反馈不自动成为全局需求，也不自动扩大授权。

对话小步直接在原 Task 内维护，不建立独立子任务。用户选择顺序与必要依赖冲突时解释具体影响，讨论可行路径，不能为了跟随思路跳过必要验证。范围内正常协作沿用已有授权，不反复请求同类许可。中断恢复时以实际文件和原记录核对，不重复实施。

### 六、Tutor 行为与 Task 细化

入口：`$speckit-modes-tutor [Task]`。已有 MVU 直接沿用，在指定 Task 内拓展实施与学习安排。

有 plan 和 Task 但缺少 MVU 时，复用 Increment 的规划规则补齐，范围严格限定指定 Task 的既有目标、范围与验收，不关联、纳入或修改其他 Task。外部 Task 可以作为依赖引用；范围不足以形成业务闭环时明确说明限制，不扩围，不以局部技术完成冒充业务闭环完成。缺少 plan 时提示先完成规划。

默认用户编写主要代码。AI 围绕当前步骤了解必要基础、解释概念与理由、提供提示和必要示例，依据用户真实实现反馈、纠错与验证。用户要求代写时按当次范围执行，随后继续原默认分工，不把局部请求解释为后续全部代写。

细步骤直接展开在原 Task 内，写清目的、操作位置、实施做法、依赖和可观察的验证结果，再补充前置知识、讲解、用户实践和反馈。原 Task 的整体目标、范围和工程验收保留。工程通过和学习掌握分别记录，AI 示例或测试不充当用户掌握证据。

每次出现有价值的学习内容时形成知识片段：问题、关键解释、关联代码、用户理解或待巩固点；普通进度不强行生成知识点。Task 结束后基于这些片段与用户共同整理学习报告，归档到 personal-hub 的既有 `apps/personal-hub/content/blog/`。

写报告前读取 `apps/personal-hub/content.config.ts` 与现有文章，沿用 title、description、date、tags、status 等实际格式，初始使用 `status: draft`。在共同讨论形成具体稿件与目标后保存，复用已有稿件，不强制沿用已删除 Review 的双确认流程，不自动发布。工程完成不等于学习掌握或报告已完成，分别如实记录。

### 八、仓库内影子描述

已确认仅服务当前仓库，位于 `.specify/memory/user-shadow/`：

- conversations：每次对话与工具操作的摘要，保留关键表达、理由、纠正和必要上下文；工具摘要保存目的、关键结果、影响及必要日志引用。
- conclusions：提炼的有效结论，关联对话来源和适用情境，区分明确表达与暂定观察。
- profile.md：综合结论形成当前自然语言影子描述及协作建议，避免把单次工程选择泛化为永久特征。

每轮摘要留档；有新结论才更新 conclusions，影响整体理解时更新 profile。保留讨论中被推翻的方案与纠正过程，后续更正用新记录关联旧依据，不伪造原话或精确时间。对当前不可见的历史明确说明覆盖范围，不声称完整捕获所有会话。

按用户接受的默认读取规则，新会话、中断恢复或画像变化时读取；持续协作沿用已加载的当前描述，有需要时检索相关结论与依据，避免每轮重复读取全部历史。每轮在回复前保存已经发生的表达与动作，后续可以补记上一轮实际回复摘要，不提前虚构回复或工具结果。

将仓库级规则写入章程并同步章程提示词，必要时同步 AGENTS.md；不新增跨仓库服务或全局画像。本地 Markdown 文件创建不等于已具备独立后台监听或自动截取会话能力，须说明 agent 实际遵循与验证的范围。

### 十一、验收、顺序与交付

工作流基座为主线，先完成本轮工程交付；随后分发 Spec 承接 Tutor 与 Increment 的真实行为验收。Direct 由用户后续新增的基础业务 Spec 验收。其他本轮需求随工作流基座验收。明确区分工程完成、真实用户行为验收、阶段批准与总体结案，不用未创建样本或旧模式证据冒充通过。

规划和任务须覆盖：Increment 的材料缺失与更新路径、技术风险识别及失败处理、合理划分与进度保留；Direct 的用户顺序、依赖、映射与恢复；Tutor 的单 Task 边界、用户主写、学习证据与知识片段；影子三层记录与纠正；分析创建与刷新；新入口与旧入口退役；分类和治理一致性。

代码实施时执行目标包 lint、check-types、build 和适用测试，检查受影响消费方。TS/JS/Vue 编辑遵循 document-changed-symbols，前端样式与响应式按各自强制技能。Markdown 写完立即执行 pnpm exec eslint --fix 并读回。无法运行的验证逐条写明命令、原因和剩余风险，不运行或声称根级 pnpm test。

本轮先更新规划，不凭本提示词勾选任务或执行发布、部署、数据库及其他外部资源变更。继续原阶段验收约定，保留已完成事实和用户未提交改动。提示词、正式规格、实际实现与验收证据的状态分别报告。
