## 一、当前范围：先交付 Implement

1. 暂停 Pair、Tutor、Direct 三种协作模式的研发，不继续增加这三种模式的适配、自然语言入口、跨模式切换、学习或共同报告能力。
2. 将三种模式的工程专项、入口行为、学习/报告和真实用户验收从当前 Spec 的测试、移交及结案范围移出，不保留为本期必须补测的条件。保留暂停标记、原 Task 身份、完成事实和历史材料，暂停不能记作通过或永久删除。
3. 优先完成原生 Implement 的实施前讨论与方案消费。Increment 保留为 MVU 规划入口；规划与实施分工继续区分，不引入新的实施引擎或协作模式。
4. 采用已选择的第二种方案：工作流宪章规定共同开工条件，一个共用的实施准备 skill 承载讨论、方案保存与恢复，通过官方已有 `before_implement` hook 接入原生 Implement。
5. 这套规则只在工作流宪章、skill、hook 及所属 Spec 产物中维护，禁止写入或要求目标项目写入 AGENTS、CLAUDE 等项目级工程规范，也不增加项目级指令路由。当前阶段不接入三种暂停模式。

## 二、MVU 与实施前 Task 保持轻量

Increment 按当前 Spec 的最小、可逐步推进和验收的业务闭环，或用户提供的描述，形成小 MVU。取消其 Task 定位参数；已有 Task 可以作为现状和职责关联材料读取，不要求先指定 Task 才能规划，不删除 MVU 与真实任务的职责映射。

MVU 主要参考已有用户画像，帮助理解顺序与协作方式；不为每次闭环规划推断新偏好或制造画像结论。结合需求、现有方案、存量代码、真实依赖与已有证据补足思路，保留划分理由和业务验收。

取消宪章和消费者中每个 Task 必须预先填满八栏目、在清单内强制拓展详细实施步骤的要求。实施前的 tasks.md 保留稳定身份、简洁目标、必要范围/依赖、验收及唯一工程 checkbox，并在方案形成后链接详细方案。详细内容按真实需求展开，不能把旧八栏目原样搬到新文件。

## 三、开工前先有经过讨论认可的实现方案

实施请求到来时，实际读取原 Task、需求、plan/MVU、相关存量代码、目标项目规范、已有方案与证据。普通自然语言发起实施和显式 Implement 都使用同一个实施准备 skill。

没有有效方案时，暂停业务代码实施，进入讨论；初始思路可以由用户提供，也可以由 AI 根据项目提出。先听用户自己的方向，再核对遗漏、需求差异、真实依赖与技术可行性，提供有依据的建议。讨论中重要未知影响范围、权限、核心逻辑或验收时说明影响，不自行补成已确认决定。

讨论形成用户认可的方案后即可按有效授权开工，不要求用户预先独立完成设计，也不把后续每次正常续做变成重新审批。已有确认方案先核对适用范围再复用；影响已确认逻辑、职责、范围或验收的实质变化回到讨论，普通工程调整记录依据后继续。

自然语言发现、实际完整加载和进入原生 Implement 分别验证。不得仅凭 hook 存在宣称拦截了所有普通对话；不通过项目级规范补路由。若真实宿主未按预期进入共同准备流程，报告具体漏触发和限制。

## 四、一 Task 一份实施方案，逻辑明确、写法可调整

在所属 Spec 的专门目录保存每个原 Task 的实施方案，由原任务链接，沿用原 ID，不新增独立子任务身份或工程状态。建议目录为 `implementation/<Task ID>.md`，最终名称由后续 plan 统一确定。

方案应让用户能够判断：做成什么、核心逻辑和数据关系是什么、为什么这样做、按什么顺序推进、如何验收；保存用户方向、AI 的项目核对和补全、讨论确认及重要调整理由。写到足以实施和审阅即可，不强制固定栏目、字数或所有字段先列全。

新增文件和写法必须建立在实际读取存量代码及项目规范的基础上。优先复用已有实现；必要新增说明职责、理由和拟放位置。已确认的组织思路需要尊重，具体路径、命名和一般内部写法可以随实际情况调整并同步方案，无须为每个普通细节重复询问。不能借“灵活”改变已确认业务逻辑或跳过规范与验证。

多 Task 实施时不能让一次 `before_implement` 检查自动放行后续所有未讨论任务。明确实际准备开工的范围，确保每个进入实施的 Task 有适用的已确认方案；超出已确认范围时先停受影响部分。后续 plan 必须实测原生入口如何遵守这一边界，不能靠说明文档假定 hook 已控制逐任务推进，也不修改官方生成副本伪造成功。

实际已读原生模板在extensions配置解析失败时仍可继续、对带condition的hook也可能跳过当前直接调用。plan必须核查配置失败、执行失败、条件处理及多Task连续推进的真实结果；若接入无法保证无有效方案时停止，报告限制并调整设计，不把hook登记成功或说明输出当门禁已经有效。

综合Spec分析新增核心功能点内容，一个功能点独立成块，以功能名称和简洁但全面的文字讲清楚这个功能做什么，必要逻辑自然融入说明。内容随功能需要展开，不强制每点填写作用/流程/边界/关联等固定栏目，不以总表代替各点说明，也不扩成完整技术设计。沿用analysis/spec-analysis/README.md及必要分文档，保留原六类分析的适用职责，需要时引用有效材料，不复制活动定义或工程状态。

[核心功能点讨论稿](../discussions/2026-11-10-logic-navigation.md)已按用户纠正改为每功能一块的文字说明，并补入技术验证、续接恢复、独立节点和收尾等原有功能。此前的变更沿革导航和单点固定栏目方案撤回，历史来源仍按需要辅助引用。功能分组按实际需求决定；当前Spec有效要求已核对，实际生成/刷新消费与源码实现尚未验证，不能声称生产分析已交付。

画像核查要区分“保存对话摘要”“提炼有效结论”“汇入当前描述”实际做到哪一层。本次已发现存在结论文件而 profile 未及时吸收的情况，后续核查真实来源与更正，不把全部问题都解释为缺少日志。实施思路讨论是重要事实来源，按目标项目既有记录约定提炼和更新；不新增 AGENTS 条款、不把本仓库个人路径或资料带入对外技能，也不把单次业务选择变成永久偏好。

继续核查“记录很多但总结性结论不足”的实际断点，结合现有材料分别判断是否未提炼、未汇入当前理解或未在后续行为中应用。结果区分已证实原因与未核实部分；当前只证实存在汇总未及时更新的事实，不能把完整原因诊断写成已经完成，也不能仅增加日志就宣称问题解决。历史回查以可见、相关来源为依据，不虚构完整历史覆盖。

用户进一步明确希望画像理解自己的习惯、思路和思维逻辑，并要求AI主动补充范围。[画像讨论稿](../discussions/2026-11-10-user-shadow-scope.md)提出目标动机、判断取舍、思考路径、设计实现、推进反馈、协作自主、沟通审阅、知识基础及质量纠错九个维度；它们是待讨论的AI补充，不是九条已经证实的用户特征。结论需要来源、情境和确定程度，最终画像以连贯自然语言综合，并能在后续协作行为中得到核查，不能只增加记忆文件。

画像的实际应用检查已获用户同意先试用：观察相关理解是否影响提问与方案取舍、实际行为是否符合情境、纠正是否在后续生效。按重要决定在原记录留依据、阶段回顾抽查真实样本、重复偏差时区分提炼/汇总/读取/应用/情境/失效等断点的轻量方式观察效果；不要求逐轮应用报告或用户打分，不把任务事实核查混成人物画像推断。接受试用不表示机制已实现或有效性已验证，后续保留反馈和调整依据。

## 六、验收与后续同步

本期测试覆盖：无方案时停止实施并讨论；AI 提出/用户提供思路后真实确认；已确认方案复用与中断恢复；自然语言和显式 Implement 的同一准备流程；逐 Task 方案边界；轻量清单与独立方案的唯一进度；工程安排合理调整及实质偏差重议；方案/记录保存失败与恢复；原始输入、摘要和关键逻辑的追溯；Increment 无 Task 参数及同版分发。

技术验证仍按实际风险安排，工程最低检查仍遵循目标项目已有要求。讨论认可、必要验证通过和真实业务验收分别判断。Pair/Tutor/Direct 的专项行为、自然语言进入及跨模式测试全部排除；移除旧挂载是交付范围核对，不等于重新测试三模式能力。

用调度中心 T019 进行的讨论只用于检验实施前讨论的交互和粒度，不把四表、金额复制或“不考虑性能”等具体业务选择写成通用工作流规则，不据此自动修改该业务 Spec。

按已汇总输入同步有效spec和质量清单，再通过澄清/方案流程重规划plan/MVU/tasks、契约、验证指南与图示，受影响未完成任务按新范围衔接，旧完成任务不重开。后续实施沿正式方案和任务，不以本提示词存在认定开发或真实挂载完成。共用准备skill的名称/目录、官方hook如何真正停止或放行以及逐Task方案边界，均由后续plan验证，不通过项目级规则或手改官方生成副本来假定成立。

中断恢复先核对有效方案、原Task、真实文件与已确认修复，保留身份、验收、完成事实及历史引用，不因未勾选重复实施。保存失败报告已写/未写、影响与恢复办法，读回修复后再推进依赖步骤，不声称跨文件原子回滚。
