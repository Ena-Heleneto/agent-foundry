## 可直接使用的追加提示词

请在现有工作流基座 Spec 中追加 Increment 的“用户规划描述”能力，沿用已有功能、任务身份及历史证据。Increment 仍负责规划，先形成或修订 MVU，再据此生成或调整 Task；规划过程不自动执行业务实现。

### 一、输入与两条路径

调用形式允许明确 Spec、可选 Task，以及自然语言规划描述，例如：

```text
@specs/dispatch-center/002-cost-accounting-scheduling $speckit-modes-increment
我们先实现用户间的权限逻辑，验收后实现记账服务，然后是日程服务，实现步骤中按照 表设计->service ->接口 ->前端测试页面测试业务逻辑 ->前端页面的形式
```

描述通常是用户对 MVU 和实现路径的初步思路，可以包含业务优先级、推进顺序、验收衔接、实施步骤及局部约束，不要求用户先提供完整设计或按固定模板填写。

- 有描述时，实际读取并理解本次描述，将其作为本轮规划的重要输入，说明哪些顺序、约束和验收衔接来自用户，哪些内容是 AI 据项目补充或建议调整。
- 无描述、仅有 Spec/Task 定位或空白描述时，沿用现有 Increment 流程，依据项目材料推荐闭环和任务，不强制用户补一份思路，不沿用上次描述覆盖本轮意图。
- 两条路径均保留已有材料前置：缺 plan 时说明缺项并返回规划入口，描述本身不代替正式方案；已有 mvu 先读取复用，旧 plan 详情按原兼容规则处理。

### 二、结合已有项目补全思路

读取当前需求、plan、同级 mvu、tasks、相关实现及验证证据，理解已有业务逻辑、可复用能力和实际依赖，再对照用户描述。检查业务角色和边界、前置条件、主要及失败路径、验收信号和必要技术验证是否足以支持目标；只补与本次目标有关的缺口，不机械照抄描述，也不凭空扩展业务。

对有充分项目依据的遗漏，给出补全内容及理由；没有依据的内容明确标为假设或待讨论。遇到影响业务范围、权限边界、验收或关键依赖的歧义，提出具体问题并说明影响，不把猜测变成已确认需求。原规格需要变更时按现有治理同步需求后再落实下游，不仅改 tasks 留下冲突的规格。

尊重用户已明确的方向。若顺序与必要依赖或技术前置冲突，指出具体冲突、理由和最小调整建议；不能无说明地改成 AI 自己的方案，也不能为保持描述字面顺序跳过前置验证。既有明确授权和确认直接复用，不为普通细化反复请求同一许可。

### 三、先按小业务闭环规划 MVU

采用用户已同意的方向：以小的、可观察且可验收的业务结果逐步推进，完成相应验收后再按规划推进下一项。业务模块或服务可以包含多个 MVU，不自动把整个服务当作一个不可拆分的大闭环，也不把“建表”“写 service”等技术层分别当成业务 MVU。

示例中的业务方向是“权限 → 验收 → 记账 → 日程”，应据现有业务和真实依赖细化为小闭环，保留用户给出的验收衔接。示例用于说明行为，不将它固化为所有项目的业务顺序，也不据此直接重排或实施调度中心现有任务。具体采用哪些权限/记账子场景，应从目标项目确认，不能把举例当成新增需求。

每条 MVU 沿用现有状态＋依据和四项短说明：闭环结果、节点与关键逻辑、关联 Task 及职责、验收信号。说明本次划分如何承接用户思路、补齐了哪些必要环节、为何采用当前顺序，以及保留或暂缓哪些内容。用户方向与必要项目约束一起影响最终闭环。

### 四、再把闭环展开为 Task

以已经形成的 MVU 和依赖为依据生成或调整工程任务，不能先照描述拆出一堆技术任务，再反向拼凑闭环。

在每个小闭环内部，参考用户给出的实施步骤链：

```text
表/数据模型设计 → service → 接口 → 前端测试页面验证业务逻辑 → 正式前端页面
```

该链是本次用户提供的规划偏好，不是每个项目或每个 MVU 必须重做的固定五层模板。已有实现及验证证据直接复用；某层不适用时说明原因；必要技术验证和真实依赖决定合理的调整。测试页面用于较早观察业务结果，不能用页面能打开替代业务验收，也不因示例而强制新增测试页面框架或另一套测试系统。

保持“一个业务闭环内逐步打通并取得反馈”的组织方式，避免先做完所有服务的表，再做完所有 service，最后才一次性看到业务效果。既有任务继续复用原 ID、目标、验收及完成证据；细步骤留在原 Task 内，确有新增缺口才使用未占用编号。同步任务正文分组、顺序、依赖和导航，不只增加一份建议列表。

### 五、保存、恢复与结果说明

沿用 spec/plan/mvu/tasks 的职责：需求变更归规格；plan 保留总体方案及 mvu 的文件级引用；mvu 保存闭环详情；tasks 保存工程步骤和唯一完成状态。分别说明用户原思路、结合项目后的补全或调整、最终 MVU 与 Task 的对应关系，以及理由和待确认项，复用原材料位置，不新增一套状态文件。

写入和格式检查成功后，按原规则复用同一综合分析能力；不可用时分别报告规划保存结果与分析未完成。重复调用读取最新已保存材料和本轮描述，无实质变化时保持稳定，不能重复创建相同闭环和任务。原完成事实不因思路修订被抹去，当前规划完成不代表业务、工程或用户验收通过。

### 六、需要覆盖的验收场景

1. 无描述：仍能按原流程处理不同材料路径，不额外要求填写描述。
2. 有描述：用户业务顺序、验收衔接和步骤偏好在最终 MVU/Task 中可追溯；任何必要偏离都有项目依据和说明。
3. 描述不完整：依据现有逻辑补齐必要环节；关键未知单独提出，不擅自扩围或伪造确认。
4. 用户思路与实际依赖冲突：明确冲突与调整建议，保留技术前置及历史证据。
5. 小闭环推进：先形成可验收业务结果，再生成关联 Task；闭环内步骤链可按已有实现复用或按适用性调整。
6. 重复/恢复/已有部分完成：原 ID、完成事实及证据保留，无重复闭环或工程状态；新旧描述有冲突时按当前明确输入处理并保留变更原因。

先将这些要求同步进现有需求与设计，再规划技能修改及必要验证；不要将本提示词保存、状态标注或讨论同意视为技能已实现、已挂载或行为验收通过。
