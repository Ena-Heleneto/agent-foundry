## 已确认的需求

### 删除 Guide

用户明确认为引导式开发没有必要，同意删除 Guide。后续追加提示词应覆盖其 skill、指令注册、自动化挂载及对应验收的移除；历史记录保留，不把历史证据改写为新模式的验收结果。

### 最小闭环与自主协作

用户认为熟悉和不熟悉技术时，最小闭环都适合作为推进依据。熟悉技术并能独立完成时，用户可以自行控制 MVU，使用 Explore 协作，不需要为此调用额外的生成指令。

原 Explore 的目标以原始输入为准：围绕正式任务，按照用户提出的想法、逻辑和思路逐步推进，记录实现思路及其对应的任务状态；不要求按 tasks 的排列顺序实施。最终名称已确认为 Direct，独立子任务体系按后续确认删除。

### 生成 MVU 与 Tutor 分成两个指令

用户明确指出生成 MVU 与 Tutor 的使用时机不同，因此应拆成两个指令。此前提出的合并方案不采用。

生成 MVU 的新指令负责规划最小闭环和实现路径；Tutor 负责进入任务后的导师协作。讨论初期使用 Roadmap 作为候选名，最终已确认为 Increment，见下方命名决定。

原始输入给出的新指令使用场景仍待进一步细化：plan 之后生成或调整 tasks，以及实施中针对指定 Task 补充 MVU 并同步 plan/tasks。

### Tutor 沿用 MVU，再拓展 Task

用户最新确认：“沿用吧，在mvu的基础上再拓展task”。

进入 Tutor 时，已有 MVU 作为基础，Tutor 沿用它并拓展对应 Task，而非因进入导师模式重新生成一套 MVU。Task 的拓展字段、粒度、保存位置与验收边界仍需讨论。

### Tutor 默认用户编写主要代码

用户确认：“默认由自己写主要代码吧，如果需要ai写，我会在对话中说”。

Tutor 默认由用户编写主要代码；需要 AI 编写时，由用户在对话中提出。AI 按该次请求的实际范围实施，局部代写不自动改变后续默认分工。具体讲解、提示与实践反馈方式仍待细化。

### 片段式知识索引与学习报告

用户接受以下建议：每次出现有价值的学习内容时，保存一个简短知识片段，包含遇到的问题、关键解释、关联代码、用户的理解或待巩固点。普通进度对话不强行生成知识点。

Task 结束后，使用这些片段与用户共同整理学习报告。用户已确认归档项目为 personal-hub，沿用现有 apps/personal-hub/content/blog/；具体稿件和文件名在共同写作时确定。知识片段的分类位置与索引组织在本轮提示词中提出拟定方案，尚未实施。

本项确认针对学习内容的片段记录，不替代原始输入另行提出的每次对话记录和协作画像需求。

### 原 Task 内展开细步骤，删除独立子任务体系

用户确认：“是的，把细步骤直接展开在原 Task 内，并删除独立子任务体系”。此决定替代现行章程 VII 中独立子任务体系的后续建设方向，正式治理文件尚待同步修订。

细步骤直接展开在原 Task 内，不再另建独立子任务编号、目录及状态体系。Tutor 在已有 MVU 的基础上拓展对应 Task 的细步骤与学习安排；知识片段单独分类保存，由 Task 引用，不以知识资料另造工程任务身份。

后续必须同步修订章程 VII 与章程提示词，以及两个 Spec 中受影响的规格、计划、任务、契约、验收安排、相关技能与有效入口引用。历史子任务记录保留，取消活动流程对旧体系的依赖；具体历史兼容与未完成记录的衔接方式仍待确定。该决定不表示已执行工程删除，不自动改变既有任务 checkbox 或验收证据。

### 业务闭环与 AI 主动检查技术风险

用户希望把有风险的技术假设与组织实现路径的最小闭环结合，并明确纠正：“闭环成立应该基于业务而不是技术”。用户认可技术风险由 AI 主动检查，并指出这与后续的用户画像需求有关。

MVU 的闭环目标与完成标准以业务结果为依据。技术风险验证服务于业务闭环，不把技术链路联通或局部技术实验通过直接等同于业务闭环完成。AI 主动识别实现业务结果所依赖的技术假设，并检查可用的验证证据，不要求用户先手动标记风险。

现行章程 III 的技术风险验证与本轮业务闭环规划需要按上述关系统一修订；具体触发条目、检查时机、证据要求及发现风险后的任务调整方式仍待细化。此前“闭环里程碑”与 MVU 分成两套独立概念的建议不作为已确认设计。

画像的后续确认见下方范围、影子描述、保存位置和摘要留档决定。读取与执行机制在追加提示词中列为拟定细节；画像不能替代实际技术证据，仍需落实到规划与实施规则中。

### MVU 划分关注合理性

对于 MVU 保存业务闭环目标与验收、Task 保存实现步骤，一个 MVU 关联多个相关 Task、指定 Task 作为规划切入点的建议，用户表示“建议可以”，并进一步提出：“mvu没有标准，仅靠ai判断能合理吗，我觉得合理比准确更重要”。

本轮 MVU 划分以可解释的合理性为重点，不追求唯一正确的划分。用户随后以“符合”认可业务意义、可验收、范围适合推进、顺序有依据四条原则，以及说明理由、在过程中调整的方式。此决定不降低需求事实、依赖关系、技术证据或实际验收结果的准确性要求。
