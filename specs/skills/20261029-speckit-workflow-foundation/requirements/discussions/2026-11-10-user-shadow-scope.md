# 讨论稿：画像需要理解什么

日期：2026-11-10。范围：当前仓库的画像与工作流协作设计。
来源：[原始需求](../raw/2026-11-10-implementation-discussion-revision.md)、本轮实际表达（原仓库私有记录，未迁移）。

## 已明确的目标

用户希望沉淀自己的习惯、思路、思维逻辑等，并明确要求 AI 主动补充画像应理解的范围。目标是让后续协作理解用户如何判断和选择，不能只保存每个 Task 的技术决定或重复用户自述。下面的维度与提炼节奏是 AI 提议，尚未作为全部已确认规则。

## 建议覆盖的维度

| 维度               | 应理解的内容                                                     | 后续如何应用                                   |
| ------------------ | ---------------------------------------------------------------- | ---------------------------------------------- |
| 目标与动机         | 想解决什么，为什么重视，当前更在意哪些结果                       | 解释方案为何符合目标，识别真正的优先级         |
| 判断与取舍         | 怎样比较质量、时间、复杂度、风险和可调整性，什么理由足以接受改变 | 提出符合当前判断标准的建议，解释必要偏离       |
| 思考路径           | 从什么问题开始，怎样拆解、建立关系、判断依赖及验证假设           | 沿用户容易理解的逻辑组织讨论，补齐缺口         |
| 设计与实现习惯     | 怎样划职责、看待复用与抽象、安排数据和业务边界、接受工程细节调整 | 先查现状再提出实现安排，不套用僵硬模板         |
| 推进与反馈节奏     | 希望每次推进多大、何时看到结果、何时讨论或验收                   | 组织合适的步骤和反馈点，减少过早展开           |
| 协作与自主边界     | 用户希望决定什么、AI可以自主决定什么、何时需要提醒或重议         | 调整提问和行动范围，复用仍有效的授权           |
| 沟通与审阅方式     | 需要怎样的解释、术语、例子、图示和细节量才能判断                 | 提供易于审阅的方案，先听用户思路再针对性补充   |
| 知识基础与学习需求 | 已经展示或明确说明的熟悉程度，当前希望深入理解或直接推进的部分   | 调整讲解与介入深度，不从熟悉某一点推断所有能力 |
| 质量与纠错方式     | 如何判断做对、需要什么证据、对哪些失败敏感、纠正后希望怎样续做   | 重视实际验证、保留纠正来源，避免重复已处理问题 |

适用情境、来源、确定程度和变化贯穿上述维度。当前阶段的选择、特定业务的建模和长期倾向需要区分；不要求一次对话填满所有维度，也不把清单变成固定人格标签。

## 用本次互动检验提炼边界

- 用户明确指出预设案例和处理路径会左右其思考，并要求选真实 Task 开放提问。可以据此调整本轮提问方式，不能推断永远不能给建议。
- 用户暂时认可方案明确逻辑、AI查现状后安排普通工程细节、实质变化再讨论，并希望实际使用后调整。应保留“暂时”“试用”的条件。
- T019讨论展示了先澄清模板与记录的关系、再处理服务及汇总的路径。可作为本次思考过程的观察，不足以认定所有任务都必须从数据库开始。
- 本次选择四类数据结构及当前不考虑性能是特定业务/阶段决定，保存在任务方案或讨论中；不能直接变成永久技术偏好。

## 建议的提炼与应用方式

从真实表达、选择、理由、纠正和可核对行为中提炼，区分用户明确表达与带情境的暂时观察；先复用或修订现有结论，避免每轮制造新条目。结论带来源和适用条件，重要变化合入连贯自然语言的当前画像；详细证据留在结论和摘要中。

建议在形成重要讨论结论时检查是否需要提炼，明确纠正及时修订；普通进度不强造结论，未确认观察不写成确定事实。具体触发、保存职责和检查方式继续讨论，不依靠后台监听或额外项目级规则。

后续提问、方案解释、推进节奏和自主行动应能体现相关画像结论。核查时分别看是否有有效结论、是否合入当前理解、实际行为是否应用；文件存在或读过profile本身不能证明理解有效。发生不一致时核对来源和情境，保留纠正，不机械套用画像覆盖当前明确指令。

## 建议怎样检查实际应用

用户要求继续讨论画像如何真正被使用。本节由AI提出；随后用户明确表示尚不清楚最佳方式，先试用。当前按轻量方式在实际协作中观察效果，不代表正式工作流机制已实现或验收通过。

| 检查点               | 应观察到的行为                                             | 本轮可用的例子                                                       |
| -------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| 相关理解是否影响决定 | 重要提问、方案取舍或分工能关联一条适用理解，必要时说明理由 | 用户希望先讲自己思路，AI先给真实Task目标再开放提问                   |
| 行为是否符合情境     | 在相应场景调整解释、节奏或自主范围，并保留必要工程判断     | 逻辑明确、工程细节可调整时，查代码后安排普通写法；影响核心逻辑才重议 |
| 纠正是否在后续生效   | 后续相似场景不重复已指出的错误，新的明确要求能修订旧理解   | 不再用预设实现路径替用户表达，也不把本期不考虑性能推广到所有业务     |

日常不逐轮填写画像应用报告或要求用户打分。重要决策可在原Task方案、讨论或既有协作记录中留下相关理解与实际影响；阶段回顾或用户指出偏差时，抽查真实样本及后续行为。没有适用机会时不能声称通过，也不为验收模拟用户反馈。

出现偏差时先定位链路：真实信息没有提炼、结论没有汇入当前理解、相关内容未读取/未选中、读了但行为没有体现、情境误用，或旧理解已经失效。按实际证据修复对应部分，不能统一归结为需要更多日志或一律重写profile。上述是诊断问题的分类，不新增工程状态服务或计分系统。

任务范围、代码现状、有效授权和已确认方案仍以各自材料为依据，不能把任务续接失败全解释成人物画像问题。画像用于理解和协作，不替代事实核查、必要验证或当前明确指令；技术上确有冲突时说明具体依据，保留独立判断。

用户已同意先试用“重要决定留依据、阶段回顾抽查、重复纠正时回查链路”的节奏，结合实际反馈调整触发频率和记录负担。后续正式机制的接线、职责和验收仍须在方案阶段落实，不依靠后台监听或项目级规则加固。不要要求用户先证明这套方式一定有效，也不能仅因接受试用就判应用效果通过。

本稿补充画像目标，不新建或修改 AGENTS 等项目级规范，不启动 Implement 或暂停模式，不替代 a.md 其余主题的后续讨论。
