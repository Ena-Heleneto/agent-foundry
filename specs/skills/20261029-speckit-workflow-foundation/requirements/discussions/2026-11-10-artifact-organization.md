# 讨论稿：产物职责分类与简洁需求摘要

日期：2026-11-10。来源：[a.md 原始需求](../raw/2026-11-10-implementation-discussion-revision.md)、[现有资料位置契约](../../contracts/artifacts.md)。
状态：用户接受作为第一版基础布局，并明确其他生成文件无法预先穷尽、需要灵活处理；不表示已修订宪章或批量迁移资料。

## 建议的职责分工

| 内容                         | 所属 Spec 内建议位置                                                                          | 主要用途                                                     |
| ---------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 原生需求、方案和任务等主文件 | spec.md、plan.md、tasks.md、research.md、data-model.md、quickstart.md，闭环详情仍为同级mvu.md | 保存各自唯一有效内容，保持原生读取兼容                       |
| 需求材料与简洁导航           | requirements/，沿用raw/、discussions/、prompts/                                               | 分别保存原始输入、讨论及确认过程、整理后的追加提示词         |
| 单Task实施方案               | implementation/<Task ID>.md                                                                   | 开工前确认的实现思路和必要细节，由原Task链接；目录名仍为建议 |
| 逻辑与综合分析               | analysis/spec-analysis/                                                                       | 关键逻辑及变更影响导航、六类分析，引用有效详情               |
| 实际验证证据                 | analysis/acceptance/                                                                          | 保存真实动作、结果和限制，关联原任务                         |
| 图与图导航                   | diagrams/及diagrams.md                                                                        | 图文件按主题维护，导航链接唯一活动图                         |
| 契约、检查单与结案材料       | contracts/、checklists/、descriptions/                                                        | 沿用已有职责，不将工程状态复制进这些文件                     |

只在有内容时创建目录，不为每个需求复制全部空目录。历史文件先核对引用和职责，再按实际修改范围衔接；分类不能触发其他Spec批量搬迁。学习/报告目录保留历史，当前三模式暂停不额外创建相应产物。

## 其他生成文件的灵活归类

上表是基础布局，不是允许生成文件的穷尽清单，也不要求在任务生成时提前列全未来文件。

- 新资料先核对项目已有约定与相邻材料，再根据实际用途放入合适目录；现有分类不足时允许扩充目录并说明职责，不为套分类而产生不合适的位置。
- 文件名称、粒度和拆分按内容及阅读需要决定。沿既有授权开展普通记录或补充时，不仅因文件未在预设表里就反复询问；新增资料仍须与当前需求有关并说明必要性。
- 在相关导航或所属Task/方案中登记必要用途、来源和关联关系，让后续能找到；不另建全局文件注册器或第二套进度。
- 保持有效定义和工程状态的唯一来源，更新引用；不靠复制整份文件维持两个活动版本。历史事实与现有引用按原保护规则衔接，不自动批量搬迁。
- 若新增资料涉及业务范围、验收或已经确认职责的实质变化，按变化本身讨论；不把灵活处理解释为任意扩展需求。

用户画像沿目标项目现有仓库级位置维护，本仓库既有位置是.specify/memory/user-shadow/，不为每个Spec复制画像，也不将该路径硬编码到对外技能。

建议宪章只维护产物职责、建议布局、唯一来源及引用保护原则；具体skill负责在相应阶段读写正确位置。工程代码的目录和写法仍沿项目现有规范，不在AGENTS等项目级规范新增这套工作流规则。

## 建议的简洁需求摘要

以requirements/README.md作为需求导航的候选位置，每次实质变更增加一段简洁记录，关联raw原文、讨论与当前有效需求。原始输入保存时保留原意，整理稿和摘要不能覆盖原文。

建议每段只写：日期和主题、遇到的问题、解决方向、本次改变的范围、当前确认/待定情况以及来源链接。内容以能快速读懂为准，不机械套固定字数或将整轮对话抄入摘要；时间精度以实际可知信息为准。
