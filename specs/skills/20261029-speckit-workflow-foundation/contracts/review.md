# 契约：Review 规划、双确认与博客草稿写入

适用：FR-021～029、033；当前原生入口为 $speckit-modes-review，由 modes 扩展生成；完整真实 A/B 与博客写入演练尚未执行。过程资料归 `<FD>/reviews/<Task ID>/`，正式稿仅写入既有 `apps/personal-hub/content/blog/**/*.md`。Review 不由 Implement 自动触发。

子任务的归属、形式、唯一记录及跨模式续接统一遵循宪章 VII；Review 只消费现有记录，不另立子任务规则或另建拆分 Skill。

## 输入与主题去重

读取 Spec/Plan/Task（已拆分时先读父级整体交付约定）、子任务目录记录、Tutor 各状态会话与学习归档、Pair 实际证据、遗留问题、现有博客目录/标题/内容。Tutor active/paused/completed 均可发起，不能把未完成或未知结论写成已掌握事实。

逐主题比较现有文章，选 `create`、`extend`、`merge` 或 `skip`。merge 表示将新增知识整合进选中的一个既有目标，不自动删除、搬迁其他文章；若确需其他文件操作，另提具体范围确认。优先扩充已有知识体系，不按对话轮次制造文章。

## 确认 A：逐篇规划批准

每篇必须展示 Article ID、主题与前置依赖、动作、精确目标、相关既有文章、完整大纲、证据缺口与未解决问题。A 在逐篇 Markdown 规划中记录已展示内容与用户真实批准出处。

支持批量批准、单篇调整、重新规划和暂缓；仅获 A 的文章进入正式成稿。目标、动作或大纲发生实质改变后重新展示并确认 A；由此使 B 失效。未获批准时最多保存 Spec 内规划，不写正式博客。

## 成稿与证据检查

每篇按主题及学习依赖组织：学习前提、问题、目标、是什么/为什么/如何工作、适用时机、限制、独立最小示例、运行验证方法、引用与后续方向。私有代码仅作补充，示例不依赖本仓库私有模块。

优先官方文档、源码、标准、SDK/驱动与制造商资料；来源记录 URL/本地源码位置、版本、条件及支持的具体结论。社区资料补充时注明性质；网络不可用不编造来源。示例区分实际已运行与未运行，不把 AI 示例当用户执行。嵌入式主题另覆盖资源所有权、内存生命周期、并发、硬件条件、错误处理与性能影响。

核心结论缺证时该篇转 blocked，列出缺项与验证建议；即使用户一般性同意也不能以无证据稿绕过规则。非核心疑点可清楚标注后进入 B。其他文章独立继续。

## 确认 B：最终字节与目标差异批准

在 Spec 过程区准备草稿，先对该 Markdown 执行章程要求的 ESLint；随后必须按**最终博客目标路径**的实际配置，在内存中产生可批准的最终字节，不能仅凭 Spec 路径格式化结果假定目标路径相同。使用已有 ESLint 的只读预计算接口，示例命令如下，正文经 stdin 传入，参数以数组调用，不经 shell 拼接：

```bash
pnpm exec eslint --stdin --stdin-filename apps/personal-hub/content/blog/<slug>.md --fix-dry-run --format json
```

解析结果中的最终 output（无 output 时取原输入），再以同一目标路径预计算一次；仍会变化、仍有 lint 错误、目标被忽略或配置无法解析时，阻断该篇进入 B。将固定点字节保存在 Spec 草稿中；对草稿文件的章程格式检查也必须不再改变这些字节，若两路径规则无法得到共同固定点则报告配置冲突，在写正式文章前解决，不自动放宽规则。

同时在该篇 Markdown 审核记录中保存实际目标路径、相关 ESLint 配置及工具版本，必要时记录内容 hash 方便核对；这些是批准依据的证据，不是固定 JSON DTO 或新的状态系统。随后向用户展示：

- Article ID、最终目标路径、动作及已获 A 的规划。
- 完整正文、最终引用与待验证项、运行/未运行状态。
- 修改摘要；更新已有文章时展示完整相关 diff，保留无关内容和元信息。
- 目标当前原文 baseline_hash（新建为 null）、最终稿 draft_hash。
- 最终目标的格式上下文及核对依据；配置或工具版本变化会使本次 B 失效。
- 元信息最终 `status: draft`；已有 published 必须展示 `published → draft` 与正文差异，说明获批后原文件成为草稿。

B 绑定上述完整批准对象，支持批量、逐篇调整及部分通过。未批准文章不能写正式内容；正文、引用、目标文件/基线、格式上下文或最终字节变化后，至少重取对应 B；大纲/动作/目标变化还重取 A。内容 hash 只辅助核对一致性，批准本身仍必须来自真实用户指令。

## agent 直接逐篇核对和写入

不使用 workflow-task-context、article.py、state.json、锁、事务或回执系统。每篇的规划、A/B 指令出处、已展示正文/差异及实际写入结果保存在 reviews/<Task ID>/ 对应 Markdown，子任务状态仍只在原目录 README。

1. 核对 A/B、核心证据、精确目标、已批准 draft 字节及格式固定点；目标必须是当前仓库 apps/personal-hub/content/blog/ 下的 .md，拒绝路径逃逸、软链接越界及未经批准的目标更换。
2. 读回目标原文、配置/工具版本并与 B 展示依据比对；任何可检测差异在正式写入前暂停，重新展示并取得对应批准，不先改文件再补批准。
3. 只向获批目标写入，新稿已有同名文件时停止核对；已有文章保留无关正文/frontmatter，published→draft 必须已在 B 明确展示。新稿元信息满足既有 schema（title/description/date/tags/status），不改博客配置迎合样例。
4. 写后执行章程 Markdown ESLint 并读回，最终字节应仍为批准的固定点；异常变化保留现场，报告实际差异，不追认成功或事后补批准。
5. 将实际命令/退出码/结果和目标 hash 记录到该篇 Markdown；一篇失败只阻断该篇，不回滚其他成功篇。

## 中断、失败与重复请求

写入或结果记录失败时停止该篇后续动作，报告哪些文件已变和哪些未保存。恢复先读目标：等于批准稿则只补实际结果记录，不重复写；等于原基线或新稿仍不存在则复核批准仍有效再重试；其他内容则保留实际文件、报告冲突并重新审核。部分写入不能因“文件存在”就判成功，不自动删除或回滚用户修改。归档不覆盖，重复请求先核对已有条目，不创建重复文章或批准。

不承诺跨文件原子性或并发强隔离；执行期间发现同一路径/格式配置有并发改动即停止协调。MVU-D 需覆盖目标规则不同、B 后配置/工具或目标变化、格式非幂等、忽略目标与写入/保存故障，并保留真实 A/B 和实际博客可见性证据。

## 博客集成边界

实际集合与版本见 research R7。列表与详情分别验收：开发下可预览 draft，非开发默认环境列表不含 draft 且详情 404；额外验证 `NUXT_PUBLIC_IS_DEV` 字符串覆盖的既有风险，不能用列表结果代替详情结论。实际固定 Worker/D1，本地运行不可用则记录原因，D 不通过。

本功能不运行发布/部署/远端数据库操作。文章写为 draft 不代表已发布站点已撤回旧版本；实际部署与发布仍由用户决定，不作无运行证据的线上状态承诺。
