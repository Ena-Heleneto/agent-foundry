## 概要

以可验收的业务结果组织 MVU，在其内部先验证必要技术假设，再增量实现。新增 Increment 负责计划与任务路径；Tutor 沿用闭环并在指定 Task 内指导用户实践；Explore 改名并重写为 Direct，用户决定当前实现方向；Pair 保留。最终统一挂载 Tutor、Pair、Direct、Increment 四项，删除 Review、Guide 及六项旧产物/门禁技能的有效来源和挂载。

工程进度只在原 Task 内维护，保留整体交付约定与八栏目，细步骤内联，不创建独立子任务身份。画像仅服务本仓库；综合分析复用一个技能，在 after_tasks 及 Increment 更新后生成/刷新。技能读取目标项目治理，不把 Foundry 个人资料与路径作为外部运行约定。

本计划替代旧 Explore/Guide、五模式、七 hooks 与独立子任务的活动设计。旧实测、旧 Task ID、根目录图和描述快照保留；当前 tasks.md 有效任务为 T049～T082，旧 48 项归档并标替代。此前阶段安排与已完成事实继续保留，后续按 tasks 当前证据续接，不能从旧 T042/T044/T045 或分发 T006 的失效做法继续实施。

本次追加“需求结束后的开发过程产物清理”：治理统一要求生成/更新任务清单时安排末尾清理，当前实际收尾复用 T080。对象包括文件及文件内代码段、文档、注释、失效代码等；用途不明的内容保留并记录位置、原因和后续处理条件。其余清理、必要验证和引用检查通过可完成清理部分，整体结案继续满足原条件。方案取舍见 [R32～R34](research.md#r32清理规则由项目治理维护)，不新增自动清理服务或状态体系。

## MVU 判定

本节沿用现行 before_plan 的 mvu-gate 扫描，TV 表示计划中的技术前置验证，不是新 Task/子任务身份。TV 的实际执行状态只在后续 tasks 和证据中维护。

| 条件                      | 本轮事实                                                                                   | 结论                               |
| ------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------- |
| C1 无先例新依赖/框架/协议 | 沿用 Markdown、官方 CLI、现有 Node/shell 与工具，不引入新依赖                              | 未命中；版本仍实际核验             |
| C2 外部系统失败模式未验   | 官方 CLI 与 agent 集成的五变四、卸载旧 hooks 和部分失败组合未实测                          | TV-01 命中，旧五项重装结果不能豁免 |
| C3 未验证假设/高风险决策  | 多文件规划保留、未知附件保护、双入口分析刷新，以及局部清理用途判断和完成边界存在新行为假设 | TV-01/02/03/04 命中                |
| C4 首次跨包/进程契约      | 新四模式及分析附件经 CLI 消费、分发核验采用新集合                                          | TV-01/03 命中                      |

仅在三项同时满足时豁免：已有适用的同类验证、无新依赖和外部交互、失败可由已有检查/测试兜底。纯正文格式、既有本地画像分类及报告 schema 读取可复用既有 Markdown/ESLint 与实际 schema，三项均满足，不另造技术实验；真实学习、画像纠正和草稿行为仍须验收。官方迁移、规划更新、双触发刷新不满足这三项，不豁免。

本次清理增量对 C1/C2/C4 均未命中：只消费项目本地治理和记录，无新增依赖、外部交互或跨进程契约。C3 命中误删及局部完成被误当结案的假设；T051/T052 只支持保存、原身份与引用保护方法复用，未覆盖清理用途判断，且 lint/类型检查不能证明资料仍有无保留用途，因此三项豁免并不同时满足。实际清理若发现新依赖或外部影响须重新判定，不扩大此结论。
