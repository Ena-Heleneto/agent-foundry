# PR 描述：Spec Kit 工作流基座优化

由 `artifact-pr-description` 在 clarify 阶段根据 [spec.md](spec.md) 生成的分析后需求文档。本文件描述拟交付范围和澄清结论，不表示功能已实现；后续阶段不自动更新。

## 变更概述与解决的问题

本次优化让开发者能围绕同一个正式任务，选择导师引导、结对编程或原生自动实施，并在切换和中断后继续已有进度。各模式共用子任务，但学习掌握、编码操作、文章审核和正式工程验收分别管理，避免重复拆解和错误宣告完成。

辅助资料将按用途归档在所属规格目录中，保持原生规格文件和工作方式兼容。旧的实施随行说明机制改由用户主动进入 Tutor 学习、再用 Review 整理成独立技术笔记；现有技术可行性验证门禁和实施断点续跑完整保留。

## 澄清后的重点变化与交付要点

- 子任务按事先约定的验收条件判定完成，切换模式不改变标准。编码子任务达到代码验收可以完成并推进；学习目标仍需验证掌握，尚未掌握的学习记录独立保留，不因代码写完而自动通过。子任务完成也不会自动标记父任务完成。
- Tutor 与 Pair 保存进度失败时，暂停进入新步骤及更新完成状态，先报告、排查并重试，保存成功后继续。每轮状态、独立单元归档和恢复摘要须能支持中断恢复，重复操作不生成重复记录或覆盖历史。
- Review 更新已有 `published` 文章时，在第二次人工确认中同时展示正文差异和转为 `draft` 的状态变化。批准后直接更新原文件并设为草稿，不另建修订副本，之后由用户自行发布。
- Tutor 负责评估基础、解释原理、安排练习和验证理解；用户主导核心学习代码，AI 默认不代写。每个正式任务持续维护一个可暂停、恢复、结束及重新开启的会话，全部单元通过也由用户决定是否退出。
- Pair 负责讨论当前编码步骤、审查、调试和验证；默认不修改业务代码，只有指定文件或片段的明确授权才允许局部编辑。局部授权不代表自动实现、重构、提交或推送许可。
- Review 先检查已有文章并按主题规划，允许新建、扩充、合并或不写；先确认规划，再审核完整草稿，两个检查点均支持批量、单篇调整及部分通过。核心证据不足的文章单独阻断，其他获批文章可以继续。
- 分级验收按需求复杂度选用单项、完整流程或跨模式集成验证，不强制每项需求都具备全部层级。子任务具有唯一父任务归属，各模式共享实例和进度，知识资料可以引用复用。
- 只移除旧随行说明 Skill、有效挂载及其在 Implement 前后的对应条目，并同步相关活动规则和旧需求引用。历史文档和已有引用保留，发现失效引用先报告并提出非破坏性处理方案。

## 验证方法与操作途径

1. 对两个父任务检查子任务唯一归属；在同一父任务下完成学习、结对、自动实施和返回学习的切换，确认不重复拆分、不丢进度、不改变验收标准。包含代码通过而学习未通过的案例。
2. 演练 Tutor 首次启动、讲解但未掌握、练习纠错、逐轮保存、单元归档、暂停恢复、结束及重新开启；确认 AI 示例不记为用户执行，旧归档不覆盖。
3. 演练 Pair 默认只读、局部授权、反复修改审查、构建测试及中断交接，确认没有越界编辑或自动完成正式任务。
4. 对 Tutor 和 Pair 分别制造保存失败并重复调用，确认成功保存前没有进入新步骤或更新完成状态，恢复后不重复记录。
5. 使用已有同主题文章和核心证据不足的候选稿演练 Review 去重、两次确认、批量与单篇调整及部分通过，确认未批准或证据不足内容不能写入。
6. 验证新文章及已有文章更新，包含一篇原为 `published` 的文章；先展示正文与状态差异，批准后原地保存为 `draft`，无关内容保留，自动发布次数为零。
7. 对照替换前的行为验证原生实施、技术可行性门禁阻塞、通过、失败回退及中断恢复；确认旧 Skill 无有效残留调用，历史资料完整保留，Implement 不再自动生成随行说明或追加引用。

以上是后续实施的验收要求。本阶段只完成需求澄清与文档质量检查，未执行这些功能行为验收。

## 潜在影响与注意事项

Skill 接入方式须依据已安装 Spec Kit 和仓库实际机制设计；子任务标识、分类目录、状态转换、同步与幂等方案、验收里程碑信号留给 Plan，不预设接口或额外框架。

当前挂载复制脚本不会自动清理源目录中已删除的技能副本，因此删除源 Skill 后仍需核查有效挂载及指令配置。不得因清理旧机制误删 `mvu-gate` 或改动原生 Implement 的执行与验收行为。

博客复用现有 Markdown 草稿方式，列表与详情页的草稿可见性需要分别核实。已有文章由 `published` 转为 `draft` 会改变其可见状态，必须在写入确认中明确展示；Review 不自动发布，不新增发布系统，也不擅自重构博客。

章程优化须遵守既有修订程序；不删除或迁移历史随行资料，不将业务代码、测试或正式文章搬入规格目录。仓库已有未提交改动保持原状。
