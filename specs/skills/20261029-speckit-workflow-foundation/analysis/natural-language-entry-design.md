# 四模式正式入口的自然语言发现设计

日期：2026-11-10。来源：本轮用户讨论。**状态：入口路线已由用户选择；本文为后续规格和任务调整的设计依据，尚未实施。**

## 目标与范围

用户通过自然语言或显式指令选择协作模式，两种方式均加载对应的 Spec Kit 正式入口，使用同一行为、任务定位和保存规则。当前工作流工具支持暂限 Spec Kit，暂不维护其他任务工具的等价材料兼容路径。此范围不限制工程工具，也不改变独立 coding 技能的通用性。

## 方案取舍

已讨论两种路线：四个正式入口分别描述适用场景，由宿主直接发现；新增统一工作流技能，先识别请求再分派模式。用户明确选择“方式一”。因此沿用四个入口，不新增统一分派技能、第五模式或模式选择状态服务。

## 入口与来源

| 正式入口                | 自然语言意图示例                     |
| ----------------------- | ------------------------------------ |
| speckit-modes-pair      | 我们结对做这个任务                   |
| speckit-modes-tutor     | 指导我完成这个任务，主要代码我自己写 |
| speckit-modes-direct    | 这个任务按我的思路推进               |
| speckit-modes-increment | 基于已有方案补齐闭环和后续实施计划   |

四个正式入口的 description 表达各自适用意图，由宿主选择并读取完整技能；不将自然语言发现描述为确定性的关键词命令解析。显式调用同一入口时不经过额外路由。

`packages/skills/src/skills/workflow/task-*` 继续作为唯一维护来源，经构建和官方挂载生成正式入口。目标消费环境只公开生成入口参与模式发现，原始 `task-*` 不再作为并行的公开调用入口；不删除生产来源，也不手改生成副本。原始来源的安装位置、发现可见性和附件引用须在后续技术验证中确定，不预设某个字段能跨宿主关闭发现。

## 上下文与行为

进入模式后先核对目标项目及工作流治理。优先采用用户明确指定的 Spec 和 Task，其次使用已唯一定位的上下文或项目指针；指针失效时按现有规则检索，只有唯一匹配才续接，有歧义只补问必要定位信息。Task 始终关联所属 Spec，切换模式不重建任务或复制工程状态。

保留各模式原有前置与分工：Increment 只推进规划，按有 plan 无 tasks 等已有分支处理；Direct、Tutor、Pair 不因自然语言进入而绕过必要材料、技术前置或操作授权。明确的模式选择可以直接进入，无须再要求用户输入正式指令；普通讨论或意图不清时保持当前分工，需要改变分工才澄清。

项目未初始化 Spec Kit 时，说明不在当前工作流支持范围，不回退到其他任务工具，也不自动初始化。必要入口缺失或已知过期时，报告缺项及官方挂载修复路径，不通过加载原始 task-* 冒充正式入口调用；是否执行修复沿当前授权处理。来源、构建及生成入口同版由交付验证保证，不要求每轮会话全量重装。

hooks 继续按既定生命周期执行，保留各技能已有的明确请求和内部复用职责，不因本次模式发现增加 hooks 或泛化触发条件。business-node-delivery 仍独立自然发现，不加入模式链接或安装依赖。

## 后续同步与验收

先按本设计增量同步现有 spec、契约和方案，再在原 tasks 中安排有依赖的验证及实施；保留已完成 ID、结果和历史证据，不把设计选择算作任务或阶段验收通过。

验收分别覆盖：四个正式入口的自然语言选择与完整读取；显式和自然语言的相同行为；唯一定位、歧义及材料缺失；模式保持和明确切换；未安装及已知过期入口；生产来源、构建、安装正文与附件同版；目标环境没有重复的原始模式发现入口。真实宿主发现与只读描述识别分别报告。

T093 原本验证通用业务规则在四模式上下文的发现及加载后职责，不能直接抵扣本次模式入口发现的新范围。当前安装的 Pair 入口仍含旧子任务正文，作为后续刷新与验收对象，不能用 T065 源码工程通过推定正式入口已更新。具体任务安排及适用工程检查在计划阶段确定。
