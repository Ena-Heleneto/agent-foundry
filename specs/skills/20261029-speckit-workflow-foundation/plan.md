## 2026-11-18 profile 集合拆分方案

**输入与范围**　承接[三项澄清](spec.md#session-2026-11-18)，完成独立落盘、摘要、分析与影子画像的 Phase 0 和 Phase 1。实际 Git 分支为 `feature/init`，Spec Kit 解析的功能标识为 `20261029-speckit-workflow-foundation`。工作流基座其他能力沿各自有效范围推进。

### 概要

主 AI 每轮加载对话落盘 Skill，保存并读回可见原文。成功确认的新增范围交由子代理实际运行对话摘要 Skill。命中已确认条件时，对话分析独立使用该原文，摘要进行或失败时也能启动。主 AI 核实分析子代理已保存并读回足以改变画像的结论后，自动调用影子画像 Skill。正在更新时继续使用最近有效入口。对话落盘可单独使用，首次画像入口由画像 Skill 按实际理解和覆盖建立。

### 推进顺序与依赖

先用同一最小候选验证落盘独立使用、真实三轮调用和摘要子代理。再验证分析可独立启动和有效结论自动交接，完善分析、入口及有限重试。共享提交的前置验证通过后覆盖两会话合并、迟到结果及遗忘恢复，最后从四个最终维护源精确复制复验。独立本人应用沿真实机会核对，并进入原结案条件。闭环详情见 [mvu.md](mvu.md)。

共享提交验证以前，候选及各 Skill 的用例使用隔离资料根，每个目标文件仅一个写入者；摘要和分析可在途重叠，但分别保存不同文件，主 AI 不竞争改写子代理输出。此阶段不运行需要多个写入者争用同一文件的用例。共享提交前置及两会话/同文件场景统一在原共享验证任务汇合，不反向作为摘要独立验收的完成条件。

暂停/恢复由对话落盘 Skill 保存项目内最小控制依据，位置及恢复顺序见[资料模型](data-model.md#暂停与恢复依据)。控制依据独立于可清理的对话资料根，重新复制 Skill 不覆盖它；这是本次对既有暂停要求的设计补齐，不新增项目代理路由或管理服务。

整根移走、删除或重建与摘要/分析在途的组合纳入共享提交验证。新代次不能单独证明旧写入者已失效：必须验证根与锁身份变化时，旧工作仍无法提交到新根，或确认所有旧写入者已终止后再开放新根共享写入。具体操作沿原 Task 开工方案形成并验证；组合失败时只暂缓受影响共享/重建能力，不能以新锁获取成功代替旧工作已拒收。原文独立记录、普通清理和明确遗忘的边界保持。

宿主无法自然匹配、实际派发、继续协作或自动交接时，保留能够确认的步骤与缺口。共享提交失败时保留有效文件和未合入来源，暂缓受影响的并发或遗忘验收。旧日志实验与单技能演练按各自发生时的范围使用。任务阶段已沿当前设计对齐职责与路径；后续仍按原任务的适用认可、实际前置及授权进入实施，Phase 1 设计保存不代表能力通过。

## 共同准备与逐 Task 开工

原生 Implement 对损坏 extensions.yml 会报告后继续，非空 condition 跳过直接调用，单次前置后遍历 Task；因此 hook 本身不能充当程序级锁。原生在实施前会读取存在的宪章，故首选由宪章定义每个 Task 的共同条件：完整消费同一准备能力，实际核对该 Task 的认可方案、必要前置和有效授权，失败只允许读取、诊断、讨论或修复，不允许受影响业务实施。

hook 使用无非空 condition、optional:false 的 before_implement，负责尽早进入准备。缺失、禁用、跳过、解析或调用失败不豁免共同条件。准备 skill 缺失、过期或无法加载时明确报告并停止；没有有效宪章或宿主未消费时不能宣称原生已经拦截。该机制是 agent 执行契约，其行为必须经 TV-10 证伪验证，不能承诺所有普通聊天自动被 hook 控制。

先唯一定位项目/Spec/原 Task，再读需求、plan、同级闭环、原任务、相关代码及项目规范、既有方案和证据。有适用的真实认可方案则复用；无方案先听用户方向，必要时 AI 根据实际项目提出建议，经真实讨论认可并成功保存后继续。存在文件或 AI 自称确认均不等于有效认可。进入下一 Task 或并行安排前逐项核对；一次认可只覆盖其真实讨论范围。

方案表达做成什么、核心逻辑和数据关系、理由、顺序、验收、讨论来源及必要工程依据；这些是内容责任，不是固定字段模板。工程路径、命名和内部写法可在已确认逻辑内合理调整并记录；逻辑、职责、范围或验收的实质变化只停止受影响部分并重议。恢复先对照最终保留代码、真实确认和撤回方案，避免按未勾选状态重复修复。保存失败报告已写/未写及恢复入口，成功格式检查和读回前不推进依赖动作。

不采用官方 preset/command override 作为本期既定实现。该能力可在 TV-10 失败后形成最小调整提案交用户审查；不提前增加 commands 模板、安装通道或手改生成入口。

## 自然语言请求与变更影响判断

2026-11-12，用户[确认补入此边界](requirements/raw/2026-11-12-spec-revision-planning-boundary.md)：“调整一下需求”是自然语言示例，不是固定口令，也不等于必须修改MVU。先定位所属项目、原Spec和请求内容，再判断需要处理的层次；不凭单个词机械选择技能，不新增统一分派入口、命令或项目级指令路由。

| 请求内容                           | 处理顺序与写入边界                                                                                         |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 修订需求、业务规则或验收定义       | 按已确认的变更修订原spec.md，核对对总体方案、闭环、依赖和任务的影响；仅同步受影响部分，不另建同目标Spec。  |
| 调整业务闭环、拆分、依赖或执行顺序 | 属于实施规划调整时才按Increment推进；沿已有plan/MVU/tasks增量更新，没有需求定义变化就不顺带改Spec。        |
| 实施或继续原任务                   | 沿共同实施准备核对原Task及适用认可方案，条件满足才实施；实施中遇实质需求变化，先停受影响部分回到需求讨论。 |

影响核查可以读取下游材料，但不要求全部重写。仅影响Spec的修订就保持plan、mvu、tasks不变；只影响某Task的验收或实现安排而不改变业务闭环时，按实际影响同步该Task或实施方案，MVU保持。需求与规划都变化时，先修订获确认的需求，再衔接所需规划，不只改MVU而漏掉Spec，也不因用户只说“调整需求”自动改代码。

没有plan或MVU时，单独修订已存在的Spec不因Increment的规划前置缺失而被拒绝；不为改Spec而自动补建规划材料或初始化新功能。内容或定位仍不清楚时，只补必要澄清；明确且适用的用户决定直接复用。实质变更按既有规则保留原文和简洁摘要，普通措辞修正不冒充新的业务需求。

T099在原自然语言发现/定位/行为职责内，分别核对Spec修订、纯规划、两者同时变化及含糊请求。检查实际处理位置、技能读取/调用、受影响与不应变化材料的差异；只修Spec却强制调用Increment/重写MVU、无plan就拒绝Spec修订、未经请求进入代码、混合变更漏同步，均不能计正确处理。相关技能已按原T104/T096补充来源规则，见[来源证据](analysis/acceptance/request-boundary-source.md)；独立只读场景判断不等于实际宿主/文件行为通过。正式安装、自然发现和用户效果仍需按原Task核对，不以方案认可或源文件保存自动记工程完成。

## Increment、记录与分析

Increment 输入为目标 Spec 和可选规划描述，不接收 Task 定位参数。无 plan 停止规划写入；有 plan 无 tasks 时先形成小 MVU 再生成轻量任务；已有 tasks 时核对实现与证据、按职责关联，不以原 Task 作为规划入口粒度。已有成果复用，先业务结果再 Task，任务正文顺序及真实依赖同步；稳定 ID、完成事实与历史引用保护。

画像主要作为理解顺序与协作的参考，不替代项目事实或验证，也不为每次规划强造偏好。实施讨论提供新的有效认识时，按目标项目既有约定区分摘要、结论、当前理解与实际应用；以真实后续机会轻量抽查，不逐轮报告或评分，不将单 Task 建模写成永久特征。个人路径与资料不进入对外技能。

需求实质变更保留原始输入、简洁分段摘要和讨论来源，默认复用 requirements/raw、discussions、prompts 与 requirements/README.md。资料按职责灵活归类，新文件不要求注册或预先穷尽；范围/验收改变才讨论，不批量迁移其他 Spec。

artifact-spec-analysis 仍用 after_tasks 与 Increment 显式调用同一来源，在 analysis/spec-analysis/README.md 及必要分文档增加一功能点一块的简洁完整说明，必要逻辑自然融入，不强制固定栏目或总表。保留原六类分析的适用职责，标明缺项、暂停和未验，不维护第二份活动定义或工程状态。business-node-delivery 保持独立 coding 发现，不向准备或 Increment 添加其链接、显式调用、hook 或安装依赖。

分析技能的当前维护位置按既有集合迁移为 packages/skills/src/workflow/artifact-spec-analysis/，after_tasks 唯一声明位于同集合 collection.config.json，不再维护逐技能配置。下文 register-hooks 的逐技能读取仍是旧脚本事实；完整接线需后续注册任务适配集合声明，本轮正式来源隔离登记不抵扣该职责。
