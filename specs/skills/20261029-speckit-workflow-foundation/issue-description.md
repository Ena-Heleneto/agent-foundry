# Issue 描述：Spec Kit 工作流基座优化

由 `artifact-issue-description` 在 specify 阶段根据 [spec.md](spec.md) 生成，作为需求提出时的原始意图快照；后续阶段不自动更新。

## 背景与痛点

当前工作流可以定义需求、规划任务并执行，但“带着学”“一起写”“事后整理知识”还缺少明确的协作边界和可恢复记录。学习与编码如果各拆一套步骤，切换模式容易重复劳动；把讲解或子步骤完成当成工程验收，也容易造成错误的完成判断。

原先实施过程中自动生成随行说明的方式，需要改为由用户主动选择学习和复盘。替换时必须保住现有实施流程、技术可行性验证门禁和历史资料。博客已经有内容目录、文章元信息和草稿流程，应直接复用。

## 核心要做的事情

1. 先调查已安装的 Spec Kit、仓库章程、现有挂载和博客实际机制，再在澄清与计划阶段确定具体设计，不先假定存在某种扩展接口。
2. 按需求复杂度设置小、中、大验收里程碑，不强制每个需求走完所有层级。建立所有模式共用的子任务，每个子任务只属于一个正式任务，切换模式继续当前进度；重拆未完成步骤或改变正式任务需要先确认。
3. 将工作流的辅助资料按用途归档在所属规格目录下，让任务、图示、学习和复盘材料可追溯。原生规格文件继续按原方式工作，业务代码、测试和博客文章保留原有位置。
4. 增加导师模式 Tutor：先了解用户基础，再解释、安排练习、审查和验证。用户主导核心练习代码，AI 默认不代写；每轮保存可恢复状态，按学习单元独立归档，支持暂停、恢复、结束和重新开启。讲解过、看过 AI 示例都不等于用户已掌握。
5. 增加结对模式 Pair：用户决定设计并编写主要代码，AI 聚焦当前一步提供讨论、审查、调试和验证。默认不改业务代码，只有获得指定文件或片段的明确授权才编辑，并保存交接进度；授权不扩展为自动实现或提交推送许可。
6. 增加复盘模式 Review：用户主动发起，先检查已有文章并规划新建、扩充、合并或不写。用户先确认规划，再审核完整草稿和已有文章差异；两次确认都支持批量、单篇修改及部分通过。文章围绕可迁移知识组织，解释原理、前提、限制与验证方法，并给出可追溯资料。
7. 对核心证据不足的文章单独阻断写入，其他文章可继续；未核实结论和未完成学习记录明确标注。获批内容进入博客现有草稿流程，复盘过程材料留在所属规格中。
8. 移除旧随行说明 Skill 及其在 Implement 前后的两处挂载，检查有效副本、指令和配置中的残留调用，同步旧需求引用。保留旧文档与已有引用，失效链接报告后提出非破坏性处理办法。

## 预期达成的效果

同一正式任务可以在导师、结对和原生自动实施之间切换，继续原子任务及已有进度。学习会话、编码操作、文章审核和工程验收各自管理，不因任何子步骤完成而自动宣告正式任务完成。

学习记录能在中断后恢复，重复保存不会增加重复内容，归档不覆盖历史，失败明确报告。结对编辑严格遵守局部授权；复盘先去重、后研究，未经批准或核心证据不足的文章不会进入正式内容区，也不会自动发布。

验收需要实际演练首次启动、逐轮保存、暂停恢复、跨模式切换、局部授权、双重确认、部分批准、失败重试和文章草稿更新。旧机制清理后，现有实施、技术可行性门禁及断点续跑结果保持一致，历史资料完整保留；不能只证明技能可以触发。

## 明确不做的事情

- 不另写 Auto，不替换原生 `/speckit.implement`，不删除或修改 `mvu-gate` 及其挂载、门禁和断点续跑逻辑。
- 不让 Tutor 默认代写核心学习代码，不让 Pair 未授权修改业务代码、一次性实现整个任务或自行提交推送。
- 不因切换模式、创建或完成子任务而自动改写正式任务的范围、验收标准或完成状态。
- 不机械地把每轮对话写成一篇文章，不编造资料、实验结果或硬件参数，也不强制每次复盘新增文章。
- 不另建博客发布系统或独立修订草稿系统，不擅自重构博客，不自动发布文章。
- 不删除或迁移历史随行说明，不将业务代码、测试或正式博客文章集中迁入规格目录。
- 本次需求定义不直接实施功能；具体标识、目录、状态与接入方式在后续阶段确定。
