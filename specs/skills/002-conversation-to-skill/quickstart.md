## 记录验收

### 接入前置

T035 先在隔离环境核对三个接入前置，记录所测宿主版本、候选来源、实际证据和结果。已有临时 Hook 探针覆盖原生信任、首末轮保存和非交互对照。依赖完整记录的正式交付在前置通过后推进。 [可重跑探针及结果](analysis/recording-acceptance.md#t035-原生首次启用与首末轮联动) · [技术前置](research.md#2026-11-25-自动记录的技术前置)

1. **首次启用。** 沿候选的项目级入口安装实际文件。若需要信任，在隔离仓库根运行不带消息的 `codex`，由用户通过 Codex 确认项目及对应 Hook。退出空白引导会话，从新打开的 `/hooks` 或适用的 `hooks/list` 独立读回实际项目来源、当前定义、启用和受信状态。引导期间主记录和详情均为零。安装完成后从同一隔离状态新开普通 `codex` 会话，直接发「读一下 README」，核对这条原话在读取 README 前保存并读回。
2. **回调时的范围。** 在交互首轮与后续轮次进入回调时验证当前轮次和归属证据。保持项目和 Hook 可信，在隔离仓库执行下面两个非交互命令，将会话 ID 替换为已建档的合成交互会话。核对业务正常完成、回调及范围判断的实际结果、记录文件清单与内容以及记录器的正文读取活动。期望零新增、零续写、零额外正文补读。
3. **最终回复结束后保存。** 使用原生交互终端和分段合成回包，连续两轮均零模型工具调用。关联同一会话和轮次的宿主最终回复发送结束事件、项目文件写入完成及重新打开文件逐字读回的时点。通过顺序为发送结束、自动保存全文、实际读回，读回文本须与宿主实发全文逐字一致。每轮仅保留一份该回复，无需追加用户消息触发保存。缺少结束事件、全文比对或实际读回时记为证据不足。 [时序依据](research.md#正常最终回复结束后的保存与读回)

```bash
codex exec '请只回复 T035-EXEC'
codex exec resume '<已建档的合成交互会话 ID>' '请只回复 T035-EXEC-RESUME'
```

### 正式来源复验

前置通过后，从实际交付来源按下节刷新隔离安装并做完整验收。若采用 Hook，先用候选通过完整记录验收，再移除其接替的旧记录逻辑。重新安装移除后的最终版本，复验实际加载来源、以下首期场景及每个合格轮次恰好一个对话组。证据归入原 T035 验收资料。 [最终来源验收](#流程-skill-最终来源消费)

在维护仓库构建主线产物。构建将记录 Skill 连同三个 Python 入口原样复制到 `dist`。运行产物中的 `install.py`，才在目标 Git 工作树登记 `.codex/hooks.json`。确认原生信任后再发首条用户消息。 [构建与入口映射](implementation/T035.md#独立-hook-入口与交付)

```bash
pnpm --filter @foundry/skills build
python3 -B packages/skills/dist/skill/profile/conversation-recording/scripts/install.py --project '<隔离 Git 工作树根>'
python3 -B packages/skills/tests/conversation-workflow/helpers/recording-hook-probe.py --extended
```

`--extended` 使用真实 Codex CLI、回环合成回包和独立会话状态运行下列过程用例。真实模型的普通问答和对完整安装资料的读取另行取证。

1. 在两个终端进入目标仓库内不同项目目录运行 `codex`，各发送首条和至少一条后续消息。输入前各自零主记录和详情。首条后各建一份主记录，用真实模型的普通问答覆盖首轮与后续轮次各一个未选用记录 Skill 且零模型工具调用的样例。核对每轮用户原话与正常回复均当轮保存并读回，无实际详情的普通问答只写主记录。另测跨午夜才发首条，按实际开启日归档。
2. 输入带附件的任务，调用具有额外选项的工具，覆盖短输出、长输出、流式输出和工具附件。对照真实参数、结果与原件哈希。从主记录的「查看经过」打开实际轮次的详情文件。同一轮取证最终回复发送结束后的写入和读回，逐字比对实发全文。正常退出前无需再发消息，退出后核查原文仍可读。
3. 在一个样例会话中触发用户停止，另测已建档会话在新消息落盘前关闭且原文不可取得，以及最终回复已发完但尚未保存时强制中断。确认以最后一次成功落盘为准。从样例仓库内跨日两次运行 `codex resume <会话标识>`。确认各次实际启用项目记录，核对原会话归属、恢复后的有效工作目录和当前交互轮次。检查仍续写原日的主记录，有实际详情的新轮按宿主轮次创建详情文件，新事件各保存一次，丢失原文仍为缺档。归属不符或无法核实的恢复核对既有文件、零新增、零续写、零正文补读及用户任务继续。两个会话的相同文本保持独立。另在隔离仓库为已建档的新版样例添加匹配原资料路径的 Git 忽略规则，再交互恢复并发送新消息。核对原文件内容保持原样，新位置在项目内且可在 Git 工作区看到，从本轮新内容开始记录，并注明本次起点及可核实的原位置。
4. 模拟资料区无法写入及部分写入失败，记录用户看到缺口的时点和任务继续的结果。原文仍可取得时，恢复可写后核对写入重试的实际保存范围。
5. 在样例仓库让代理修好一个问题后提交。回查原始请求和提交前的修复过程。观察提交步骤开始至结果回复发出期间的写入活动，并比对前后的主记录、详情和附件，核对该时段的记录写入次数以及由记录引入的工作区和暂存区新增差异均为零。再发普通消息，核对新内容继续保存，且可通过 `git status --short --untracked-files=all` 查看记录文件。恢复按第 3 步判定归属及写入。
6. 从目标仓库外的同名前缀目录开启交互式会话，在同一可信项目内复验 `codex exec` 和 `codex exec resume`。再从仓库内使用 `codex resume` 选择在仓库外创建的样例会话，并选择仓库内目录。对照结果均为零新增、零续写、零额外正文补读。 [规格确认](spec.md#记录验收与试用顺序)
7. 在已纳入记录的会话中调用一个在对照目录运行的样例工具，核对工具活动仍归入原会话，详情可回查它的工作目录。

上述工具及提交验收还须覆盖以下场景。

- 在同一会话中用两次调用从不同位置取得两个同名且内容不同的附件，例如两份不同目录下的 `report.txt`。分别从两个详情事件打开附件，核对链接目标路径不同，并用 `cmp` 或哈希逐一比对来源文件。第二次保存后重新打开第一条链接，核对原件仍然一致。交互恢复后继续记录时检查两个链接仍有效，已保存的事件各保留一次。

- 使用同一文件工具分别完成业务读取和记录保存、附件复制、断点核对、读回。业务调用的参数和输出应完整可查，内部记录调用不生成新的待记录事件。没有新增业务事件时，保存经读回确认后结束并继续任务；再次恢复也不补录这些内部活动。用户要求查阅记录及提炼/分析派发仍按业务范围保存，不能仅按工具名或资料区路径排除。
- 在同一用户轮次中让首次真实提交受控失败，随后修复并再次提交。分段核对首次提交前和两次提交间的修复均已保存，两次提交及各自结果回复期间分别为零写入，且由记录引入的 Git 新增差异为零。后续普通对话照常保存，记录文件在 Git 工作区可见。可核实归属的恢复中，修复事件各保留一次、提交事件仍跳过。无法核实的恢复按第 3 步核对。不能以一次成功提交或整轮零写入替代该样例。

## 流程 Skill 最终来源消费

记录、提炼和分析按实际正式来源验收，生成的协作 Skill 按便携消费验收。T014 保留旧索引版的正式记录来源。T035 核对准备交付的新版记录及配套组件。T022 在 T017/T021 保存后核对三份流程来源，T026 在 T024/T025 的维护改动后刷新并复验受影响流程。后续清理改变最终来源时，再刷新并复验。

1. 记录实际维护源、版本或源码快照、交付产物、隔离安装位置及启用/信任依据。先核对实际安装命令的来源；当前根 `pnpm skills:link` 指向紧急版，不能仅因命令成功便推定主线新入口已安装。沿既有交付/同步路径在隔离目标刷新本次范围内的最终来源，保护其他来源条目，不手改安装副本。
2. 对照维护源、构建产物与安装文件的清单、完整正文和文件摘要。记录安装核对三个事件分别指向各自的 Python 入口，并读回信任状态。重复安装核对记录条目数量，用隔离对照核对无关 Hook、配置及归属不同的文件仍可使用。新启宿主确认实际发现路径以及 `shadow-profile` 发现数为零。
3. 新开实际 CLI 会话取得正式入口的消费证据。记录核对宿主实际加载并触发的安装组件，并通过实际安装入口完整读取记录 Skill 正文和必要资源。另取模型未读取 Skill 仍可正常记录的轮次。提炼和分析核对父、子代理各自读取的完整安装正文及必要资源，将路径和文件快照关联到实际父轮次和子线程。
4. 用当前快照重新执行受影响的业务流程，将证据放回 T035、T022、T026 的对应验收文件。来源再变化即复验对应入口；缺少刷新、读取或复验时保留该项未验，不凭先前候选探针勾选业务任务。

## 提炼与分析验收

先完成上述最终流程来源消费门禁，再用相应安装入口开展以下业务验收；此前 T015/T018 的最小探针另记候选来源及其适用范围。

先用受控模型和真实 Codex CLI 核对派发与回传链路。再分开准备三组起始材料，用普通用户任务触发判定，提示词不点名工作流或提供样例中的关键依据。通过 `/subagents` 和宿主事件关联父轮次、阶段、子线程与回传，核对实际派发数。

| 起始材料                                             | 提炼派发数 | 分析派发数 |
| ---------------------------------------------------- | ---------- | ---------- |
| 对话不足以提炼，特点也不足以形成规则                 | 0          | 0          |
| 本轮对话足以归纳特点，特点尚不足以形成或修订规则     | 1          | 0          |
| 已有可形成或修订规则的确认特点，本轮没有待提炼的证据 | 0          | 1          |

首次自动提炼的验收由记录入口实际生成仓库内两个项目目录的合格记录，并在同一资料环境配置可读的仓库外、旧影子画像和未确认落盘样例。各组样例用可区分的内容。核对实际交给子代理的证据及产物溯源均采用仓库内两个合格来源，旧样例可继续查阅。每条规则经特点文档回查到实际采用的原始对话。

在每个实际派发样例中，从主记录的父轮「查看经过」定位详情，对照宿主活动逐项核对主会话可取得的派发、交互及回传工具名称、完整参数和输出、事件顺序与子线程关联。用带已知文本的输入和返回比对原值；只能取得活动摘要或字段缺失时，核对对应缺口而非补造。T005 先以受控子代理工具样例验证来源，T015/T018 核对实际链路，T022 验收最终流程入口产生的记录。子线程内部独立留存仍在首期范围之外。

通过 `skills-ref validate <协作 Skill 目录>` 或等价检查核对实际生成目录，确认全部必要资源可在目录内定位。把同一份产物按另一兼容代理的常规方式装入隔离项目，给代理一个代表性任务，记录它发现、读取和应用规则的证据。格式校验和真实消费分别取证。 [Agent Skills 格式校验](https://agentskills.io/specification#validation)

准备包含独占和共享依据的两条规则，删除其中一条，再接收删除前发出的旧分析结果，最后运行一次符合条件的新处理。逐项核对规则、特点及原始对话的变化。

## 共享规则并发采纳验收

先在 T019 的本地回归验证采纳契约，再由 T022/T026 用两个真实父会话及独立分析子线程验收。记录每次派发版本、父轮、子线程、候选位置和采纳前后规则/关联/目录快照，采用受控回传顺序，不能仅靠两次串行分析代表并发。

1. 两个父会话都以同一当前版本 V0 派发独立分析，并让两个候选均在父代理确认前可回传。先采纳 A，核对版本推进到 V1，规则、依据关联和目录一致；再回传 B，核对它因 V0 已过期而未被采纳，V1 及其有效依据未被覆盖或清理，B 的候选及来源仍可核查。交换 A/B 先后顺序复验。
2. 在采纳入口设置可控交错点，让两个写入者都尝试核对 V0，证明版本检查与写入采用同一协调边界，最多一项按 V0 成功；不能在边界外各自检查后轮流覆盖。部分写入失败时不报告成功版本，保留最后确认结果和可恢复的实际缺口。
3. 在两个分析均已派发后删除当前一条规则，核对删除推进版本；随后回传两项旧结果，均不能恢复删除项、清理共享依据或回退目录。继续用最新版本及足够的已有或新增材料发起一次新处理，允许自然重新形成同一规则。

同一资料区、同一份协作 Skill 内进行上述协调，其他独立会话的原始记录仍可继续保存；不新增工程状态服务或永久禁止规则重新形成的名单。

## 旧入口归档切换验收

按用户确认提前执行归档及撤除。在候选工作区比对旧源码与 archive 中的相对文件清单和哈希，核对活动源码、启用声明、构建产物及项目安装副本。依次执行主线交付扫描、常规本地同步和旧源定向同步，再通过新启动的 CLI 宿主重新扫描项目，验证旧入口发现数量为零。T014 通过后，代理在临时仓库用新开的 Codex 会话补验 `conversation-recording` 能被发现并正常记录，`shadow-profile` 的发现数量仍为零。真实对话及历史规格按退役时的现状保留。[开发同步脚本](../../../scripts/dev/actions/link-skills/link-skills.sh) · [T029 验收方案](implementation/T029.md)

历史发现证据只证明当时现场。当前安装不同或宿主仍列出旧入口时，先核对安装目录、实际来源及现有同步路径，保护其他技能和用户资料；同步后新启宿主，以 `skills/list` 的 `forceReload: true` 重新核对仓库根和子目录，并使用可发现的其他技能作阳性对照。当前会话已有的技能目录不作为刷新成功的证据。本轮复核见[退役记录](analysis/shadow-retirement.md#当前工作区复核2026-11-20)。

下列命令用于候选工作区的只读交付清单检查。预期输出的名称中没有 `shadow-profile`。常规同步在隔离工作区执行，定向同步可指定临时目标目录。

## 当前工作区安装与手动试用

这是记录里程碑最后的真实仓库验证。T035 通过后，使用同一验证过的项目级入口在当前工作区安装记录 Skill 及适用配套组件。完成安装时核对实际来源和所需的原生信任。用户可直接打开 Codex 验证首条。 [T033 试用记录](implementation/T033.md)

收到安装交接后，用户在当前工作区验证一条普通任务。

1. 在当前工作区直接运行 `codex` 开启新会话。如出现原生信任提示，确认项目及本次安装的三条 Hook，再发第一条「读一下 README」。
2. 收到回复后，从该轮实际判断的资料根打开 `records/<会话开启日>/<会话ID>.md`，用当轮「查看经过」打开详情。核对主记录中的选址依据、自己发出的原话及 Codex 实际回复，并在 Git 工作区确认记录文件可见。
3. 上述内容都能核对就反馈「通过」。如果有问题，反馈卡在哪一步，例如找不到主记录、链接打不开、详情缺少哪条发言或 Git 状态看不到记录文件。
