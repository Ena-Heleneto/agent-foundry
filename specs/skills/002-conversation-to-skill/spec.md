# Feature Specification: 从 Codex 对话生成协作 Skill

**Feature Branch**: `feature/init`

**Created**: 2026-11-19

**Status**: Draft

**Input**: [规格提示词](requirements/prompts/2026-11-19-conversation-to-skill.md) · [原始需求](requirements/raw/2026-11-19-conversation-to-skill.md) · [需求讨论与确认](requirements/discussions/2026-11-19-open-questions.md)

用户在与 AI 的实际协作中逐步形成编码习惯、沟通偏好和决策方式。用户可以从持续保存的对话核对这些特点的依据，把本仓库不同项目目录中的经验归纳进一份可独立使用的协作 Skill，并维护其中的规则。旧影子画像退出本项目的有效技能入口，以原样归档保留历史依据。

- Q: 同一会话中，两次工具调用生成了同名但内容不同的附件时，记录应怎样保存这两个附件? → A: 分别保存两个原件，详情链接各自指向对应文件。

#### 主记录追加需求

- 用户确认以对话主记录替代索引摘要。首个里程碑保存发言原文与可核实的经过，提炼和分析由后续里程碑承担。同一会话在首次开启日建一份文件，文件顶部保存会话元信息。连续跨日和正常恢复沿合规的原文件续写。
- 首期按用户发起的宿主轮次建组。每组一个紧凑块，标出该组首条用户消息的本地日期，按发生顺序保留「发起」「补充」「回复」原文及其换行。用户中途补充归在同一轮时写到实际位置。AI 主动问询的分组方式留待后续讨论。过程短句写实际做过的事，调用方式在详情中回查。主记录模板放在记录 Skill 的 `template/record.md`。[主记录样式](#主记录样式)
- 收到用户原话后先落盘。当时要求正常轮在发出前保存最终回复全文。现行保存时机见[最终回复保存时机确认](#最终回复保存时机确认)。不可控中断以最后一次成功落盘的位置为准。此次切换完成时移除开发期间旧索引版生成的记录产物，统一按新版建档和续写。对应 FR-002～FR-004 和 FR-007。

#### 详情追加需求

- 有实际详情的组各生成一份 `details/<会话ID>/<轮次ID>.md`，文件位于会话开启日目录下。目标文件落盘且可打开后，主记录才显示独立的「查看经过」。普通问答组只保留主记录中的日期、「发起」和「回复」。详情模板放在记录 Skill 的 `template/detail.md`。
- 按发生顺序照录 AI 已向用户展示且可取得的进度和推理摘要，以及实际工具事件。用调用 ID 关联各次调用和输出，保留并行、分段输出及失败重试的顺序。调用参数和包括长日志在内的可取得工具输出都写在本组详情文件中，以原文保存。宿主已截断时保留取得的部分并注明「已截断」。
- 截图和其他附件原件放在会话的 `attachments/`，从对应详情条目链接。主记录、各组详情和会话附件随项目变更进入 Git。密钥、环境变量值和认证文件按仓库约定排除，详情注明原文省略的范围。对应 FR-003～FR-005。[详情文件与附件](#详情文件与附件)

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 自动保存并续接对话 (Priority: P1)

作为 Codex CLI 使用者，我希望从本仓库内交互式会话的第一条消息开始记录，之后能按会话直接读到我和 AI 的原话，了解这组对话里 AI 做过的事，并打开对应的操作详情。多个会话各自保存，跨日继续同一会话时仍能沿原文件阅读。

**Why this priority**: 可回查的对话是提炼和分析的依据，记录本身也能帮助用户找回一次工作的经过。

**Independent Test**: 从项目级安装后的本仓库两个工作目录分别开启会话，覆盖首轮及后续轮次均有普通问答，另发送含工具调用的任务。核对模型未选用记录 Skill 且零工具调用的对话也会落盘。对照宿主发言核对主记录的内容、顺序与保存时机，检查「查看经过」的目标。分别验证连续交互跨日、普通回复后退出和中断后恢复，并核对无法确认恢复归属时的跳过结果。

**Acceptance Scenarios**:

1. 给定隔离仓库首次完成项目级记录安装及一次记录 Hook 信任确认，用户在两个工作目录按日常方式同时打开空白会话。两处都沿用已确认的信任，首条消息出现前各自的主记录和详情数量为零。用户直接发出首条消息，例如「读一下 README」，该条原话已在对应业务动作前保存并读回，各自建立一份主记录。正常最终回复发送结束后，系统在当轮自动保存全文并读回。收到回复后无需再发消息，正常退出后也能从主记录逐字回查。首轮或后续轮次中模型未选用记录 Skill 且零工具调用时，仍在同一轮保存和读回用户原话与正常最终回复。
2. 给定一轮包含可见进度、工具调用、长日志和附件的对话，从主记录的「查看经过」可以直接打开本组详情文件。可见内容和工具事件按实际发生顺序排列，工具参数和输出原文在本组详情内可读，附件链接可以打开会话附件目录里的原件。仅用于保存、核对记录的内部工具活动不产生新的待记录事件。确认保存后能继续业务工作，不递归追加记录操作。
3. 给定正常会话发生写入失败，当当前轮继续执行时，则缺失的对话块或内容已标记，用户任务继续。恢复写入时原文仍可取得的部分可以重试保存。
4. 给定会话持续交互跨过零点，或者用户次日使用 `resume` 恢复可核实属于本仓库的同一会话，沿合规的原资料位置及原开启日续写同一份主记录。每组标注该组发起的本地日期，每个新事件只保存一次。遇到不可控中断时，记录停在最后一次成功写入的位置。无法核实恢复归属时，本次零写入、零正文补读，已落盘消息仍可回查，用户任务继续。
5. 给定用户说「修好这个问题，然后提交」，原请求和首次提交前的修复过程当轮保存。每次提交步骤及其结果回复的记录写入次数为零，此段由记录引入的 Git 新增差异为零。若提交失败后在同一轮修复并重试，两次提交之间的修复照常记录。后续普通对话继续保存，产生的记录文件可在 Git 工作区查看。
6. 给定自动记录已启用，当用户从本仓库目录外打开交互式会话，或者用 `codex exec` 发起非交互式运行时，则相应的主记录和详情文档数量均为零。
7. 给定新会话同时有可用的项目自定义目录和 Agent 工具的项目目录，选用自定义目录。仅有可用的工具目录时选用工具目录，两档均无可用目录时在项目内建立记录目录。各样例的主记录、详情及已保存的附件均可在 Git 工作区查看。
8. 给定按本版格式建档的会话已有资料位置仍符合写入条件，项目目录约定改变后继续使用原文件。已有资料位置命中 Git 忽略规则时，已有记录保留原位，新选的位置仅承接本轮起的新内容，记录起点和可核实的旧位置。
9. 给定用户在同一轮中途发言，主记录将「补充」及原话放在该组实际发生的位置。多行原文可从同一组完整还原。普通问答组展示日期、「发起」和「回复」。有实际详情的组在详情文件保存并能打开后，以独立的「查看经过」链接打开本组文件。
10. 给定新会话，在会话开启日目录下以会话 ID 临时命名会话目录，并按原时序保存并读回首条消息，不等待标题。
11. 给定已用会话 ID 临时建档的会话，第一轮完整问答结束后，主题明确时由子代理根据已保存的早期对话生成短标题。在原开启日目录下用采纳的标题重命名会话目录，并同步更新受影响的记录链接；有详情与附件时，主记录仍能打开对应详情，详情仍能打开原附件。后续对话即使换了主题也不再次派发命名，恢复时在现有目录续写，不另建主记录。
12. 给定同一日期目录已存在一个按标题命名的会话，当另一会话确定了相同标题时，两个会话的目录名均为「标题＋各自不同的短后缀」。先建档会话的受影响链接同步更新，两份记录均能独立回查，互不覆盖。
13. 给定已有记录的会话，用户在 Codex 界面将其名称从「修复登录」改为「修复登录超时」，在该会话下一次自动记录完成时，原日期下的会话目录名和记录中展示的标题反映新名称，受影响的记录链接指向新路径。会话 ID、发言原文及附件保持不变；若新名称同名，沿用短后缀规则。不要求改名后立即更新。
14. 给定第一轮完整问答未形成明确主题，或未取得可采纳的子代理标题，继续使用会话 ID 目录，正常保存回复和后续对话，不因等待命名而停写。
15. 给定一个普通任务中父代理并行派发两个子代理，并给其中一个补发指令，从主记录的对应轮次进入详情，能分别回查父会话实际可取得的派发、补充指令、回传及其先后顺序。能核实的活动对应到各自的子线程，不把一个子代理的结果串到另一个；某个子代理没有回传或字段不可取得时，保留其他已取得的内容并注明缺口，不补造结果。
16. 给定主代理依次启动子代理 A、B，然后先完成自己的回复，主记录立即保存主代理回复，不等待子代理。若 B 先回复、A 在用户下一条消息之后才回复，主记录按「A 发起 → B 发起 → 主代理回复 → B 回复 → 用户下一条消息 → A 回复」的实际顺序展示，每条子代理记录标明对应身份。B 的回传不冒充 A 的回复，A 的迟到回复不回填到派发处、不覆盖主代理回复，也不另建一份主记录。不含子代理的对照仍使用原有轮次样式。

### User Story 2 - 用多个项目的对话生成并使用协作 Skill (Priority: P2)

作为在本仓库内跨项目目录工作的使用者，我希望代理按需归纳有依据的用户特点，再汇总为一份包含适用情境的协作 Skill，带到其他项目继续使用。

**Why this priority**: 从对话中提炼的经验只有转成代理可执行的规则，才能在后续协作中复用。

**Independent Test**: 提供同一用户在本仓库两个项目目录的已落盘样例，并加入一份仓库外来源的样例检验材料范围。观察父代理分别派发提炼和分析，再将生成的目录交给另一个支持通用 Skill 的代理处理代表性任务。

**Acceptance Scenarios**:

1. 给定已保存的对话尚不足以支持某项特点，当父代理判断提炼条件时，则该项保持待积累。已有材料足以支持特点时，父代理派发提炼子代理，每项特点有独立文档和可回查的依据。一次性项目决定仍带有当时的适用情境。
2. 给定已有提炼文档，当父代理判断分析条件时，则在足以形成或更新规则时派发分析子代理，汇总生成一份协作 Skill。依据不足时等待后续材料。来自本仓库不同项目目录的依据可逐条回查，特点与规则形成后可直接使用和维护。
3. 给定协作 Skill 目录已生成，当用户按常规方式在其他项目或兼容代理中使用该目录时，则代理可以据此发现、读取并在实际任务中应用规则。
4. 给定本仓库同时存在旧影子画像对话和新流程记录，当首次自动提炼时，则特点的原始依据均来自新流程记录，旧影子画像对话可作为历史资料回查。
5. 给定两个父会话基于同一规则版本分别启动分析，当结果先后回传且其中一项已被采纳时，则另一项过期结果不覆盖较新版本，保留依据并在最新材料上重新判断。与删除交错时也保留当前删除结果。

### User Story 3 - 删除规则并保留以后重新形成的可能 (Priority: P3)

作为协作 Skill 使用者，我希望删除某条规则，同时保护其他规则当前使用的依据，并让以后观察到的行为仍能形成有效规则。

**Why this priority**: 用户可以维护当前协作规则，长期可复核的对话材料也能继续发挥作用。

**Independent Test**: 准备两条规则及独占、共享的提炼文档。删除其中一条，再用保留的对话执行一次符合条件的提炼和分析。

**Acceptance Scenarios**:

1. 给定待删除规则有一项独占依据和一项共享依据，当用户删除规则时，则当前 Skill 移除该规则，独占提炼文档及关联被清理，共享文档仍支撑另一条规则，原始对话仍可回查。
2. 给定同一规则曾被删除，当后续有效的提炼和分析再次得到足够依据时，则同一规则可以自然形成，依据既可以来自已有对话，也可以来自新增对话。
3. 给定删除前已有一轮分析在进行，当该轮回传包含被删除规则的旧结果时，则当前产物仍反映用户的删除决定。

### User Story 4 - 归档并退役旧影子画像 (Priority: P3)

作为仓库维护者，我希望将旧影子画像技能原样存档，再撤下活动入口，便于以后追溯旧行为和当前交付边界。

**Why this priority**: 迁移需要保护原始技能和历史对话的依据，同时结束旧入口在项目中的自动发现与交付。

**Independent Test**: 在有旧源码和项目级安装副本的环境中执行退役，核对归档原件及正常安装或同步后的技能发现结果。

**Acceptance Scenarios**:

1. 给定旧影子画像技能仍在维护与安装位置，当退役完成时，则新 Spec 下存在内容完整的原样归档，项目级旧安装副本及旧入口的启用和交付配置已移除，历史规格与已有对话仍可追溯。
2. 给定旧入口已退役，当执行项目正常安装或同步并重新发现技能时，则可发现的旧影子画像入口数量为零。

### Edge Cases

- 宿主信任提示与用户的确认操作期间，空会话的主记录和详情均为零。需要宿主信任的候选在取得信任后才算启用。
- 同日并发会话可以产生相同文本。根据会话、轮次和内容实际来源识别重复写入，各会话的相同发言仍独立保存。
- 遇到用户停止、CLI 被强制关闭或进程失去控制时，以最后一次成功写入为记录边界。中断若发生在正常最终回复发送结束后、保存前，主记录可能留有末轮缺口。只保存到「发起」的块仍是有效记录。
- 正常运行中的写入失败按 FR-006 处理。主记录、详情或附件中已确认保存的内容仍可用于后续处理。
- 同一个文件工具既可用于业务也可用于记录维护，应按本次操作用途区分，不能按工具名或资料区路径统一排除。记录维护与业务操作分别调用，用户要求查阅记录的业务活动仍按范围保存。
- 不同项目的行为依据可能只适用于各自情境。提炼文档说明适用范围，分析后的规则保留这些条件。
- 子代理无法启动或结果尚未返回时，已保存的输入和当前有效产物仍可使用，相关阶段按实际完成情况判定。
- 两个父会话可同时分析同一份协作 Skill，但其结果采纳与删除应协调进行。过期候选不能覆盖较新规则、依据关联或目录内容，也不能因过期结果清理其他规则仍在使用的特点。
- 删除规则前已经启动的分析在随后回传时，当前版本仍反映删除结果。再次生成由后续符合条件的提炼和分析决定。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001** 要分别提供记录、提炼和分析三个独立 Skill。每份 Skill 有符合通用规范的独立目录、`SKILL.md` 和必要文档资源，定义自身职责、触发条件、输入和产物。提炼和分析由 AI 按各自的 Skill 指令直接使用宿主已有工具执行。当前记录阶段以现有 Skill 目录为输入，同一次本地安装将整份 `conversation-recording` 复制到项目 `.agents/skills/`，并在 `.codex/hooks.json` 登记该副本中的三个入口。Codex 分别触发对应用户消息、工具完成和回复完成的三个 Hook。每个 Hook 由独立脚本处理对应事件，互不调用。各脚本共用宿主事件读取、会话校验和文件存储能力。新增交付方向为结合集合配置与脚本构建形成打包产物，并支持通过 curl 安装时自动挂载 Hook；具体安装入口、目标环境、信任、更新及失败恢复方式待讨论确认，当前本地复制安装仍是已验收方式。
- **FR-002** 项目级记录安装后，用户通过 Codex 原生流程对本次安装的记录 Hook 确认一次并启用记录。同一项目的 Hook 定义和 Codex 信任状态保持不变时，后续普通启动无需再次确认。用户在本仓库根目录或子目录按日常方式运行 `codex` 并发送消息，无需手改配置、点名记录 Skill 或另行启动记录。每个符合条件的交互轮次都自动进入记录流程，包括模型未选用记录 Skill 且零模型工具调用的轮次。用户发出的第一条正常对话消息触发 FR-003 建档，后续轮次沿同一会话续写。纳入记录的用户发言须在对应业务动作前保存并读回原文。无业务动作时，在开始发送最终回复前完成用户原话的保存和读回。正常最终回复发送结束后，在当轮自动保存实际发出的回复全文并读回，内容与实发文本逐字一致，无需用户再发消息。主记录可以独立写入，已发生的过程按 FR-004 和 FR-005 随本轮推进陆续写入。写入失败、恢复及不可控中断、Git 提交停写分别按 FR-006、FR-007、FR-008 处理。若采用 Hook，须在其通过首期会话记录验收后移除由其接替的旧记录逻辑。
- **FR-003** 记录流程在实际保存时根据项目规则和已核实的会话位置选择或复核资料根。首次选址依次考虑项目自定义规则、Agent 工具的实际项目内资料目录、根据项目情况自选的项目内记录目录。主记录、各组详情文件和会话附件均纳入项目 Git 管理，随项目变更提交，并遵守[详情文件与附件](#详情文件与附件)中的提交边界。Git 忽略规则不得覆盖新写入的记录或附件。每个会话按实际开启的本地日期建档；新增布局在日期目录下按对话标题命名会话目录，目录内包含主记录、详情和附件。首次记录以会话 ID 临时命名会话目录，不等待标题，按 FR-002 保存并读回首条消息。第一轮完整问答结束后，主题明确且已保存时，由命名子代理根据已保存的早期对话生成短标题。采纳标题后，在原日期目录下用标题重命名会话目录，并同步更新受影响的记录链接，保留已保存内容及会话 ID。主题不明确或未取得可采纳的标题时，保留会话 ID 目录并继续记录；命名不阻塞正常记录。成功采纳后不因后续对话变化再次自动派发命名，仍适用同名后缀和用户在 Codex 界面主动改名的规则。同一日期目录下，对话标题相同时，所有同名会话的目录名均在标题后添加彼此可区分的短后缀，包括先建档的会话；改名时同步更新受影响的记录链接，不覆盖任何记录。本次澄清不迁移或改写既有记录。会话 ID、实际开启时间和首次工作目录继续作为现有身份及归属核验材料，是否调整其保存方式待目录方案讨论。连续交互和正常恢复跨日均沿合规的资料根和原开启日续写同一份主记录；目录已改名时使用新路径。并行会话各自保存。此次开发变更完成时，移除旧索引版生成的记录产物，建档和续写统一采用经确认的新规则。

  用户在 Codex 界面修改已建档的会话名称后，在该会话下一次自动记录时同步更新原日期下的会话目录名、记录中展示的标题及受影响的链接，不要求即时同步；命名冲突沿用短后缀规则。会话 ID、发言原文及附件不因改名而改变。标题读取的[隔离验证](requirements/discussions/2026-11-26-recording-title-source-research.md#2026-11-26-隔离-cli-实测)已完成，正式读取方式及路径命名规则尚未确定。用户直接在磁盘上重命名或移动会话目录不属于首期支持和验收范围。
- **FR-004** 首个里程碑保存原始对话和可核实的操作经过。无子代理时，主记录采用[主记录样式](#主记录样式)，由用户发起的每个宿主轮次对应一个紧凑文档块。每组通过随块保存的宿主轮次 ID 定位，并显示该组第一条用户消息的本地日期。涉及子代理时，主记录按 FR-017 展示，仍保留主轮次与详情的关联。发起、同轮补充和最终回复按实际顺序保留原文，多行、空行、列表和代码块能够还原。简短过程写 AI 实际做了什么。本组已有实际详情，且详情文件保存后可打开时，才显示独立的「查看经过」链接。提炼用户特点和分析协作规则属于后续里程碑。
- **FR-005** 当组内有可留存的进度原话、可见推理摘要、工具活动或附件时，按[详情文件与附件](#详情文件与附件)写入一份独立文件，以会话 ID 和宿主轮次 ID 对应到主记录的组。工具回调先保存文本、宿主稍后提供同一结果的附件时，在原结果块补齐原件和链接，该结果仍只记录一次。主会话中可取得的子代理派发与回传按实际活动留存，包括提炼和分析的派发。仅为记录本身保存、复制附件、核对断点及读回确认而产生的内部工具活动不纳入待记录事件，避免递归自记录。
- **FR-006** 正常会话发生写入失败时，要先标记受影响的块和缺失内容，再继续用户任务。资料区暂不可写时在会话中标明缺口。恢复可写且原文仍可取得时可以重试保存，失去原文的部分保留缺档。已确认落盘的材料可供提炼继续使用。
- **FR-007** 会话关闭、终止或用户停止时，以最后一次成功落盘的位置为准。项目记录已按 FR-002 启用，且原会话与恢复后的有效工作目录均可核实属于本仓库的交互式恢复，沿合规的资料根、原日期和原文件写入恢复后发生的新事件，每个事件只保存一次。此前尚无合规的本版记录时按 FR-003 选址，从本轮新内容开始建档。已有本版记录的位置命中 Git 忽略规则时，保留已写内容，在新位置记录本次起点和可核实的原位置。归属不符、无法核实或入口为非交互时跳过本次新建、续写和记录所需的会话正文补读，用户任务继续。
- **FR-008** 记录入口维护跳过记录的场景，按实际操作步骤匹配，首个场景为 Git 提交。每次提交步骤开始至对应结果回复发出期间跳过记录写入，该时段由记录引入的工作区和暂存区新增差异为零。恢复时沿同一边界处理。用户原始请求、修复过程、两次提交间的修复和后续普通对话照常保存。
- **FR-009** 父代理要惰性判断已落盘的材料是否足以归纳有依据的用户特点，条件满足时派发提炼子代理。自动提炼使用同一用户来源于本仓库根目录及子目录的已确认记录，仓库内的多个项目目录可以共同提供依据，已有与新增记录均可用于后续提炼。首次自动提炼使用新流程保存并确认落盘的本仓库记录。旧影子画像对话作为历史资料保留。
- **FR-010** 每项特点要用单独的文档文件保存，说明适用情境、依据和关联的来源项目及原始对话块。提炼要区分用户明确表达、反复出现的行为和只适用于一次任务的决定。
- **FR-011** 父代理要独立惰性判断提炼结果是否足以形成或修订规则，条件满足时派发分析子代理。分析根据已有提炼文档形成可执行规则，保留规则到提炼文档的关联，支持汇总本仓库多个项目目录的特点形成一份协作 Skill。特点和规则依据材料自动形成，供用户直接使用与维护。多个父会话更新同一份 Skill 时，结果采纳与删除应协调核对当前规则版本，过期结果不覆盖较新规则、依据关联及目录内容，保留候选及来源供后续重新判断。
- **FR-012** 生成的协作 Skill 要包含完整且符合通用规范的目录、带有效 `name` 和 `description` 的 `SKILL.md` 及正文引用的必要资源。兼容代理应能仅凭产物目录在其他项目中发现、读取和应用规则。原始对话、附件和溯源依据留在本地资料区。
- **FR-013** 用户要能删除当前生成的任一规则，并清理仅为该规则提供依据的提炼文档及关联。共享文档继续支持其余规则，原始对话和附件仍可供回查和重新提炼。
- **FR-014** 后续满足条件的提炼与分析要允许依据已有或新增的对话重新形成已删除的规则。删除结果对当前版本生效。
- **FR-015** 要将 `packages/skills/src/profile/shadow-profile/` 中的旧 Skill 原样移入本 Spec 的 `archive/shadow-profile/`。核对归档完整后，移除 `.agents/skills/shadow-profile/` 安装副本并撤下旧入口的启用和交付配置。历史规格和已有对话资料继续作为历史依据保存。
- **FR-016** 第一里程碑中 Skill 的模板文件需要经 ESLint 检查并修复，当前包括记录 Skill 的 `template/record.md` 与 `template/detail.md`。检查应针对实际模板源码；ESLint 忽略该类文件或执行失败时，不得记为通过，须如实报告并另行核对模板内容。
- **FR-017** 主代理和业务子代理独立运行时，主记录仍按 FR-002 的时机保存用户发言与主代理回复，不为记录等待子代理。未涉及子代理的会话保持 FR-004 的现有展示样式；涉及子代理时，在同一主记录按事件实际发生时间穿插可取得的启动输入、对话补充和实际回复，标注时间和对应子代理身份。跨轮到达的回复按实际发生位置记录，用可核实的子线程身份关联原派发，不将它归作主代理的回复。无法取得内容时按实际范围留缺，不补造；不替代 FR-005 的工具详情留存。主、子代理事件来源和可核实时间仍需验证。
- **FR-018** 主记录中每两个相邻消息块之间都应有清晰可见的分隔，不仅靠空行区分。每次发起、补充或回复各是一个消息块，包括普通对话内同一轮的多个消息块及主、子代理交错的消息块。分隔是外层排版，不得混入原文、拆开多行消息，或改变轮次、时间顺序、代理归属和详情链接。

### 主记录样式

记录 Skill 在 `template/record.md` 存放 Markdown 模板。对话组用二级标题，组间用横线和下一组的二级标题区分；组内消息用三级标题标明角色和类型，相邻消息之间用横线分隔。标题与正文分开，正文不加引用前缀或框线。同一轮中途插入的发言用「补充」标识，写在实际发生的位置。简短过程用一两句表达实际做过的事，调用命令、参数和工具输出从详情回查。横线和可见标题不作为消息识别依据。 [样式确认及实施方案](implementation/T036.md)

以下是无子代理时的轮次样式，分隔线为示意。涉及子代理时按 FR-017 展示跨轮时间顺序；轮次和子线程身份用于关联详情，不决定迟到回复的展示位置。两种样式都按 FR-018 区分相邻消息块。

```markdown
# 对话记录

会话 `{会话ID}` · 开启 `{开启时间}` · 目录 `{首次工作目录}`

## {日期或时间} · {组标题}

### 用户发起

{用户原话}

---

### 主代理回复

{回复原文}

[查看经过](details/{会话ID}/{轮次ID}.md)
```

### 详情文件与附件

详情模板位于记录 Skill 的 `template/detail.md`。详情文件以真实轮次 ID 命名。详情及附件沿同一会话的首次开启日存放。

```text
records/<开启日>/
├── <会话ID>.md
└── details/
    └── <会话ID>/
        ├── <轮次ID>.md
        └── attachments/
            └── <附件文件名>
```

- 详情按实际发生顺序保存可取得的工具事件，以及 AI 已向用户展示的进度原话和推理摘要。工具事件保留可取得的时间、工具名、调用参数、工作目录、输出和执行状态。并行调用的输出和同一次调用的分段输出均用实际调用 ID 关联到对应调用，失败和重试各自保留。
- 可留存的调用参数和工具输出均以原文写在本组详情文件中，包括长日志、分段输出及报错。宿主已截断的输出保留能取得的部分，并标明「已截断」。其他缺失内容按实际范围标记。
- 截图和其他附件原件按原始字节保存在会话的 `attachments/` 下。目录在有附件需要保存时创建，详情从对应事件用相对链接打开该原件。同一会话内同名但内容不同的附件分别保存，避免覆盖已保存的原件。
- 密钥、环境变量值和认证文件按仓库的提交约定排除。详情保留可记录的调用和执行状态，并注明原文省略的范围。

### Key Entities _(include if feature involves data)_

- **会话**有可区分的身份、使用者、来源项目或工作目录、实际开启时间和已保存范围。同一会话的主记录汇集连续交互及正常恢复后的对话。
- **对话轮次**由一条用户发言开启，包含有顺序的后续发言和可取得的活动。无子代理时每轮对应一个主记录块。有详情时按真实轮次对应详情文件；涉及子代理时，仍保留轮次归属，不强制其启动输入与回复在主记录中相邻。
- **子代理对话事件**归属于可核实的子线程，并与所属主会话关联。主记录保留可取得的发起、补充、回复及其实际时间顺序，用子代理身份区分并行对话。
- **用户特点**有独立记录文档，保存归纳依据、适用情境和原始对话的定位。一个特点可以支撑多条规则。
- **协作规则**定义适用情境和可执行行为，有一项或多项提炼依据。其依据关系需要支持独占与共享文档的清理判断。
- **协作 Skill**是可独立使用的交付目录，包含规则入口和必要资源。对应的提炼、溯源和原始记录保存在本地资料区。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001** 在新隔离仓库用现有记录 Skill 目录执行本地复制安装，核对 `.agents/skills/conversation-recording/` 的实际文件。`scripts/` 只有三个入口，三条项目 Hook 分别指向安装副本中的对应脚本。在隔离对照中分别只保留一个入口及公共模块，运行其登记命令，读回对应的用户原话、工具结果或实际回复。另在无预置信任的 Codex 状态中通过原生界面完成一次记录 Hook 信任确认。退出首次启用会话，保持安装定义和信任状态，在两个不同项目目录并行打开普通交互会话。两个会话均无需再次确认记录 Hook，输入前各有零份主记录和详情。各会话在用户直接发出第一条正常对话消息时建立一份项目内 Git 可见的主记录，随后至少一轮续写同一文件，每个合格轮次恰好一个对话组。首轮及后续轮次各至少有一个模型未选用记录 Skill 且零工具调用的样例，且均在当轮保存并读回用户原话和正常最终回复。含业务动作的轮次在首个对应业务动作前已保存并读回用户原话。正常最终回复在发送结束后自动保存全文并读回，读回内容与实发全文逐字一致。正常退出样例无需再发消息，退出后仍可读取。每组可按日期、宿主轮次和记录顺序定位，详情链接能打开实际的同组内容。仓库外交互会话及非交互式运行零新建、零续写和零记录所需的额外正文补读。合规恢复和提交停写按 SC-003 和 SC-004 验收，旧索引版生成产物按 FR-003 核对移除结果。三个 Hook 通过首期会话记录验收后，移除被接替的逻辑，再用最终安装版本复验。
- **SC-002** 同一会话中有实际详情的组分别对应一份可从主记录打开的详情文件。可见进度、推理摘要和工具活动可按发生顺序回查。并行调用、分段输出和失败重试能对应到实际调用，所有可留存的参数和输出原文直接在本组文件中可读。截断及因提交边界省略的范围已注明，保存的附件原件与来源字节一致。同一会话中，两次工具调用产生同名但内容不同的附件时，从每条详情链接打开的文件均与该次调用的原件字节一致。工具回调先到文本、同一结果的附件稍后到达时，详情中该工具结果只出现一次，附件链接可打开且与原件字节一致。实际子代理派发样例中，主会话可取得的派发及回传活动能按顺序定位。同一文件工具分别执行业务和记录维护时，业务调用保留，内部记录调用不产生待记录事件。保存经读回确认后结束并继续任务，不因记录活动自身无限追加。
- **SC-003** 在正常写入失败样例中，用户可识别受影响的内容且当前任务继续。中断样例覆盖回复发送结束后、保存前的强制中断，主记录保留到最后一次成功落盘的位置。之后在可核实归属的两次恢复中沿用原日期和文件，已保存内容保持可查，新事件各记录一次。归属无法核实的恢复对照为零新增、零续写和零正文补读，既有记录保持可查。
- **SC-004** 在真实的「修复后提交」样例中，可回查用户请求、首次提交前的修复和后续普通对话。在同一轮提交失败、修复再重试的样例中，还可回查两次提交之间的修复。每次提交步骤及其结果回复期间的记录写入次数为零，且由记录引入的工作区和暂存区新增差异为零。普通轮次的主记录、各组详情和会话附件在 Git 工作区可见，符合提交约定的文件可随项目变更一同提交。
- **SC-005** 使用本仓库至少两个项目目录的已保存材料得到一份协作 Skill。该次生成的每条规则均可经提炼文档回查到原始依据，参与材料的来源均可核实位于本仓库目录内。首次自动提炼时，每条特点的依据均可回查新流程记录。两个父会话从同一版本派发分析后，先采纳的结果推进当前版本，随后返回的旧结果及与删除交错的旧结果均不回退当前规则、依据关联或目录内容。
- **SC-006** 一位使用者将产物目录带到另一项目后，兼容代理可以仅凭该目录在至少一个代表性任务中正确应用其中的规则。
- **SC-007** 删除测试中，一条规则及其独占提炼依据被移除，共享依据及原始记录完整可查。后续符合条件的一次处理能够基于保留的材料重新形成该规则。
- **SC-008** 旧技能的归档内容与原件一致，项目经正常安装或同步后可发现的旧入口数量为零。
- **SC-009** 采用通用 Skill 格式核验时，记录、提炼和分析三份 Skill 各有一个独立、可读的入口及可定位的必要资源，各自的输入、触发条件和产物都能核对。
- **SC-010** 在隔离用例中让父代理启动两个业务子代理但不等待，至少一个子代理在下一用户轮开始后才回复。用不同的已知输入和回复对照同一主记录的顺序、时间和代理标注；主代理回复在子代理结束前已保存并可回查，两份子代理回复按实际时序写入且不混淆身份。无子代理的对照保持原有样式和保存时机。
- **SC-011** 打开实际生成的普通对话主记录，核对同轮及跨轮的每两个相邻消息块之间均可看到分隔；多行消息、消息正文内的分隔符及代码块原样回读，详情链接仍可用。恢复续写后新边界不漏、不重复；主、子代理时间线以 SC-010 的交错样例补验同样的显示规则。

## Assumptions

本次补充的并发采纳边界及验收修订依据见[一致性修订记录](requirements/discussions/2026-11-19-open-questions.md#一致性分析后的修订2026-11-19)，原始输入保留不变。

- 子代理对话事件按 FR-017 加入主记录；父会话能取得的工具活动仍按 FR-005 保存。子线程内部工具与附件及记录维护类子代理的留存范围待确认。已有父会话派发与回传的样例不能代替跨轮、非等待时间线的验证。
- 归档日期以会话实际开启的本地日期为准，首条消息出现时按该日期建档。原始资料按来源归档，自动提炼按会话来源目录判定材料是否属于本仓库。
- 一次明确的持续性偏好或纠正可以成为提炼依据，日常观察随证据积累。分析以能够形成或修订规则的提炼结果为依据。具体判断条件由后续规划明确。
- 旧 `profile` 集合中其他 Skill 的复用由后续规划核对。
- 规划需要验证目标环境可取得会话身份、实际开启日期、消息、结束及恢复所需的内容，且支持父代理实际派发子代理。三份流程 Skill 和最终产物的格式遵循通用规范。 [Agent Skills 规范](https://agentskills.io/specification)
