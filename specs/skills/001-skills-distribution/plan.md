### 开源源码与正式安装来源

后续由用户将`packages/skills-distribution-urgent/`、`packages/skills/`、`specs/skills/`、`apps/mcp/`一同迁入新开源仓库，保持相对结构，新仓库采用ISC并保留适用第三方许可。eval源码及样本可随packages/skills保留，正式技能发布物、官方列出与安装中的eval数量必须为0；正式安装建议只指向精确payload固定树，不指向源码仓库根。

四处源码不等于完备的可运行新仓库：当前技能包依赖未在迁移范围内的preset-config及根catalog，部分测试引用`scripts/dev`和`.specify`；迁后人工配置新根依赖/目录和等价检查，消除未交付Foundry引用，不暗中追加迁移整个preset目录、不建设工程导出器，也不删测试求绿。`apps/mcp`仍消费旧`packages/skills/dist/manifest.json`，而主线当前没有该生产能力；源码可随迁，运行兼容及线上部署不能因此标通过。该旧缺口不自动扩展为本轮紧急实现任务，实际受影响消费者另按调用关系验证。

`specs/skills`正文、历史验收和archive也需逐项核对公开范围，不能只排除`.specify`目录：已有材料含个人画像摘要及私有引用。原始依据保留当前仓库，公开副本只保留可公开内容和真实来源说明，不能为修复断链复制画像或伪造历史。当前本地阶段只准备清点和调整说明，实际迁移前仍核对最终字节。

### 连续推进中的迁后阶段

## Summary

来源统一维护在src一级集合，collection.config.json使用packageName、mcp及skill映射；逐事件hook保存独立参数和扩展属性，正文、frontmatter及附件按原字节交付。集合自动发现，实际技能选择由清单决定，缺配置或空清单不自动交付技能。

按[已确认职责与分段](requirements/discussions/2026-11-11-independent-plugins.md)分别维护目录、技能复制及脚本生成插件，各插件独立读源，无总函数内嵌全部实现、共享业务context或必需API通信层。用户最新已取消强制组合式/工厂函数和声明全部内置的约束，普通模块写法按实际实现选择。当前目录插件已实现并注册，collections插件暂时负责技能资产及虚拟入口；其余两个插件仍只有空函数。目录在真实写出后补齐，文件通过Vite资产API交付，维持清理前校验和write=false等边界。详细工程结果见[目录实现记录](implementation/T075.md#实际实现与验证2026-11-11)。

用户要求文档同步后自行手写修改；本轮不继续编码，AI等待用户实际改动或进一步请求。脚本生成规则、位置及MCP内容仍待后续讨论；既有工程记录不替代用户未来修改后的验证，也不据局部构建放行安装/挂载、候选或发布。闭环及工程状态继续在原位置维护。

## 总体架构：一条链，逐步返回结果

**适用范围修正（2026-11-11）**：本节及下方原重做边界、推荐顺序中的旧三目录、BaseBuildPlan和MCP清单算法保留为旧重规划参考。当前主线遵循FR-048～060的集合来源、独立插件及空MCP目录；T068～T070执行前须按现有方案核对适用内容，不直接恢复已归档模型或提前决定T077。主线任务身份、顺序和用户手写分工保留；紧急副本只按上方增量及其契约实施，不将这些旧算法当作前置。

`读取来源 → 形成构建计划 → 写出并复核 → 准备候选 → 绑定平台归档 → 发布已验字节 → 只读远端核验`。

这是构建/CI 的内部阶段，不是新增终端用户命令。每个阶段只消费前一步已核验结果；失败抛出带阶段和原因的错误，外层报告 failed，并将依赖阶段标为 not-run。数据模型见 [data-model.md](data-model.md)，完整输入和返回契约见 [contracts/build-pipeline.md](contracts/build-pipeline.md)。

1. 来源读取固定实际技能、MCP、脚本及依赖证据，构建前拒绝链接、身份冲突、非法路径和缺必需材料。普通开发输入与干净提交候选分开；未提交字节不得冒认指定提交。
2. 内存中产生目标路径和内容；构建计划不写文件。T067/T068先验证的BaseBuildPlan/BaseBuildOutput只是原始三目录/MCP中间结果；T069补齐完整BuildPlan并校验后，才写出完整BuildOutput。单一有序编排负责三目录、MCP 清单、Release 和两种安装格式，避免多个独立钩子靠偶然顺序覆盖输出。
3. 从实际磁盘重新核验产物，不只比较内存计划。脚本与附件按原始字节交付，清单及格式转换按既定规则生成，源内手写 MCP 清单失败。
4. 全量 dist 与公开 payload 分开。payload 精确等于 release.json.files 加 release.json，额外文件也失败；candidate须显式选isolated/full，准入表见[pipeline契约](contracts/pipeline.md#候选范围与准入条件)。isolated只允许列明的局部来源和未执行完整门禁，不豁免严格字节/附件/README/许可证检查；full须全部内容门禁通过，上传前仍无ready。Foundry始终仅隔离用途。
5. 上传前固定内容索引；上传成功后把真实 artifact ID 与内容摘要绑定成独立平台收据。最终 CandidateResult 结合内容索引和收据，才判断正式资格；本地 isolated 材料不会升级为真实平台。
6. 发布只读取可信固定版本的工具和已核验候选，不安装依赖、不构建、不执行候选脚本、不回写 README。只读复验核对远端全部文件和实际主线curl入口结果。

## 推荐顺序与调整依据

依据[本轮明确顺序与补全理由](requirements/discussions/2026-11-10-build-actions-mount-order.md)，清退之后先完成唯一 vite.config 的内容构建、MCP 清单、Release/投影、读盘和纯安装兼容验证；Spec Kit 原生挂载暂用明确未实现的脚本占位。优先复用已有未接通分支，保留已完成文件核验，不在 Vite 里生成假成功脚本、不调用旧注册器；挂载请求非零且零原生写入，--no-mount 保留纯安装事实。

构建局部结果可验收后，再实现 GitHub Actions 的只读检查、严格候选、归档绑定、发布故障保护及手动发布 workflow，复用同一构建实现。此阶段可用声明完整限制的 isolated 材料开发与验证，不先要求真实挂载交付；占位或任何必需挂载证据缺失仍使正式 full/ready 失败，不能通过改标签升级。

Actions 实现和隔离验证之后，完成纯安装链所需前置，取得主线正式同版来源，替换临时占位，接通仅 Increment 与所选 hooks 的真实挂载及宿主加载。随后汇合完整内容、安装/挂载、支持矩阵、文档与发布门禁，完成完整本地交付；用户直接迁移后，在独立仓库重新检查与构建，另获指定候选授权才首次发布。CI 开发、完整本地验收和真实平台发布分别判断。

此安排让维护者先检查内容与纯安装，再审阅和验证自动交付，最后检查原生项目集成；替代此前构建起步即同步开发只读 CI 的推荐。正式来源、真实平台或用户条件缺失只阻断对应完整下游，不要求前两段开发等待；原最终功能与验收、暂停/撤回身份和唯一末尾综合收尾继续保留。详细任务映射与状态集中在 mvu/tasks，不在 plan 重复维护。
