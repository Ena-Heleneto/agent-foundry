# 构建、GitHub Actions、真实挂载的推进顺序

## 用户原意

用户指定本 Spec，调用 task-increment 并提出：

> 我们的实现顺序 先实现构建配置，vite.config，同时 speckit 挂载脚本使用 临时占位脚本占， 在实现发布 流水线，这部分使用github action，最后实现speckit挂载脚本

本次据此将实施顺序调整为：先完成单一 Vite 构建及其产物验证，挂载先临时占位；再实现 GitHub Actions 的检查、候选、归档与发布流程；最后接通真实 Spec Kit 挂载。此顺序替代此前构建刚开始便同步开发只读 CI 的推荐，不撤销原功能或验收要求。

## 实际材料与补全理由

T064 已实际清退旧构建，有效 vite.config.ts 当前明确拒绝 build；新构建和流水线尚未实施。mount-entry 已有原生未接通时明确失败的骨架，可优先复用作为占位边界，保留同版文件核验及安装事实；现有 register-hooks/register-commands 源码不因本次规划删除，也不在占位阶段调用。具体最小调整在对应 Task 实施准备时核对。

占位是临时可见的未实现状态：请求真实挂载时非零退出、hooks/commands 不执行，报告未实现及恢复条件；显式 --no-mount 时适用阶段 skipped，纯安装已成功事实保留。构建仅复制脚本原始字节，不执行脚本或由 Vite 生成虚假成功入口，不新增终端用户子命令。占位不能通过实际加载、完整矩阵或正式发布门禁。

构建阶段先让维护者检查真实技能和附件，并在隔离项目纯安装；流水线阶段让维护者审阅同一产物的检查、候选身份及授权/失败行为；挂载阶段才让使用者取得真正可用的 Increment 和所选 hooks。阶段结果分别验收，不能以技术文件存在代替其结果。

GitHub Actions 可以先完成实现和隔离验证，真实发布仍须真实挂载、正式同版来源、完整检查及迁后指定候选授权。占位阶段只允许 development 或明确 isolated 的实验，正式 full/ready 拒绝缺挂载证据；不借“先实现发布流水线”授权提前发布占位包。T060 的完整本地交付及迁后 T061/T062 留在真实挂载之后，避免把完整验收提前成开发前置。
