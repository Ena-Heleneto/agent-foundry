# install.sh 主流程与当前取舍

日期：2026-11-14。来源：[本会话用户原始输入](../raw/2026-11-14-install-shell-flow.md)。本次同步需求和讨论，不作为 T077 完整实施方案或工程验收。

## 当前脚本参数、版本表及依赖准备

用户后续明确首个版本参数默认 `latest`，版本表项含 `version`、`url`；接受 jq，并选择 npm 准备依赖以减少自有下载代码，要求不全局安装。固定下载根从环境变量方案改回脚本内维护。此前主线“无 latest 默认”和“工具自动下载未定”的说明按本节更新，具体最低 Node 版本没有因此重新定案。

当前脚本及示例约定版本表为数组，最新已发布记录放第一条，`latest` 取首条；指定版本必须唯一匹配。该排序约定没有自动比较语义化版本，发布端后续须维护约定顺序。当前下载的 `release.json` 明确指版本链接表，不是旧单版文件清单；后者的完整性职责保留，但同名、schema、存放位置及下载映射尚待发布设计适配。

运行顺序为：检查基础命令 → 创建本次私有临时子目录并登记 EXIT 清理 → npm 临时安装 jq → 下载版本表 → 解析请求版本的 URL。后续选中内容下载、文件摘要校验、正式安装及适用挂载尚未接入。用户问到的 `trap` 是登记退出时的命令，写在 curl 前不等于当场删除；`mktemp` 的日期时间前缀用于辨认，随机后缀避免多次运行重名。

源码现在检查 curl/node/npm/uv，通过 `npm install --global=false --prefix <本次目录>/deps --cache <本次目录>/npm-cache` 安装固定 `node-jq@6.3.1`，通过包内 `bin/jq` 调用，不改全局 PATH。npm 方案替代此前 Linux x86_64 的手动下载和摘要分支；不由此宣称全部平台通过。npm 校验包与其安装脚本的执行不等于所选技能文件完整性校验，后者仍须单独实现。

上一轮实际完成：Bash 语法、默认/指定版本及错误分支隔离检查、退出清理检查、`pnpm --filter @foundry/skills build`、源脚本与 dist 产物字节比对。另在临时目录实际验证过 npm 安装 `node-jq@6.3.1` 和版本查询，所下载 jq 报告为 1.7.1；这是 Node 包版本与其封装二进制版本的区别，不是用户新设的最低运行时。真实 R2 地址仍是占位，未实际下载技能或完成安装。版本标记文件及持久发布记录的生成仍未接通；本次只保存这些事实，不补改代码或任务完成状态。

## 问题与用户明确的思路

用户要先理解 `install.sh` 的运行逻辑，明确提出的主线是：**检查环境 → 下载依赖或者文件 → 完整性校验**。讨论围绕使用者执行脚本后发生的事情展开，不能用插件构建或发布准备代替脚本运行逻辑。

Agent 此前默认 `install.sh` 只下载并启动旧 Node 安装器，随后又引入 `installer.tar.gz`、先复制整个 `script/` 等建议，没有先对齐职责，造成理解偏差。这些不是用户已经选定的实现方案，不再作为本轮已确认前置。

## 已明确的取舍

- **维护方式**：以最后一次明确选择为准，维护独立 Bash 源脚本，构建时原样交付；不继续动态拼接整个脚本。用户当前源文件是 `packages/skills/build/plugins/vite-plugin-curl/install.source.sh`，插件位于同目录的 `index.ts`。
- **目录**：`dist/curl/install.sh` 与 `dist/skill/<集合>/<技能>/` 分工，`curl/` 和 `skill/` 平级。安装器内部模块的最终发布位置尚未确定；Agent 提议的 `dist/curl/script/` 不视为用户确认。
- **发布承载**：主线选择 Cloudflare R2。用户说明已有账号和域名；具体下载根、桶及发布目录规则后续确定，当前可以用占位值讨论脚本。源码仓库和发布文件承载位置分别看待，固定版本及源码追溯继续保留。
- **消费端下载**：用户进一步明确，在用户目录下新建或使用临时目录，再从 Cloudflare 下载文件。按既有清单与内容保护要求，具体组织为使用已有或新建的父目录、为本次运行创建独占子目录，先取得同版清单，再下载所选技能及附件，之后进入文件完整性校验；父目录名和公开 URL 仍可使用示例占位值。
- **本地版本与发布历史**：本地两个产物只包含当前构建，各自有当前包版本标记；历史技能版本及固定链接保留在 R2，curl 的版本表记录版本与下载地址的对应关系。不能把远端历史版本目录当作本地 `dist` 必须累积的目录结构。

## 本地产物与远端版本的关系

用户纠正的关系为：当前源码构建得到 `dist/skill/` 与 `dist/curl/`，对应产物标记当前包版本；技能包按不同版本发布到 R2，curl 记录这些版本的下载链接，消费端按用户选择查表下载。当前源码构建不自动等于最新已发布版本。

三类材料职责分开：

| 材料 | 职责与来源 |
| --- | --- |
| 当前产物版本标记 | 表明本次包版本，由对应源版本派生；本地不保存全部历史版本目录。 |
| curl 技能版本表 | 当前下载名为 release.json，数组表项含 version/url，最新在前；持久来源位于生成目录之外，后续构建交付副本。 |
| 单版文件清单 | 旧契约也叫 release.json，描述某版技能及所需文件、大小和摘要；与当前版本数组不是同一 schema，名称及路径须后续适配。 |

版本表解决“去哪里取得哪一版”，单版清单解决“这一版包含哪些文件、如何核验”，不能互相代替。版本标记、选定表项、发布内容及单版清单的版本必须一致；`latest` 先解析成具体已发布记录，后续固定该记录对应的内容与源码身份。未知或未发布版本明确失败，不回退其他版本。

## 版本管理需求与建议边界

用户已提出简易版本管理，并明确本轮追加需求；对应 [FR-068～070](../../spec.md#当前追加需求本地产物版本r2-版本表与简易版本管理2026-11-14)。需求覆盖维护源版本、构建派生版本文件、技能成功发布并核验后登记实际版本和链接。清空 `dist` 不应删除历史发布记录，构建成功或上传失败不能写成发布成功，已发布同版内容不能静默覆盖。

Agent 当前建议从现有 `packages/skills/package.json` 读取版本、为两个产物生成独立文本 `VERSION`，源码中以 JSON 维护版本表并交付到 curl；`releases/skill-versions.json` 是示例来源位置，尚未生成。第一版手工维护版本与发布记录、构建自动复制派生，也是建议；当前已明确并接入的是 version/url 数组解析和 npm 临时依赖，skill/curl 共用或分别编号、版本标记文件名、持久记录位置、发布链接指向及版本管理自动化仍待后续定案。

关于开源惯例的讨论已查阅 [Vite 的 package.json](https://github.com/vitejs/vite/blob/main/packages/vite/package.json)、[Go 的 VERSION](https://github.com/golang/go/blob/go1.24.0/VERSION)、[npm 版本字段说明](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#version)和 [GitHub Release 与 tag 的关系](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。这些材料说明版本可记录在包元数据、专用文本及发布 tag 等位置；不据少量例子断言“大部分仓库”使用某个文件名。此前 `version.json` 只是 Agent 举例，不是通用规范或用户已选格式。

## 用已有需求补全安装闭环

用户明确的是前三类动作；下面的选择、安装、挂载及清理沿已有 FR-007、FR-010、FR-011、FR-016～023 和安装契约整理，不记作用户在本轮新提出并逐项确认的要求：

```text
检查运行环境
→ 读取安装参数，确定版本、所选技能和目标位置
→ 获取本次需要的依赖及文件
→ 检查版本、必需文件、路径、大小和摘要
→ 将核验通过的所选内容安装到正式位置
→ 执行适用的隐匿及 hooks/Increment 挂载
→ 清理本次临时材料，报告结果和退出码
```

下载的具体对象根据真实运行依赖和交付边界确定，可能包括清单、运行材料和所选技能文件，不能把“下载依赖或者文件”直接等同于“必须下载另一套安装器压缩包”。下载的运行材料在核验通过前不执行；失败保留具体阶段和已有成功事实，不冒认全部完成。

## 下载阶段的具体顺序

1. 检查基础命令，在用户目录下创建带日期时间及随机后缀的独占子目录，登记退出清理，不混用上次残留。
2. npm 将固定 jq 封装包和缓存准备在本次子目录中，不全局安装或写入目标项目。
3. 从固定下载根取得版本链接表 release.json，按首个位置参数或默认 latest 解析 URL；无效表、未知或重复的指定版本及无效地址失败，不执行远端字符串。
4. 后续从选中版本的固定地址取得内容及单版文件清单，再按所选技能核验正文、附件、必需路径、大小和摘要；通过后才进入安装。当前步骤尚未接入，不因取得版本 URL 视为完成。

R2 提供静态文件访问即可，无须另写下载后端。前提是真实版本表、选中版本的内容及核验材料已发布并可通过 HTTPS 访问；当前本地构建输出不等于远端已有内容。本轮只同步流程和此前局部代码事实，不执行部署或下载。单版清单及旧 `skills/` 到当前 `skill/` 的路径适配仍待实现核对，不能直接套用旧路径声明新消费链路可用。

## 暂存的理由及确认边界

用户已明确用户目录下准备临时目录并从 R2 下载的方向；本次运行独占子目录是结合既有保护要求的组织方式。既有安装契约另要求正式技能提交前使用与目标同文件系统的暂存区；用户目录下的下载目录不保证与安装目标同文件系统，不能据此推定最终提交可直接原子移动。

暂存用于避免下载中断或校验失败时覆盖正式技能、留下新旧文件混杂的目录。失败时只清理本次可证明拥有的材料；已有内容保护继续适用。临时目录是“待校验文件的暂存区”，不固定为系统 `/tmp`，不因此承诺多文件或跨阶段原子回滚；独立运行材料和正式技能的暂存位置按各自职责确定。
