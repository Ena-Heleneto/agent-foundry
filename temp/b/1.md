# 我们需要继续完成 @packages/skills 包没有完成的构建工作

1. **讨论阶段**  
   本轮是 Spec Kit 启动前的原始需求讨论。围绕 `packages/skills` 尚未完成的构建与发布工作，结合仓库现状，逐项确认需求范围、兼容边界和验收条件。版本回退机制与测试范围在本轮讨论中确定。

2. **交付产物**  
   讨论结束后，将已确认的需求、验收条件和相关调研结论整理成一份 Spec Kit 提示词，保存到项目临时目录。

3. **流水线交付顺序**  
   先完善测试环境的发布流水线。测试环境通过约定的验收后，再扩展到生产环境。

4. **开发协作**  
   开发阶段，将彼此独立的调研、核对和审查工作尽量交给多个子代理并行处理。主代理继续推进手头工作，子代理得出结论后主动汇报。
   程中，在不影响主代理开发的情况，附属工作尽可能使用多个子代理同步进行，主代理不需要等待子代理，当子代理有结论后，汇报处理即可

### 功能点3 临时的版本管理

我们需要在流水线中支持简易版的版本管理
在构建是生成的VERSION文件中新增一个时间戳字段
流水线中新增一个job，将线上的 release.json 拉取下来，然后编辑，在最上层添加VERSION的时间戳作为最新的版本
产物全部就绪后，在最后环节统一上传的R2
这是没有版本管理工具情况下的临时处理
我们需要回兼容性回退机制，将临时处理的代码放到临时的目录中，等版本管理工具上线在切换过去

## 注入的知识

1. **原始需求讨论阶段**  
   从全仓视角识别受影响的模块和调用方，完整核对相关的构建入口、集合配置、发布工作流、安装脚本和测试入口。围绕待定问题查阅相关主流工具的做法，记录适用条件和对本项目的影响。

2. **提示词交接**  
   将已核实的仓库事实、已确认的需求与约束、待确认的问题分别写入提示词。需要后续复核的结论附上文件路径或文档链接。

3. **Spec 需求分析阶段**  
   基于提示词中的证据核对当前仓库。将影响需求范围、兼容行为或验收条件的内容写入 `spec.md`，将实现参考和方案调研交给规划阶段。待确认事项继续标记为待确认。

4. **生成 `speckit.tasks` 前**  
   基于已有的 spec、plan 和调研记录，复核当前分支上的相关实现、可复用入口和验证方式。发现仓库现状变化或影响范围遗漏时，先补充对应材料，再拆分任务。

5. 创建spec目录后，将原始需求提示词移动到spec目录内并重命名
