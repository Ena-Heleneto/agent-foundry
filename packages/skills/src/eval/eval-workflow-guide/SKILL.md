# 模块重构与迁移分阶段执行指南（eval-workflow-guide）

## 适用场景

本技能为实测评估专用样本技能。当对现有业务模块或功能包进行结构重构、接口解耦或目录迁移时，必须严格按照本指南的四阶段流程推进，不得跳步执行。

## 流程总览

重构全流程分为四个顺序阶段：
1. **阶段一：影响面分析与测试基线锁定**
2. **阶段二：新旧接口共存与适配层搭建**
3. **阶段三：调用方平滑切换与逐项替换**
4. **阶段四：废弃旧实现与清理验证**

---

## 阶段一：影响面分析与测试基线锁定

### 1.1 分析目标
在动任何代码之前，必须明确本次重构的输入边界与下游消费方。

### 1.2 步骤要求
1. **清点被改动符号**：
   - 导出函数、类、类型定义及配置项。
   - 使用文本搜索或 AST 工具检索当前仓库内全部消费点，形成清单。
2. **确认既有测试覆盖**：
   - 运行该模块现有的全部单元测试与集成测试，确认测试全部通过。
   - 若测试覆盖不足，必须先在重构前补齐针对原行为的基线测试，确保重构有据可查。
3. **输出阶段交付物**：
   - 在模块根目录或会话中列出《重构影响面清单》，包含受影响文件路径、预估修改行数及风险评级（低/中/高）。

### 1.3 准出条件
- [ ] 既有测试 suite 运行通过率 100%。
- [ ] 下游所有依赖引用位置已完全盘点，无隐匿动态导入。

---

## 阶段二：新旧接口共存与适配层搭建

### 2.1 原则
必须采用「扩展并共存」（Expand and Contract）策略，避免破坏性一次性切换。

### 2.2 步骤要求
1. **建立新接口规范**：
   - 在新路径或新命名空间下创建目标接口与实现。
   - 新接口必须具备完备的类型声明与参数校验。
2. **构建薄适配层（Adapter）**：
   - 若需兼容旧调用方，保留旧入口函数或旧文件。
   - 旧入口内部直接将调用委托至新实现，并可在控制台或日志中打印废弃警告（如 `@deprecated` JSDoc）。
3. **编写针对新接口的独立测试**：
   - 确保新接口的单元测试独立运行且测试用例全面覆盖边界条件。

### 2.3 准出条件
- [ ] 新接口与测试全部绿色。
- [ ] 旧接口通过适配层委托到新实现，旧测试依然 100% 绿色通过。

---

## 阶段三：调用方平滑切换与逐项替换

### 3.1 步骤要求
1. **逐个文件迁移**：
   - 按照影响面清单，由内而外逐个将消费端导入路径和调用方式修改为新接口。
   - 每修改一个消费模块，立即运行该模块的相关测试。
2. **验证数据兼容性**：
   - 检查返回值结构与参数传递是否无缝承接。
   - 禁止在切换过程中改变底层业务计算结果或副作用时序。
3. **提交与回滚准备**：
   - 单个模块切换完成后可形成原子提交，便于若遇回归缺陷时进行二分排查。

### 3.2 准出条件
- [ ] 生产代码中不再存在对旧接口的直接引用。
- [ ] 全量工程编译通过，所有既有单测与集成测试通过。

---

## 阶段四：废弃旧实现与清理验证

### 4.1 步骤要求
1. **废弃声明核验**：
   - 再次全工程搜索旧接口标识符，确认零消费。
2. **移除适配层与旧文件**：
   - 安全删除过时的适配函数、旧文件以及专为过渡而建的临时别名。
3. **文档与注释同步更新**：
   - 更新模块 README、API 契约文档或类型导出入口。
   - 修正所有引用旧路径的代码注释。
4. **全量构建与端到端复验**：
   - 执行工程完整构建命令（如 `pnpm build` 或 `npm run test:all`），确保产物纯净无遗留。

### 4.2 准出条件
- [ ] 旧文件已彻底移除，无编译残留。
- [ ] 全仓库类型检查无报错、构建无告警、全测试套件全绿。

---

## 异常与回退机制

1. **若阶段三中发现未预期下游依赖**：
   - 立即停止继续修改，退回阶段二，补全新旧适配映射。
2. **若测试在重构后出现断言失败**：
   - 优先比对阶段一记录的基线输出，判定是行为故意演进还是逻辑回归；严禁为了让测试变绿而盲目修改测试断言。
